# 0.2.8 → 0.3.0 검토

2026-09-10 기준으로 코드 결함 2건과 사용자 문서 불일치 1건을 확인했다. 가장 먼저 고칠 부분은 게임에서 만든 F10 자료를 진단 도구가 읽지 못하는 문제다. 기존 테스트 742개와 플러그인 빌드가 통과해도 이 문제는 검출되지 않는다.

아래 본문은 수정 전 검토 기록이다. 후속 요청으로 세 건을 모두 수정했으며, 수정 내용과 검증 결과는 마지막 절에 기록했다. 아래 수치는 명시한 시험 입력의 결과이며 실제 전투 측정값이 아니다.

## 범위와 근거

- 기준: `v0.2.8`의 `3c1846f` → `v0.3.0` 및 HEAD의 `3c5069f`. 3개 커밋, 83개 파일, 추가 5,515줄·삭제 444줄이다. 시작 시 작업 트리는 깨끗했다.
- 구조: 게임 상태·카탈로그 수집은 Plugin, 배치와 전투 평가는 Core, 저장 자료의 재현은 DataTool에서 실행한다. Tests는 .NET 10에서 Core와 일부 연결된 Plugin 소스를 검사한다.
- 문서: README·CHANGELOG·STATUS·ROADMAP, DPS 안내·설계·구현·재검토·후속 기록, 배치 목적함수, 아이템 제안, 기존 제보 회귀 점검, 재현 안내를 코드 경로와 대조했다. 과거 문서가 명시적으로 한정한 당시 상태를 현재 결함으로 세지 않았다.
- 주요 경로: 능력치 출처 교체, 피해·마나·충전·시간 계산, 배치 후보와 최종 평가, 획득·제외·합성 추천, 설정 저장·복원, F2/HUD 갱신, F8 보호 정책, F10 저장·재현.
- 게임 근거: 설치된 1.0.30의 `Assembly-CSharp.dll`. SHA-256은 `C3939A7D431F1362DACA655938480569E11F501F7D0820A989873765555A7C39`다. 피해·능력치·무기·마법·지원 관련 클래스를 ILSpy 11.0.0.9375로 디컴파일했다.
- 실행 환경: SDK 10.0.401, 프로젝트 Core의 `netstandard2.1`, 진단 도구·테스트의 .NET 10, 게임에 포함된 `MonoBleedingEdge/EmbedRuntime/mono-2.0-bdwgc.dll`. 게임을 실행하지 않고 별도 검사 프로세스에서 이 Mono와 같은 Core DLL을 사용했다.

## P1 — 게임에서 저장한 전투 재현 자료가 지문 불일치로 거부됨

위치: `src/SephPlanner.Core/Combat/CombatFingerprint.cs:35–36`. 이 문자열이 `PlanFingerprint`에 포함되고, `PlanReplay.Rebuild`의 49–50행에서 일치 여부를 검사한다.

새 전투 지문은 실수를 `Convert.ToString(value, InvariantCulture)`로 기록한다. 문화권은 고정하지만 유효 자릿수는 고정하지 않는다. 게임의 Mono와 .NET 10은 같은 double의 기본 문자열을 다르게 만든다. `CombatReader`가 읽는 마나 회복 타이머의 실제 기본 필드값 `0.85f`만으로 재현된다.

| 항목 | 게임의 Mono | .NET 10 |
| --- | --- | --- |
| `(double)0.85f`의 기본 문자열 | `0.850000023841858` | `0.8500000238418579` |
| 같은 값의 `G17` 문자열 | `0.85000002384185791` | `0.85000002384185791` |
| 같은 전투 입력의 배치 지문 | `3449998e72964ce17fb2c58df946305a006fe4e30a8250c57050800cd36d4d73` | `68343fab7c52b2278564ddb60a9a51d92020bfa0747a71c203595d7efbd80e33` |

최소 인벤토리와 같은 Core DLL을 사용해 Mono에서 Newtonsoft.Json으로 정상 재현 파일을 저장한 뒤, 현재 DataTool의 `--reproduce`로 읽었다. 파일 자체의 SHA-256 검사를 통과한 뒤 다음 결과로 실패했다.

```text
계획 재현 실패: 스냅샷·설정의 지문이 게시된 계획과 다릅니다.
종료 코드: 1
```

같은 검사 코드를 .NET 10에서 실행해 저장한 대조 파일은 결과 일치, 종료 코드 0이었다. 따라서 JSON 라이브러리만 바꾸어 같은 .NET 런타임 안에서 수행하는 기존 재현 테스트로는 잡히지 않는다. `--allow-model-change`도 코드 버전 검사만 완화하므로 이 지문 검사를 우회하지 않는다. `.replay` 기반 `--churn` 역시 먼저 `Rebuild`를 호출한다.

영향: F10의 핵심 목적이던 실제 게임 제보 재현과 반복 배치 진단이 일반적인 전투 스냅샷에서 막힌다. 파일 손상이나 사용자 설정 문제로 안내되어 원인을 잘못 추적할 수 있다.

권고: 실수 지문을 런타임에 독립적인 고정 표현으로 정의하고, Mono에서 생성한 파일을 .NET에서 재생하는 검사를 추가한다. 같은 값의 `G17` 표현은 이번 두 런타임에서 일치했으며, 비트 표현을 쓰는 방법도 있다. 이미 저장된 형식 5 자료에 대한 호환·이관 정책도 함께 정해야 한다. 지문 검증 자체를 제거하는 방식으로 해결하지 않는다. 기본 숫자 형식의 정밀도 차이는 [Microsoft 공식 문서](https://learn.microsoft.com/en-us/dotnet/standard/base-types/standard-numeric-format-strings#general-format-specifier-g)에도 설명되어 있다.

근거 파일: `artifacts/review-030/RuntimeProbe.cs`, `run_mono.py`, `runtime-mono.log`, `runtime-net10.log`, `reproduce-mono.log`, `reproduce-net10.log`. 생성된 `mono.replay`와 `net10.replay`도 같은 디렉터리에 있다.

## P2 — 마법 비용 반올림이 게임과 달라 시전 수와 DPS가 바뀜

위치: `src/SephPlanner.Core/Combat/CombatSimulator.cs`의 `State`, 마법 비용을 계산하는 210–212행.

게임의 `Charm_Magic.GetCost`는 float로 `기본 비용 + 기본 비용 × (비용 보정 / 100f)`를 계산한 뒤 `Mathf.RoundToInt`를 적용한다. 설치된 `UnityEngine.CoreModule.dll`에서 이 메서드가 `(int)Math.Round(f)`인 것도 대조했다. 현재 Core는 double로 `기본 비용 × (1 + 비용 보정 / 100d)`를 계산한 뒤 반올림한다. 수학적으로 같은 식이어도 반 정수 경계에서 결과가 달라진다. 반올림 정책 자체보다 그 앞의 정밀도·연산 순서가 원인이다.

같은 합성 마법 입력을 두 런타임에서 실행하고, 게임 코드와 같은 float 비용식과 비교했다. 아래 불일치가 양쪽에서 동일하게 나왔다.

| 기본 마나 비용 | 비용 감소 | 게임 비용식 | 현재 시뮬레이터 |
| --- | --- | --- | --- |
| 15 | 70% | 4 | 5 |
| 25 | 42% | 14 | 15 |
| 30 | 55% | 14 | 13 |
| 35 | 70% | 10 | 11 |

이 표는 특정 실전 가방이나 해당 마법 프리팹의 지원 여부를 가정한 자료가 아니라, 지원하는 마법 비용 계산 경로의 시험 입력이다. 실행 검사에서는 마나 100으로 시작하고 마법을 한 번 사용한 뒤 실제 잔여 마나로 비용을 확인했다.

영향: 마나가 정확히 필요한 양만 남은 경우 시전 가능 여부가 달라지고, 공유 마나를 사용하는 다른 마법의 순서·횟수도 바뀐다. `MAGICMP`가 있으면 사용 마나에 비례하는 한 발 피해까지 달라진다. 비용 감소를 주는 별조각·능력치의 배치 및 획득 추천에 영향을 줄 수 있다.

권고: 게임과 동일한 float 연산 순서로 비용을 계산한 뒤 반올림한다. 위 경계와 정확히 비용만큼 남은 마나, 비용 보정 합산, 두 마법의 공유 자원을 검증한다. 허용 오차를 더하거나 임의로 비용을 올림·내림하지 않는다.

근거 파일: `artifacts/review-030/RuntimeProbe.cs`, `runtime-mono.log`, `runtime-net10.log`. 게임의 `Charm_Magic.GetCost` 디컴파일은 같은 디렉터리의 `decompiled/Charm_Magic.cs`에 보관했다.

## P3 — README의 콤보 완성 후보 순위 설명이 이전 평가 기준에 머물러 있음

위치: `README.md:247–250`.

README는 임계값에 닿는 후보가 초록색으로 표시되고 순위에서도 올라간다고 설명한다. 현재 `OfferAdvisor.Rank`는 DPS 모드에서 `ComboBonus`를 0으로 만들며, 기본 설정에서는 프리셋·콤보 강제 우선도 해제한다. 초록색 표시는 남지만 콤보 완성 자체에 대한 별도 순위 가산은 없다. 계산 가능한 콤보 효과가 전체 DPS를 높인 만큼만 반영된다. 명시한 빌드 우선 설정은 별도다.

권고: 색상은 콤보 발동을 알리는 표시이며 기본 순위는 전체 DPS 변화량에 따른다고 바로잡고, `빌드 우선 → DPS`에서 지정이 앞서는 조건을 구별한다. `docs/DPS.md`에는 이미 이 구분이 있어 README와 설명이 충돌한다.

## 회귀로 판정하지 않은 변경과 남은 검증

다음은 문서·코드·기존 검사에서 의도적으로 처리하고 있는 범위다.

- 강화·양보 배수 무시와 콤보·프리셋의 기본 강제 우선 해제는 명시된 정책 변경이다. 저장된 지정은 보존하고 빌드 우선을 별도로 켠다.
- 마음의 짐 예외는 단순히 DPS가 0인 모든 아이템에 적용하지 않는다. 수집된 자체 활성 효과 유무를 사용하며 명시적 사용 유지·고정과 주변 효과는 유지한다.
- 천칭 좌우 능력치와 방향 제약은 배치·획득·제외·합성·설정·재현에 전달된다. 영원의 식과 같이 평가한다.
- 기존 활성·지원 연결 보호, 버리기 불가 아이템의 제외·교체 방지, 합작 창 열림에 따른 HUD 갱신에는 이번 검토 범위에서 추가 결함을 확정하지 않았다.
- 무기 동작 시간 1초·추가 대상 적중 50%, 행성·다른 고유 공격·상태 이상·추가 발동·관측 잔여 능력치 고정은 문서에 명시된 추정·미지원 범위다. 새로 발견한 버그 수에 포함하지 않았다. 특히 행성 중심 빌드의 추천을 모든 공격을 포함한 실전 DPS 최대화로 해석할 수 없다.
- 미지원 자동 적용 제한은 아이템 상태·주변·지원 연결·콤보 수량의 알려진 관계를 검사한다. 고정된 미지원 공격에 대한 전역 능력치 변화 등 모든 상호작용을 막는 보장은 아니며, 문서도 이를 한정한다.
- 실제 로컬 활성 카탈로그는 아직 형식 15다. 형식 18의 실행 중 수집, F2 화면 크기·입력, F8 싱글·멀티 이동, 실제 피해 대조는 이번 검토에서 수행하지 않았다. 게임을 켜지 않고 어셈블리를 실행한 검사는 이 항목들을 대신하지 않는다.

## 후속 수정과 검증 — 2026-09-10

사용자 요청으로 P1·P2·P3을 모두 수정했다.

- P1: 전투 관측값·설정과 수동 가치의 double 지문을 런타임에 독립적인 비트 표현으로 바꿨다. 새 재현 형식은 6이며, 형식 5는 이전 Mono·.NET 표현으로 지문을 검증한 뒤 재생한다. Mono의 G15·G17에서 중간값을 반올림하는 방향도 재현한다. 빌드 변경 허용과 입력·파일 손상 검사는 유지하며 형식 6에서 구형 지문으로 우회하지 않는다.
- P2: 마법 비용을 게임과 같은 float 정밀도와 덧셈·곱셈 순서로 계산한 뒤 반올림한다. 비용 감소·증가의 합산, 무료 마법, 정확히 필요한 마나, 우선순위가 다른 두 마법의 공유 마나와 사용 마나 비례 피해를 검증했다.
- P3: README에서 초록색은 콤보 발동 표시이며 기본 순위는 전체 예상 DPS 변화량을 따른다고 바로잡았다. 지정한 콤보·프리셋이 앞서는 `빌드 우선 → DPS` 조건도 명시했다. 재현 안내·DPS 안내·현재 상태·변경 기록을 함께 갱신했다.

회귀 검사 33개를 추가했다. `scripts/check.ps1`에서 포맷, 전체 테스트 775개, DataTool·Plugin Release 빌드가 통과했다. 실패·건너뜀·빌드 경고·오류는 0이다. 로그는 `artifacts/fix-030/check.log`에 있다.
