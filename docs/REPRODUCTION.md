# 계획 재현

F10의 `inventory-snapshot.json`은 누른 순간의 관측값이다. 마지막으로 게시된 계획은 더 이른
입력으로 계산됐을 수 있고, 빌드 설정과 이전 목표도 결과에 영향을 준다. 그래서 계획 재현은
별도의 `.replay` 파일을 사용한다.

## 저장되는 것

`%LOCALAPPDATA%\SephPlanner\reproductions\<시각>-<식별자>.replay`에 매번 새 파일을 만든다.
자동 정리는 하지 않으므로 필요 없는 기록은 직접 지울 수 있다. F10은 새 계산을 기다리거나
실행하지 않고 마지막으로 성공적으로 게시된 계획을 보존한다. 게시된 계획이 없으면 기존
인벤토리 진단만 남기고 재현 자료가 없다는 안내를 표시한다.

- 그 계획에 실제로 사용한 스냅샷과 계산 설정: 콤보, 강화·양보, 사용 유지, 제한 해제 고정,
  프리셋 즐겨찾기, 수동 가치 자료, 추천 ON/OFF.
- 계산기가 사용한 메모리 카탈로그 전체. 디스크의 현재 활성 카탈로그로 대체하지 않는다.
- 당시 `PlanBuilder`에 전달된 직전 계획의 목표 목록. 나머지 이전 계획 정보는 계산에 사용하지 않는다.
- Core의 정보 버전·모듈 식별자, 게임·플러그인 정보, 카탈로그 형식·세대, 요청 지문,
  게시된 요청 번호·마지막 요청 번호와 최근 계산 오류.
- 현재·제안 점수, 배치·레벨·검증 상태·경고, 자동 적용 목표의 순서와 추천 요약.

파일은 형식 표식, JSON 본문의 SHA-256, JSON 본문으로 구성된다. 완성한 파일을 원자적으로
게시하고 이전 기록을 덮어쓰지 않는다. 해시는 우발적인 손상 검사용이며 작성자를 인증하는 서명은 아니다.
게임에서 수집한 카탈로그가 들어 있으므로 저장소·릴리스·공개 제보에 넣지 않는다. 0.2.8부터 진단 전송 기능에서는 사용자가 동의한 경우에만 비공개 수집 서버로 보낸다. [수집 범위와 동의](DIAGNOSTIC-UPLOAD.md)를 참고한다.
외부 전송이나 업로드 기능은 없다.

## 재생

```powershell
dotnet run --project src/SephPlanner.DataTool -c Release -- --reproduce "<파일.replay>"
dotnet run --project src/SephPlanner.DataTool -c Release -- --reproduce "<파일.replay>" --allow-model-change
dotnet run --project src/SephPlanner.DataTool -c Release -- --help
```

첫 명령은 같은 Core 빌드를 요구한다. 버전 문자열이 같아도 모듈 식별자가 다르면 거부한다.
코드를 수정한 뒤 비교하려면 두 번째 명령으로 차이를 명시적으로 허용한다. 이 옵션도 파일
손상, 지원하지 않는 자료·카탈로그 형식, 빠진 설정이나 입력 지문 불일치를 허용하지 않는다.
성공 메시지는 저장한 비교 항목의 일치이며 모든 내부 상태나 실제 전투 효과의 인증이 아니다.

| 종료 코드 | 의미 |
|---|---|
| 0 | 저장된 비교 항목과 일치 |
| 1 | 파일·형식·빌드·입력 또는 실행 오류 |
| 2 | 재생은 완료됐지만 저장 결과와 차이 있음 |

**지문에 항목을 더할 때는 조건부로 더한다.** 새로 읽기 시작한 상태를 `PlanFingerprint` 에
무조건 실으면 그 값을 모르는 옛 `.replay` 가 전부 종료 코드 1("입력 지문 불일치")로 거부된다 -
인챈트 제단을 넣으면서 실제로 그렇게 했다가 `reports/` 열둘 중 열이 재생조차 못 했다
(2026-09-15). 합성기의 `mixerNear` 가 조건부인 이유도 같다. 지문을 건드렸으면 **변경 전후로
`reports/` 열둘을 돌려 견준다** - 달라도 되는 것은 어셈블리 식별자를 적는
`계산 코드 차이` 줄뿐이다.

좌표·아이템·회전·추천 순위·상태는 정확히 비교한다. 점수는 Mono와 .NET 사이의 부동소수
차이를 고려해 절대 차이 `1e-8`까지 허용한다. 이는 전투 효율 오차를 측정한 값이 아니라
수치 비교를 위한 허용치다. 후보 미리보기는 점수·표시 이름·유효 레벨 요약을 비교하며 UI의
모든 표시 속성이나 전투 이벤트열까지 비교하지 않는다.

새 요청이 계산 중이거나 실패했을 때 저장하면 마지막 게시 계획이라는 안내가 나온다.
파일의 `Snapshot`과 별도 `inventory-snapshot.json`을 같은 순간의 자료로 취급하지 않는다.
기존 `--check`, `--replay`, `--churn`은 현재 로컬 카탈로그와 기본 선호도를 사용하는 경로로
남아 있다. 특히 기존 `--replay`의 개별 해석 실패 종료 코드 문제는 이번 새 재현 명령과 별개로 남아 있다.

## 검증 범위

합성 입력으로 플러그인의 Newtonsoft.Json 저장 → 진단 도구의 System.Text.Json 읽기 →
`PlanBuilder` 재실행을 검사한다. 좌표, 설정 전체, 충돌하는 수동 가치 식별자, 이전 목표,
원본 카탈로그 변경, 진행 중·실패한 요청, 파일 손상·입력 누락·다른 빌드·결과 차이를 다룬다.
직렬화 계약은 [System.Text.Json 역직렬화](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/deserialization)와
[Json.NET 직렬화 문서](https://www.newtonsoft.com/json/help/html/SerializationAttributes.htm)를 확인했다.
의존성 버전은 변경하지 않았다. 테스트는 Newtonsoft.Json 13.0.3을 사용하며 실제 Plugin은 게임에
포함된 어셈블리를 참조하므로 Unity에서 F10 파일을 저장하고 재생하는 확인은 별도로 필요하다.

실기에서는 새 DLL로 F2 설정과 후보가 있는 상태에서 F10을 누르고, 파일 생성·HUD 안내·재생
결과를 확인한다. 계산 중·추천 OFF·F9 재수집 뒤 과거 기록 재생도 확인한다. 실행 시간과
할당량, 디스크 저장으로 인한 프레임 영향은 아직 게임 안에서 측정하지 않았다.

## 0.2.8 기반 후속 패치 호환

새 자료는 재현 형식 9·카탈로그 21을 사용한다. 카탈로그 20으로 모은 자료도 계속 재생한다 -
21은 성장 아티팩트의 목표 횟수와 바뀔 대상을 더하기만 한 형식이라, 빠진 항목은 수집하지 않은
것으로 읽혀 그때의 결과가 그대로 나온다. 카탈로그 형식 검사는 `--allow-model-change`로도 넘을
수 없으므로, 여기서 빼면 그 버전으로 모인 제보가 영영 재생되지 않는다. 0.3.x와 실험 빌드에서 사용한 형식 2~8을
재사용하지 않는다. 이번 버전은 구형 형식 1·카탈로그 15를 별도로 지원한다.
게임 Mono와 진단 도구 .NET의 숫자 문자열 차이를 없애고, 구형 자료는 저장 당시의 두 숫자
표기를 검증한다. 입력 변조 검사는 계속 적용한다. 계산 코드가 바뀌면 기존과 같이
`--allow-model-change`가 필요하며, 0.3.x 전투 포함 재현 자료는 지원하지 않는다.
테스트의 `Fixtures/replay-v1-mono.json`, `replay-v9-mono.json`은 실제 게임 Mono 런타임에서
인공 입력으로 생성한 회귀 자료다. 게임 자산이나 실제 플레이 기록은 포함하지 않는다.
