## 1. 종합 판단

**프로젝트를 전면 재작성할 이유는 없다. 게임 상태 읽기 → 독립적인 계산 → 검증 → 게임 경로로 적용하는 기본 구조를 유지하면서, 적용 완료의 정확성·추천 근거·화면 상태의 명확성을 보강하는 것이 가장 효과적이다.**

Core와 게임 어댑터를 분리했고, 오래된 계산 결과를 버리며, 적용 전 상태를 검증하고 실패 시 되돌리는 장치도 있다. 단위 테스트와 재생 도구, 카탈로그 세대 관리, 배포 파일 해시까지 갖춰져 있다. 작은 게임 플러그인으로서 유지보수 기반이 상당히 마련된 상태다.

반면 사용자가 가장 중요하게 여길 질문에는 아직 빈틈이 있다.

- **“정말 적용됐나?”** 회전이 목표 각도에 도달하지 않아도 완료로 처리하는 경로를 가짜 인벤토리에서 재현했다. 서버 반영 제한 시간을 넘긴 명령은 중단 안내 뒤에 반영될 수 있다.
- **“이 추천을 얼마나 믿어도 되나?”** 게임 능력치로부터 환산한 점수와 실제 전투 효용은 다르다. 고유 효과가 레어도 추정에 머무는 항목도 있고, 빌드 의존 효과의 지원 범위가 제한적이다.
- **“지금 무엇을 보고 있나?”** 후보 미리보기 격자와 현재 보유품의 이동 안내가 함께 표시된다. 점수, 안내, 적용 대상이 서로 다른 문맥을 가질 수 있다.
- **“내 설정대로 다시 재현되나?”** 재생 도구는 기본 선호도로 계획을 만들기 때문에 강화 우선·제한 해제 고정 등이 있는 실제 플레이와 조건이 달라질 수 있다.

추천 순서는 **자동 배치 예외 경로 → 조작·표시 불일치 → 재현성과 CI → 점수 근거 보완 → 편의 기능 확장**이다. 탐색 폭 확대나 대규모 UI 재설계부터 시작할 필요는 없다.

## 5. 자동 배치와 안정성

### A1. 회전 성공 조건이 목표 각도 도달을 보장하지 않는다

**근거:** `src/SephPlanner.Core/Runtime/ApplyPlanRoutine.cs:472`, 특히 `PressOnce`의 502행. 성공 판정은 “이전 회전값과 달라졌는가”다. 목표 한 단계와 같은지, 모든 회전 뒤 최종 각도가 명령의 `Rotation`과 같은지 확인하지 않는다.

**재현:** 석판의 현재 회전 0, 목표 1에서 한 번 누른 뒤 2가 관측되는 가짜 포트를 사용했다. 외부 우클릭이 겹치거나 여러 변화가 한 번에 관측되는 조건을 모델링한다.

```text
ROTATION target=1 actual=2, result=자동 배치 완료 - 이동 0건, 회전 1건
```

레벨 검사는 이 문제를 완전히 대신하지 못한다. 방향이 달라도 레벨 결과가 같은 석판·격자에서는 차이가 드러나지 않을 수 있고, 레벨 차이가 있어도 현재 구조는 완료에 경고를 덧붙인다.

**개선:** 각 누르기에서 예상 다음 회전값을 확인하고, 종료 전 모든 대상의 위치·회전을 다시 검증한다. 예상 밖의 회전은 임의로 누르기 횟수만 보정하지 말고 외부 변경 또는 동기화 불확실 상태로 처리한다.

**완료 기준:** 정상 0→1, 순환 3→0, 0→2 관측, 석판 소멸, 이동 중 회전값 변화 모두 테스트. 최종 위치·각도가 다르면 일반적인 “완료”가 나오지 않아야 한다.

### A2. 타임아웃은 이미 보낸 명령의 취소가 아니다

**근거:** 같은 파일의 `SyncTimeout = 3`, `ApplySwaps` 277~299행. 명령 발송 뒤 3초 안에 맞바꿈이 관측되지 않으면 중단한다. 저널에는 확인된 이동만 추가한다.

**재현:** 처음 상태 `[1,2,0]`, 명령 지연을 4초로 설정했다.

```text
LATE completion t=3.0, cells=1,2,0, result=(0,0) → (1,0) 이동이 게임에 반영되지 않아 자동 배치를 중단했습니다.
LATE after delayed command cells=2,1,0
```

중단 시점에 상태가 그대로여도, 나중에 인벤토리가 바뀔 수 있다. 이미 확정된 다른 이동을 역순으로 되돌리는 것만으로는 미확인 명령까지 복구했다고 보장할 수 없다. 이 재현은 Core의 시간 모델에 대한 것으로, 실제 서버에서 4초 지연이 얼마나 흔한지 보여주지는 않는다.

**개선:** 상태를 “거부됨”과 “반영 여부 미확정”으로 구분한다. 미확정 쓰기가 남은 동안 새 F8 적용을 차단하고 최신 상태를 대조한다. 늦은 반영을 추적할 정보도 남겨야 한다. 게임 프로토콜에 명령 ID·취소·확정 응답이 없다면 클라이언트 대기 시간을 늘리는 것만으로 원자성을 보장할 수 없으므로, 불확실 상태를 정직하게 알리는 것이 우선이다.

**완료 기준:** 3초 이내 반영, 3초 이후 반영, 영구 무응답, 실패 후 재시도, 늦은 반영과 되돌리기 교차를 가짜 포트로 시험한다. 확인하지 못한 복구를 성공으로 표시하지 않는다.

### A3. 적용 도중 사용자·게임이 바꾼 칸을 보호해야 한다

**근거:** `ApplySwaps`는 시작 시 만든 `positions`·`occupants`를 사용한다. 각 `Swap` 직전 실제 두 칸의 인스턴스가 예상과 같은지 검사하지 않는다. `Rollback` 350행도 역방향 맞바꿈을 먼저 보내고 결과를 확인한다. 회전의 `PressOnce`에는 칸 소유 확인이 있어 이동 경로와 보호 수준이 다르다.

**부분 재현:** 첫 이동이 반영된 뒤 다음 프레임 전에 사용자가 해당 칸을 다른 칸과 맞바꾼 조건에서 적용기는 “이동이 게임에 반영되지 않아” 중단했다고 표시했다. 실제로는 한 번 반영됐고 외부 변경이 뒤따른 상태였다. 최종 상태는 `[2,3,1]`이었다. 완료를 잘못 보고하지는 않았지만 원인과 복구 범위를 정확하게 구분하지 못했다.

**개선:** 쓰기 전 예상 인스턴스 쌍을 검사하고, 외부 변경된 칸에 되돌리기를 강행하지 않는다. 마지막에 목표 전체를 검증한다. 이는 서버 처리 시점까지의 변경을 막는 원자적 잠금은 아니므로, 참가자 경로는 여전히 A2의 미확정 상태 관리가 필요하다.

**완료 기준:** 서로 무관한 칸 변경, 다음 이동 대상 교체, 확정된 대상 재이동, 되돌리기 대상 교체, 층 이동·사망·접속 종료를 주입해 예상 밖 아이템에 후속 쓰기를 보내지 않는지 확인한다.

### 적용기의 추가 보완

- `Progress`는 첫 이동이 확인된 뒤 갱신된다. 첫 서버 왕복을 기다리는 동안에는 빈 진행 문자열이 가능하다. 발송 전에 “이동 1단계 반영 대기”를 설정한다.
- 이동 진행의 분모는 `Targets.Count`, 분자는 실제 맞바꿈 수다. 제자리에 있는 대상과 맞바꿈으로 함께 정리된 대상 때문에 동일한 단위가 아니다. 실제 연산 수를 사전 산출하거나 단계명 중심으로 표시한다.
- 코루틴 중단 시 `InProgress`를 시간으로 풀어주는 장치는 영구 잠금을 완화하지만, 중단된 작업이 어느 상태로 남았는지를 복구하지는 않는다. 작업 식별자와 종료 사유를 기록하고 재활성화 시 재대조해야 한다.
- 실제 멀티 회전·되돌리기·진행 표시는 기존 ROADMAP에서도 잔여 실기 항목이다. Core 테스트와 별도로 릴리스할 DLL로 확인해야 한다.

## 6. UI/UX 상세 검토

### U1. 미리보기에서는 격자·점수·이동 안내의 문맥을 일치시켜야 한다

**근거:** `src/SephPlanner.Plugin/Ui/NativeHud.cs:515`는 기본 계획 점수를 표시하고, 542행은 후보 미리보기 격자를 그리지만 543행은 그대로 `RenderMoves(plan)`을 호출한다. `Plugin.cs`의 `AutoPlace`도 기본 계획을 적용한다.

따라서 후보를 집었을 때의 격자를 보면서 현재 보유품 기준 이동 순서를 읽거나 F8을 누를 수 있다. 후보 목록에 `>` 표시는 있지만, 사용자가 화면의 숫자·격자·이동 안내를 하나의 계획으로 읽는 문제까지 해결하지는 않는다.

또한 `Plugin.cs:706`의 일시적 결과 안내가 미리보기 설명보다 우선한다. 불투명도·접기 안내나 자동 배치 결과가 표시되는 동안 미리보기 격자는 유지되는데 설명 줄은 다른 내용이 될 수 있다.

**권장 동작:** 격자 바로 위에 `후보 미리보기: 아이템명`을 고정 표시한다. 기본 점수와 후보 효과를 명확히 구분하고, 기존 이동 목록은 미리보기에서 숨기거나 “현재 보유품 배치 안내”로 분리한다. F8은 미리보기 해제 후 실행하거나 해당 상태에서 적용 대상을 명확히 알려야 한다. 새 확인 팝업을 매번 추가하기보다는 상태 자체를 명확하게 만드는 편이 낫다.

**완료 기준:** 미리보기 중 F5/F6/F7/F8, 일시 알림, 후보 정렬 변화, 후보 사라짐을 조합해도 보고 있는 격자의 의미가 계속 식별돼야 한다.

### U2. HUD를 끄면 빌드 창의 우클릭 기능도 꺼진다

**근거:** `Plugin.cs:151`~152에서 F2/F3 창 열기는 HUD 활성화 조건 밖에 있지만, 168행의 `_build.RightClick` 호출은 `_settings.Panel.Value` 조건 안에 있다.

**재현 절차:** F3에서 인게임 화면을 끈다 → F2로 빌드 창을 연다 → 아티팩트 우선도를 좌클릭으로 올린다 → 우클릭으로 내린다. 코드상 우클릭 전달이 생략된다. 화면 옵션이 데이터 편집 기능을 제한하는 일관성 문제다.

**개선:** 빌드 창 입력을 HUD 표시 조건에서 분리한다. 창이 실제 최상위 입력 소유자인지도 함께 확인한다.

### U3. “다른 빌드 코드”와 “지우기”의 적용 범위가 모호하다

**근거:** `PluginPreferences.cs:113`의 `TryImport`는 새 프리셋의 양수 카테고리를 기존 `PriorityCategories`에 추가한다. `ClearPreset` 129행은 코드만 지운다.

빌드 A에서 지정된 콤보가 빌드 B를 가져온 뒤에도 남으며, 코드 지우기로도 없어지지 않는다. 가져온 콤보를 수동 지정으로 바꾸는 현재 설계에는 이유가 있지만, 교체 UI가 누적 동작을 충분히 설명하지 않는다.

**개선:** 수동 지정과 프리셋에서 파생된 지정을 구분해 관리한다. 기본 교체는 이전 프리셋 몫을 제거하고 수동 지정은 보존한다. 누적을 유지한다면 버튼 설명에 “기존 콤보 지정에 추가”와 “코드만 지우기”를 명시한다. 기존 사용자의 지정을 일괄 지우는 마이그레이션은 피한다.

**완료 기준:** A→B 교체, 같은 코드 재가져오기, 코드 삭제, 수동 지정과 중복된 콤보, 이전 설정 형식에 대한 결과를 고정한다.

### U4. “피하는 콤보 N개”를 실제 반영한 것처럼 읽을 수 있다

**근거:** 같은 파일의 `Summary`는 음수 카테고리 수를 표시하지만 `TryImport`는 `pair.Value <= 0`을 건너뛴다. 요약이 읽어낸 데이터인지, 추천에 반영한 설정인지 구분되지 않는다.

**개선:** 기능 구현 전에는 `피하는 콤보 N개는 아직 추천에 반영하지 않음`으로 알린다. 실제 기능은 우선/중립/회피 3상태 의미를 정하고 개발해야 한다. 드롭 성향의 음수를 점수 감점으로 그대로 옮기는 것은 별도 설계 판단이다.

### U5. 배치와 무관한 변화로 F8을 다시 누르게 한다

**근거:** `Plugin.cs:806`~814에서 새 상태를 읽고 제출한 뒤 적용 가능성을 검사한다. `AutoPlacePolicy.cs`는 `IsBusy/HasPending/IsCurrent`를 먼저 검사한다. 선택지만 바뀌어도 새 계획 계산이 시작되므로 배치 지문이 같아도 거절될 수 있다.

**개선:** 배치와 추천의 최신성을 구분한다. 현재 배치 지문·계획 검증·카탈로그·실시간 검증이 유효하다면 후보 계산 중이라는 이유만으로 적용을 막을 필요가 없다. 단순히 busy 검사만 삭제하면 안 되며, 실행 가능한 배치의 조건을 별도 정책으로 정의해야 한다.

### U6. 가방이 꽉 찼을 때 수동 정리 길이 사라진다

**근거:** `Core/Planning/MoveOrder.cs`는 빈 칸으로 옮기는 모델을 사용하고, 대피 칸이 없으면 목록을 비운다. 저장소의 `docs/RESEARCH.md:180`에 기록된 게임 이동 계약과 `ApplyPlanRoutine`은 맞바꿈이다. 이번 검토에서는 게임을 새로 디컴파일하지 않았으며 이 기존 조사·어댑터 구현을 근거로 삼았다.

**개선:** 사람에게도 `A ↔ B 맞바꾸기`를 안내한다. 순환의 k개 항목은 k-1회 맞바꿈으로 해결할 수 있다. 다중 칸 아이템과 회전은 별도 제약으로 남긴다. 자동 배치를 쓰지 않는 사용자에게 특히 가치가 높다.

### U7. 설정 저장 실패가 로그에만 남는다

**근거:** `PluginPreferences.Save`는 원자적 저장을 사용하지만 실패하면 `_log`에만 한 번 기록한다. UI는 성공한 것처럼 지정이 바뀐다. 다음 실행에서 원복되면 사용자는 설정이 사라졌다고 느낀다. 손상된 설정도 기본값으로 시작하고 이후 저장에서 덮어쓸 수 있다.

**개선:** 빌드 창에 `이번 실행에만 적용됨 · 저장 실패`를 표시하고 재시도 성공 시 지운다. 손상 파일은 별도 보존 후 기본값을 사용한다. 매 클릭마다 경고 팝업을 띄울 필요는 없다.

### U8. 중첩 창의 입력과 정지 복원은 실기 확인이 필요하다

**근거:** `PlannerWindow.IsOpen`은 `_panel.IsOpened`만 본다. 빌드 창의 우클릭은 EventSystem 대신 직접 커서 사각형을 검사한다. 빌드 창 위에 설정 창을 열었을 때 아래 창의 `IsOpened`가 유지되는지는 게임 컨트롤 스택 동작에 달려 있다.

또한 `PlannerPanel`은 자신이 시간을 멈췄는지 bool로 기록하고 닫을 때 `ResetTimeScaleTo1()`을 호출한다. 연 뒤 다른 정지 소유자가 생긴 경우에도 재개해도 되는지는 확인이 필요하다.

**개선:** 가능하다면 F2/F3를 상호 배타적으로 열고, 직접 입력은 최상위 컨트롤 소유자에게만 전달한다. 게임의 중첩 일시정지 계약을 확인해 복원한다. 무조건적인 참조 카운터 추가부터 하기보다 게임의 기존 생명주기를 먼저 따라야 한다.

## 7. 솔버·추천·데이터 품질

### Q1. “계산이 일치한다”와 “좋은 선택이다”를 분리해야 한다

`QueryVerifier`·`SimulationVerifier`는 질의와 레벨 계산의 일치를 다룬다. `CharmWorth`·`StatExchange`는 그 결과에 가치를 매긴다. 전자가 통과해도 실제 딜·생존·빌드 시너지까지 최선이라는 뜻은 아니다.

기존 ROADMAP에는 아티팩트 299종 중 157종에 능력치 표가 있고 142종이 레어도 추정에 남는다고 기록돼 있다. **이 수치는 이번에 최신 게임 데이터로 다시 센 결과가 아니다.** 이번에 직접 확인한 것은 `data/values/charms.json`의 수동 보완 배열이 비어 있다는 점과 `CharmWorth.Resolve`의 추정 폴백이다.

또한 `CharmWorthSource.MeasuredFloor`는 고유 효과가 남아 있는 부분 측정이다. HUD의 추정 개수는 `Rarity`만 세므로, 부분 측정의 불확실성은 그 숫자에 드러나지 않는다. `Confidence`도 정확도 확률이 아니라 환산에 사용한 능력치 표본의 신뢰 근거 비중이다.

**개선 방향:**

1. 출처를 `능력치 환산 / 부분 반영 / 레어도 추정 / 수동 평가`로 일관되게 보여준다.
2. 격자 계산 검증 상태와 추천 가치 근거를 다른 위치에서 표시한다.
3. 수동 평가에는 게임 버전·측정 방법·평가 날짜·적용 빌드를 남긴다.
4. 자주 등장하고 추천 순위를 크게 바꾸는 미지원 효과부터 보완한다. 종수만 늘리는 것보다 영향이 큰 사례를 줄이는 편이 낫다.
5. 가까운 점수 차이에 불확실한 효과가 크면 강한 단일 순위보다 “비슷한 후보”와 차이를 설명한다. 근거 없는 확률 구간을 만들지는 않는다.

### 추천 갈래 선택의 편향

`OfferAdvisor.BestTrial`은 석판 제거 갈래에서 기존 석판 배치의 해당 자리만 제거한 `yardstick`을 사용할 수 있다. 최종 승자만 전체 배치 후보로 재평가하므로, 다른 석판 제거 갈래가 처음 제한된 후보에서 탈락하면 나중에 구제되지 않는다.

이것은 코드상 휴리스틱 한계이며 특정 추천이 틀렸다는 재현 결과는 아니다. 기존 백로그에도 같은 문제의식이 있다. 개선하려면 작은 인벤토리의 모든 제거 갈래를 동일한 탐색 조건으로 푸는 비교 기준을 만들고, 저비용 갈래 평가와 최종 선택이 얼마나 다른지 측정해야 한다.

### 우선도와 고정의 의미

- 강화 우선은 값어치 배수다. 최소 레벨 보장과 다르며, 레벨 상한도 넘기지 않는다. 이 의미는 현재 문서에 잘 설명돼 있으므로 UI에서도 유지한다.
- 제한 해제 고정은 불가능할 때 무시되고 경고하는 제약이다. “고정”의 절대성보다 `가능한 경우 우선 배치`에 가까운 예외가 있음을 보여준다.
- 콤보 진행 가치는 현재 추정 모델이다. 임계값까지 남은 개수·남은 런 길이를 반영하려면 가정과 사용 맥락을 먼저 정의해야 한다.
- 이웃 효과의 남은 목록은 ROADMAP의 “여섯”이라는 설명과 실제 나열 수가 맞지 않는다. `Behavior → 지원 여부 → 근거 → 테스트` 표 하나로 관리하면 누락과 문서 노후화를 줄일 수 있다.

### 품질 검증 체계

현재 회귀 테스트를 유지하면서 다음을 보강하는 것이 좋다.

| 검증 | 확인할 질문 |
|---|---|
| 작은 격자 완전 탐색 비교 | 근사 탐색이 놓치는 정도와 원인은 무엇인가? |
| 같은 스냅샷 반복 적용 | 점수가 개선 없이 진동하거나 이동 지시가 계속 생기지 않는가? |
| 입력 순서 변화 | 동일한 인벤토리를 다른 순서로 직렬화해도 결과가 안정적인가? |
| 후보 추가·제거 비교 | 탐색 조건 차이 때문에 증가분 부호가 뒤집히지 않는가? |
| 합성 석판 질의 대조 | 여러 줄·조건·회전 조합에서도 실제 게임 계산과 같은가? |
| 지원 효과별 대표 사례 | 해당 효과를 무시했을 때와 구별되는 배치를 실제로 고르는가? |

새 테스트는 구현 내부의 숫자를 그대로 복제하기보다 입력·게임 계약·사용자에게 보이는 결과를 검증해야 한다.

## 8. 성능·비동기 실행

### 지문 중복 계산부터 줄일 수 있다

`Plugin.FeedNativePanel`은 배치 지문을 계산한다. `PlanRunner.Submit`은 전체·배치·문맥 지문을 계산하고, `Full`은 다시 `Placement`, `Placement`는 다시 `PlanningContext`를 호출한다. 일반 제출 흐름에서 배치 3회, 문맥 4회 계산되는 구조다.

**개선:** 하나의 불변 지문 묶음을 만들고 의존 관계 순서대로 문맥→배치→전체를 한 번씩 산출한다. 설정·가치 데이터가 바뀌지 않으면 문맥 지문을 재사용한다. SHA-256 알고리즘을 바꾸기 전에 중복 직렬화·정렬·해시부터 제거한다.

기존 ROADMAP의 52.63ms 최대 지연은 이번 측정이 아니다. 그 수치만으로 현재 대부분의 지연 원인을 확정할 수 없으며 GC·첫 호출·구간 중첩 여부를 함께 봐야 한다. 동일한 스냅샷과 실행 조건으로 변경 전후를 비교해야 한다.

### 추천 OFF에서도 추천 관련 읽기와 무효화가 남는다

`GameReader.Read`는 `includeRecommendations` 매개변수를 제공하지만 `Plugin.PollGameState`와 `AutoPlace`는 기본값 true로 호출한다. 추천을 끄면 `PlanBuilder`의 후보 점수 계산은 건너뛰지만, 주변 선택지 읽기는 남는다. `PlanFingerprint.Full`도 mixer와 offers를 계속 포함한다.

따라서 “후보 점수 계산을 끔”은 구현돼 있지만 “추천과 관련된 작업 전체를 쉼”은 아니다. 추천 OFF 상태에서도 상자 변화로 계획을 무효화할 여지가 있다.

**개선:** 읽기 옵션·지문·자동 펼침 정책을 함께 정리한다. 상자 열림 감지가 배치 UI에 필요하다면 선택지 내용 조회와 상호작용 상태 감지를 나눠 유지한다. OFF 모드에서 후보 변화만으로 솔버가 다시 실행되지 않는지 검사한다.

### 실행기 종료 수명주기

`PlanRunner`는 새 요청이 이전 요청을 취소하는 기능은 있지만 외부에서 종료하는 API는 없다. F9에서 `_runner = null`이 되거나 Plugin이 파괴돼도 기존 작업의 취소를 요청하지 않는다. 기존 객체의 계산이 끝날 때까지 카탈로그·스냅샷 참조와 CPU 작업이 남을 수 있다.

무한 누수라고 단정할 근거는 없다. 대부분은 계산 종료 후 해제되겠지만, 교체 순간 중복 계산과 종료 지연은 불필요하다. `Stop/Dispose`로 실행 중 취소·pending 폐기·게시 금지를 처리하되 메인 스레드에서 완료를 오래 기다리지 않게 한다.

### 다음 측정에 필요한 지표

- 폴링 시간의 평균뿐 아니라 p95/p99, 일정 프레임 예산 초과 횟수.
- 구간별 할당량과 GC 발생, 첫 실행과 반복 실행 분리.
- 솔버 요청·완료·취소 수, 게시까지 걸린 시간, pending 교체 수.
- 동일 스냅샷에서 불필요한 재계산 횟수.
- 후보 수·석판 수·가방 포화도별 시간과 배치 품질.

`FrameCost`의 현재 누적 평균·최대값은 좋은 시작점이다. 고정 크기 버퍼나 저비용 히스토그램으로 확장하고, 계측 자체가 프레임 할당을 크게 늘리지 않도록 한다. 빔 확장 객체 풀링·병렬화는 이 측정에서 필요성이 확인된 뒤 진행한다.

## 9. 코드 품질·구조

### 큰 파일보다 변경 이유의 혼합을 줄여야 한다

`Plugin.cs`에는 폴링·키 입력·덤프·창 상태·미리보기·적용 정책·안내 문구·수명주기가 함께 있다. `NativeHud.cs`는 렌더링·레이아웃·후보 표현·툴팁 설명을 함께 다룬다. `PlacementSolver.cs`도 탐색·배정·이웃 평가·결과 생성 책임이 크다.

파일을 작게 만드는 것 자체를 목표로 삼지 말고, 실제 버그가 교차하는 경계부터 분리한다.

| 경계 | 추천 분리 단위 | 기대 효과 |
|---|---|---|
| 키 입력 ↔ 화면 표시 | 입력 소유권과 액션 라우터 | HUD OFF/중첩 창 조작 버그 검증 가능 |
| 화면 ↔ 계획 상태 | HUD 표시용 불변 모델 | 미리보기·기본 배치·일시 알림 일관성 확보 |
| 계산 ↔ 자동 배치 | 실행 가능한 배치 정책 | 추천 갱신과 F8 관문 분리 |
| 설정 편집 ↔ 저장 | 선호도 모델·저장소·저장 상태 | 가져오기/교체/복구를 게임 없이 테스트 |
| 탐색 ↔ 평가 | 후보 생성·정확 평가·선호도 비교 | 휴리스틱 개선 효과를 따로 측정 |

### 가변 모델과 전역 상태

`PlanRunState.Latest`는 공유 계획 객체이고, `GameSnapshot`, `PlanPreferences`, `Plan`에는 가변 컬렉션이 많다. 현재 호출부가 스냅샷을 새로 만들어 넘기는 구조는 유리하지만, “제출 후 변경 금지”가 타입으로 강제되지는 않는다.

모든 DTO를 즉시 불변으로 바꾸기보다 스레드 경계에 들어가는 입력과 게시 결과부터 읽기 전용 계약을 명확히 한다. `CharmValueBook.Empty`, 선호도 기본값 등 공유 기본 객체도 외부에서 바뀌지 않도록 보호한다.

Plugin의 static 캐시·적용 상태·진단 상태는 종료와 재초기화 계약을 한곳에서 정리한다. 게임 객체가 살아 있는 동안만 유효한 캐시와 순수 정의 캐시를 구분하면 씬 전환 문제를 좁히기 쉽다.

### Nullable·오류 모델·주석

- Core와 DataTool은 nullable 분석을 켰지만 Plugin은 껐다. 새로 분리하는 UI 모델·설정 모델부터 단계적으로 켜는 편이 현실적이다. Unity 객체의 파괴 후 null 판정은 일반 C# null과 같다고 가정하면 안 된다.
- `PlanRunner`는 예외의 메시지만 상태에 보관한다. 사용자가 읽을 메시지와 개발자용 원인·스택·요청 식별자를 분리하면 진단이 좋아진다.
- Core에서 사용자 문구가 바로 만들어지는 곳이 많다. 오류 코드·매개변수와 한국어 표현을 분리하면 UI 테스트·다국어·로그 검색을 함께 개선할 수 있다.
- 주석은 게임 특례와 의도를 설명하는 장점이 있지만, Plugin 클래스의 “멀티는 읽기만”이나 설정의 “게임 설정 탭”처럼 이미 바뀐 설명이 남아 있다. 기능 변경 때 관련 주석을 함께 점검한다.
- 테스트를 위해 구현 타입 전체를 public으로 여는 대신 필요한 경우 `InternalsVisibleTo`를 사용한다. 다만 이름만 private으로 바꾸는 대규모 정리는 이득이 작다.

## 10. 테스트·재현·진단 도구

### D1. 스냅샷만으로 실제 사용자의 계획을 재현하기 어렵다

**근거:** `DataTool/SnapshotReplay.cs:76`은 `PlanBuilder.Build(snapshot, catalog, null, _previous)`로 기본 선호도를 전달한다. 실제 Plugin은 강화 단계·고정·콤보 우선·프리셋·가치 데이터를 적용한다. replay의 카탈로그도 현재 로컬 활성 데이터에서 읽는다.

따라서 같은 가방이라도 별·▽·고정·프리셋을 사용하는 제보는 다른 계획으로 재생될 수 있다. 이후 게임 패치로 카탈로그가 달라져도 당시 결과와 다를 수 있다. 재생 코드에 직전 계획 앵커가 있다는 점은 좋지만 입력 문맥까지 같아야 한다.

**개선:** 로컬 재현 묶음에 스냅샷과 함께 선호도, 카탈로그 세대·해시, 플러그인 버전·커밋, 점수 모델 버전, 필요한 직전 계획 문맥을 저장한다. 필요한 카탈로그를 로컬에서 보존하는 정책도 정한다. 외부 제보용으로 내보내는 데이터 범위는 기존 배포 원칙에 맞춰 별도로 정한다.

**완료 기준:** 같은 묶음을 사용하면 강화·고정·프리셋이 있는 상태에서도 동일한 목표 배치와 점수 모델을 재현한다. 카탈로그 불일치를 조용히 대체하지 않고 명시한다.

### CLI 입력과 종료 코드

`Program.cs`에는 `--help`와 미지 옵션 거절이 없다. 예를 들어 도움말을 요청해도 기본 추출 경로로 흘러갈 수 있다. 여러 모드가 함께 들어오면 코드상 먼저 검사한 분기가 실행된다.

`SnapshotReplay.Run`은 개별 JSON 해석 실패를 출력해도 끝에서 0을 반환한다. 자동 회귀 검사에서는 실패가 성공으로 보일 수 있다.

**개선:** 도움말·서브명령·상호 배타적 모드·인자 수·경로 검증을 정의한다. 정상 분석/입력 오류/일부 실패를 종료 코드와 구조화 출력으로 구분한다. `--replay`가 폴더를 받는다는 점도 명확하게 안내한다.

### 현재 테스트의 강점과 공백

266개 통과는 의미 있지만 Plugin을 직접 참조하지 않는 테스트 구조상 키 라우팅·창 상태·설정 직렬화·UI 문맥은 보호하지 못한다. 회전과 타임아웃 테스트도 기존 가짜 포트에 없는 “늦게 반영”과 “한 번에 두 단계 관측”을 자동으로 보장하지 않는다.

권장 보강 순서:

1. A1~A3를 `ApplyPlanRoutineTests`의 정식 회귀로 이관한다.
2. 입력 소유권·HUD OFF·미리보기 상태 전이를 순수 모델로 시험한다.
3. 프리셋 교체·삭제·마이그레이션·저장 실패를 게임 없는 테스트로 옮긴다.
4. 재현 묶음으로 실제 제보 회귀를 보관한다. 게임 데이터의 저장소 포함 여부는 기존 원칙을 따른다.
5. 인게임 수동 확인표를 릴리스 바이너리·화면 조건과 함께 기록한다.

진단 덤프가 씬의 모든 세피라이트 종류·거리를 적는 부분은 `InventoryDiagnostics.cs:50`~61에서 확인된다. 숨은 정보 접근을 제한하려는 프로젝트 원칙과 맞추려면 범위 밖은 개수만 남기고 기본 제보 묶음에는 화면에 공개된 정보만 담는 방법이 있다. 이 항목은 보안 취약점 확정이 아니라 제품 원칙의 일관성 검토다.

## 11. 빌드·배포·문서

### B1. DataTool은 게임 없이 CI에서 빌드할 수 있다

`.github/workflows/ci.yml`은 Core와 Tests만 검사한다. `scripts/check.ps1`도 마지막 빌드가 Plugin뿐이다. DataTool 프로젝트는 Core만 참조하므로 게임 어셈블리 제한 없이 CI에 추가할 수 있다. 전체 솔루션을 복원하거나 포맷 검사했다고 DataTool 컴파일 성공까지 보장되지는 않는다.

**개선:** CI에 DataTool의 locked restore·Release build·도움말/잘못된 인자 smoke 검사를 추가한다. 로컬 check도 전체 솔루션 빌드 또는 DataTool 빌드를 명시한다. Plugin의 순수 로직을 Core로 옮기는 방향은 계속 유효하다.

Plugin CI를 위해 게임 DLL을 저장소에 넣는 방식은 현재 프로젝트 원칙과 맞지 않는다. 로컬 검증을 릴리스 게이트로 유지하고, 별도 빌드 환경을 검토한다면 파일 접근과 배포 제약을 먼저 정리해야 한다.

### 문서와 실제 배포 구성이 다르다

README 배포 절에는 DLL 두 개만 배포하고 BepInEx는 넣지 않는다고 적혀 있지만, `scripts/make-release.ps1`은 BepInEx를 함께 넣는다. 같은 저장소 안에서 신규 설치의 정본이 갈린다. README 후반도 BepInEx 별도 설치 절차다.

**개선:** 새 사용자 설치는 `docs/INSTALL.txt`와 실제 zip을 기준으로 하나로 맞춘다. 개발자 수동 배치는 별도 절로 옮긴다. 현재 배포 방식과 과거 설계 원칙을 섞어 적지 않는다.

추가 개선:

- 버전은 `Directory.Build.props`에서 생성 상수로 전달해 BepInPlugin과 일치시킬 수 있다. CHANGELOG 절 존재 검사는 유지한다.
- SDK 버전 고정·패키지 lock·로더 원본 해시 검사는 유지한다. 최신 버전으로 바꾸는 것 자체를 이번 검토의 해결책으로 삼지 않는다.
- 릴리스 manifest 외에 검증한 게임 빌드·싱글/호스트/참가자 범위를 릴리스 노트에 짧게 표시한다.
- 제거·업그레이드 안내는 플러그인 DLL과 공용 로더 파일을 구분해야 한다. 다른 모드와 공유하는 BepInEx 폴더를 통째로 지우는 안내는 피한다.
- 릴리스 스크립트에서 stage 재귀 삭제는 계산된 경로가 프로젝트 artifacts 안인지 검사하면 경로 변경 실수를 방어할 수 있다. 이번 검토에서 삭제 동작은 실행하지 않았다.

## 12. 추가할 만한 기능

아래 기능은 이미 있는 후보 미리보기·합성 추천·설정 창·프리셋 가져오기·강화 우선과 구별한 신규 또는 확장 제안이다. 예상 난도는 일정 약속이 아니라 상대적인 구현 범위다.

| 우선 | 기능 | 사용자 가치 | 최소 범위 | 난도·선행 조건 |
|---|---|---|---|---|
| 1 | 추천 이유와 손익 상세 | 왜 이 선택인지 판단 가능 | 획득 이득·교체 손실·콤보·우선도·추정 출처 표시 | 중; 표시 모델 분리 |
| 2 | 맞바꿈 수동 안내 | 자동 배치를 쓰지 않아도 꽉 찬 가방 정리 | 인스턴스가 구별되는 맞바꿈 순서 | 중; MoveOrder 변경 |
| 3 | 이름 있는 로컬 빌드 프로필 | 런마다 별·고정·콤보를 다시 지정할 필요 감소 | 저장·복제·전환·현재 프로필 표시 | 중; U3와 저장 버전 정리 |
| 4 | 최소 레벨 목표 `≥N` | 특정 효과 발동 조건을 직접 표현 | 아티팩트별 목표와 달성 불가 이유 | 높음; 가중치와 제약을 분리 |
| 5 | 진단 상태 창과 재현 묶음 | 제보 시 로그 경로를 일일이 찾는 부담 감소 | 검증 결과·버전·파일 위치·내보내기 | 중; D1 선행 |
| 6 | 선택 항목의 위치·회전 유지 | 사용자가 의도적으로 둔 배치를 보존 | 좌표 고정과 효과 고정을 구분 | 높음; 모순 제약 설명 필요 |
| 7 | 안전 조건이 있는 마지막 배치 복원 | 적용 결과가 취향에 안 맞을 때 회복 | 직후 상태가 일치할 때만 역계획 생성 | 높음; A1~A3 해결 뒤 |
| 8 | 로컬 런 기록 | 어떤 선택·빌드가 편했는지 돌아보기 | 종료 격자·빌드 설정·선택 기록 | 중; 보존 기간·용량 제한 |
| 9 | 컨트롤러 완결 지원 | 키보드 없이 편집·미리보기 사용 | 창 호출·탐색·증감·툴팁 대체 상세 보기 | 중~높음; 실제 입력 QA |
| 10 | UI 다국어 | 게임 언어와 일치하는 사용 경험 | UI 문구 리소스화·언어 변경 반영 | 중~높음; 오류 코드 분리 |
| 11 | 추천 목록 상세 보기 | 상위 6개 밖 후보도 비교 | 열린 창 안에서 전체 후보 페이지 | 중; HUD 무입력 원칙 유지 |

당장 우선하지 않을 것:

- **탐색 시간을 늘리는 고급 모드:** 기존 측정에서 폭 확대의 효과가 제한적이었다. 휴리스틱 정확성과 다양성을 먼저 검증한다.
- **게임 중 외부 위키 자동 가져오기:** 기존 보류 사유인 이름 대응·외부 구조 의존·데이터 취급 검토를 해결해야 한다. 로컬 프로필의 가치가 더 명확하다.
- **클라우드 동기화·계정·커뮤니티 서버:** 현재 로컬 도구의 범위를 크게 넓힌다. 로컬 프로필·기록·내보내기 수요부터 확인한다.
- **근거가 없는 DPS·승률 예측:** 현재 점수는 전투 시뮬레이션 결과가 아니다. 제품 신뢰를 해칠 수 있다.

## 13. 권장 실행 순서와 완료 기준

### 1단계: 적용 결과를 신뢰할 수 있게 만들기

- A1~A3의 정식 회귀 테스트와 완료·실패·미확정 상태 정의.
- 이동 전 인스턴스 대조, 마지막 위치·회전 대조, 안전한 되돌리기 범위.
- 첫 서버 대기부터 진행 표시, 실패 원인과 중간 상태 구분.
- 실제 참가자 세션에서 회전·지연·실패 복구 확인.

**통과 기준:** 목표가 다르면 완료로 표시하지 않는다. 타임아웃 후 남을 수 있는 쓰기를 확정 실패로 취급하지 않는다. 외부 변경된 아이템에 검증 없이 추가 쓰기를 보내지 않는다.

### 2단계: 조작과 화면 문맥을 정리하기

- 미리보기 고정 표제와 적용 대상 일관성.
- HUD OFF에서도 빌드 편집 기능 동일 동작.
- 프리셋 교체·삭제의 범위 명시, 미지원 음수 카테고리 안내.
- 저장 실패 상태, 입력 최상위 창·일시정지 복원 검사.
- 맞바꿈 기반 수동 순서 및 배치 최신성 분리.

**통과 기준:** 사용자에게 현재 상태·제안 배치·후보 가정을 구별하게 할 수 있다. 표시 옵션이 편집 기능을 바꾸지 않는다. 실제 인게임 조건표를 채운다.

### 3단계: 변경을 안정적으로 검증하기

- DataTool CI 추가, CLI 인자·종료 코드 정리.
- 스냅샷·설정·카탈로그 문맥을 갖춘 재현 묶음.
- 지문 한 번 계산, 추천 OFF 읽기와 무효화 정리, 실행기 종료 API.
- README 설치·배포 설명과 실제 zip 일치.

**통과 기준:** 같은 재현 묶음으로 같은 계획을 검증할 수 있다. DataTool 컴파일 실패가 CI에서 검출된다. 고정 입력의 재계산 횟수와 할당·시간을 전후 비교한다.

### 4단계: 추천 품질과 기능 확장

- 고유 효과 중 추천 결과에 영향이 큰 항목부터 측정·지원.
- 석판 제거 갈래를 비교 기준으로 평가.
- 추천 이유 상세와 로컬 프로필.
- 최소 레벨·컨트롤러·다국어는 사용자 수요 순으로 진행.

**통과 기준:** 지원 종수뿐 아니라 대표 판에서의 선택·배치가 개선됐다는 근거를 남긴다. 기능별 성능·게임 호환·UI 회귀를 함께 확인한다.
