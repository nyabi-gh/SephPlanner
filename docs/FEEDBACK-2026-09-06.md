# F2 콤보 배치·친타마니 +3 피드백 분석

검토일: 2026-09-06  
대상 커밋: `6bdd7ed5e9bfc55aad72561c42dedce5818b64d8` (`0.2.1`)  
범위: 프로젝트 구조, 두 피드백의 데이터 흐름, 설치된 게임 어셈블리 대조, 최소 재현, 기존 테스트·빌드.

후속 수정: 같은 날 사용자 요청으로 친타마니 칸 보너스 읽기와 종이 옆 열쇠의 행 카테고리 계산을 수정했다. 아래 분석·최소 재현 수치는 수정 전 상태다. F2 콤보 지정과 배치 계산의 연결은 이번 수정 범위에 포함하지 않았다.

## 판단

| 항목 | 결론 | 확인 수준 |
|---|---|---|
| F2로 지정한 콤보에 맞춰 열쇠·종이 배치 | 구현 가능. 현재 콤보 우선순위는 후보 추천에만 전달된다. | 코드 추적·Core 최소 재현 |
| 친타마니 발동 후 칸에 +3이 남으면 자동 배치가 막힘 | `dungeonTempLevels` 누락으로 계산과 게임 레벨이 어긋나는 경로가 있다. | 게임 코드 대조·Core 최소 재현 |
| 열쇠 옆 종이가 콤보를 잘못 셈 | 종이가 이웃의 고정 카테고리만 읽어 열쇠의 행 카테고리를 놓친다. | 게임 코드 대조·Core 최소 재현 |

제보 원문의 “장애”가 자동 배치 잠금인지, 게임 멈춤·충돌인지는 아직 확인되지 않았다. 이 보고서는 실제로 발견한 자동 배치 잠금 원인을 설명하며 게임 충돌까지 재현했다고 주장하지 않는다. “종이템”은 로컬 카탈로그의 하얀 종이로 해석했다.

## 프로젝트 구조와 두 문제의 위치

`GameReader`가 게임 상태를 스냅샷으로 옮기고, `PlanBuilder`가 카탈로그·사용자 설정과 합쳐 `PlacementProblem`을 만든다. `TabletSimulator`가 칸 효과를 계산하고 `PlacementSolver`가 석판 배치 탐색과 아티팩트 배정·교환 개선을 수행한다. `OfferAdvisor`와 `TabletMixAdvisor`는 아이템 획득·석판 합성 가상 상태에서 같은 계산 기반을 사용한다.

플러그인은 계산 결과를 HUD에 표시하고, F8 적용 전에 현재 상태·계산 검증·멀티 설정 등을 확인한다. 적용은 `PlanApplier` 및 Core의 적용 루틴을 거쳐 게임의 이동·회전 경로로 수행한다. Core는 게임 참조 없이 테스트할 수 있고 DataTool은 저장된 스냅샷을 재생한다.

두 피드백 때문에 구조를 전면 교체할 필요는 없다. 첫 문제는 **사용자 의도가 배치 목적함수에 도달하지 않는 문제**, 둘째는 **런타임 칸 효과가 입력 모델에 도달하지 않는 문제**다. 기존 독립 계산·검증 구조를 유지하면서 연결 지점을 보강할 수 있다.

## 1. F2 콤보 지정으로 열쇠·종이 배치

### 현재 동작

- `PluginPreferences.ToPlanPreferences()`는 선택한 콤보를 `PriorityCategories`로 전달한다.
- `PlanBuilder.cs:189`는 이를 `OfferAdvisor.Rank`에 넘긴다. 후보 추천은 우선 콤보 일치와 진행에 가점을 준다.
- 반면 `PlacementProblem`에는 우선 콤보 필드가 없다. `PlanBuilder.cs:95` 부근에서는 콤보 정의와 현재 개수만 배치 문제에 전달한다.
- `PositionalWorth.cs:70`의 `ComboWorth`는 열쇠·종이·침이 만드는 콤보를 평가하지만, 사용자가 F2에서 무엇을 선택했는지는 모른다.
- 따라서 “자리별 콤보 계산 미지원”은 아니다. 지정과 무관하게 일반 콤보 가치가 높은 자리를 찾는 기능은 이미 있다. `PositionalWorthTests`와 `WhitePaperTests`가 그 일부를 검사한다.

최소 재현에서 콤보 임계값을 모두 4로 둔 열쇠 하나를 첫 행에 배치했다. F2 설정에 해당하는 `GLACIER` 우선순위를 넣기 전·후 모두 목표 `(0,0)`, 점수 `1.43`으로 같았다. 추천은 끄고 배치에 미치는 영향만 분리했다. 숫자는 테스트용 데이터 결과이며 실전 효율 측정값이 아니다.

### 실제 게임 규칙

설치본 `Charm_3Elemental_ByRow`는 행 번호를 `lineCategory.Length`로 나눈 나머지로 콤보를 고른다. 클래스 초기값만 보면 세 종류지만 **로컬 카탈로그의 실제 열쇠 프리팹은 네 종류**다.

| 위에서부터 행 | 로컬 카탈로그의 콤보 ID |
|---|---|
| 1, 5, … | `STURDY` |
| 2, 6, … | `EMBER` |
| 3, 7, … | `GLACIER` |
| 4, 8, … | `MAGITECH` |

구현할 때 이 표를 하드코딩하지 않고 현재처럼 덤프된 `LineCategories`를 사용해야 한다. 열쇠가 제공하지 않는 카테고리로 바꾸는 것은 배치로 할 수 없다.

하얀 종이는 좌우 아티팩트의 `GetItemCategory()` 결과에서 공통 카테고리를 물려받는다. 원하는 카테고리의 이웃 둘과 세 칸을 확보해야 하므로 열쇠보다 탐색 조건이 복잡하다.

### 추가로 확인한 종이 오류

`ComboCounting.cs:49`는 좌우 이웃의 `Definition.Categories`를 교집합으로 취한다. 게임은 현재 위치·상태가 반영된 `GetItemCategory()`를 읽는다.

로컬 열쇠의 고정 `Categories`는 비어 있다. 따라서 세 번째 행에 `빙하 열쇠 | 하얀 종이 | 빙하 아티팩트`를 놓으면 게임 규칙상 종이가 `GLACIER`를 얻지만 현재 Core는 빈 목록을 돌려준다. 이 경우를 최소 재현에서도 확인했다.

단순 가중치 추가 전에 이 계산 차이를 함께 고쳐야 한다. 열쇠의 행 카테고리뿐 아니라 침·다른 종이처럼 카테고리를 동적으로 물려받는 이웃은 게임의 계산 순서와 순환 관계를 따져야 한다. 단순한 재귀나 고정 카테고리 대체로 전체 일치를 보장할 수 없다.

### 구현 제안

1. `PlacementProblem`에 우선 콤보를 전달하고 후보·합성용 문제 복제에도 보존한다. `PlanFingerprint`는 이미 F2 우선순위를 포함한다.
2. 동적 카테고리 계산을 정비한 뒤, 배치 채점에서 우선 콤보를 반영한다. 현재 배치·탐색 배치·최종 채점·후보 미리보기가 같은 기준을 써야 한다.
3. 기본 F2 선택은 “선호”로 해석할 수 있다. 다만 사용자가 “반드시 그 콤보로”를 기대한다면 별도의 제약 또는 다른 가치보다 먼저 비교하는 우선순위가 필요하다. 추천의 기존 3배를 그대로 곱해도 다른 콤보 임계값 완성에 밀릴 수 있고, 모든 임계값을 넘은 콤보의 기존 진행 가치는 0이므로 단순 곱셈만으로 요구를 충족하지 못한다.
4. 종이는 좌우 둘과 함께 배치를 만드는 후보를 탐색해야 한다. 현재 반복 배정과 `Polish`의 한 번 교환 개선으로 찾을 수 있는 경우는 있지만, 중간 이동이 손해인 여러 물건의 재배치를 보장하지 않는다. 필요한 세 칸과 이웃 쌍을 구성하는 제한된 탐색을 추가하고 비용을 측정하는 편이 타당하다.
5. `BuildWindow.CollectCombos()`는 현재 개수가 양수인 콤보와 기존 지정만 노출한다. 열쇠만 가진 상태에서 아직 0개인 다른 행 콤보를 새로 지정하는 흐름도 보강해야 한다.

선호와 강제의 차이, 여러 우선 콤보의 충돌, 상한을 이미 채운 콤보, 불가능한 배치의 안내를 명시해야 한다. 기존 아티팩트 ★ 가중치는 아이템 전체 가치를 키우므로 특정 콤보 선택을 대신하지 못한다.

## 2. 친타마니 +3 이후 자동 배치 잠금

### 게임에서 일어나는 일

설치본의 `Charm_Chintamani.Avatar_OnDamagedServerside`를 확인했다. 발동 시 회복·무적 처리 뒤 인벤토리 쓰기 권한 범위에서 자기 좌표에 `AddDungeonTempLevel(..., addLevel)`을 호출하고 아이템을 제거한다. 클래스의 `addLevel` 초기값은 3이다.

`GridInventory.AddDungeonTempLevel`은 해당 좌표의 `levelMatrix`와 `dungeonTempLevels`에 값을 더한다. `dungeonTempLevels`는 `SyncDictionary<ItemPosition, int>`이며 동기화 객체로 등록돼 있다. 즉 친타마니 아이템이 사라져도 원래 칸에 남는 효과이고, 인챈트처럼 옮긴 아이템을 따라가는 효과가 아니다.

`ReleasePermission`은 기존 레벨에 인챈트·각인·석판을 반영한 뒤 칸 배수를 적용한다. 따라서 이 보너스를 기존 `FixedEffectCell.Level`에 합치면 Core의 배수 계산 순서와 연결할 수 있다. 보너스 수명은 게임 딕셔너리의 현재 값을 따라야 한다. 이번 조사에서는 `ClearDungeonTempLevels` 구현은 확인했지만 호출 시점까지 확정하지 않았으므로 “다음 층에서 풀린다”는 안내는 하지 않는다.

### 프로젝트에서 빠진 지점

`GameReader.ReadFixedEffects` (`GameReader.cs:233`)는 호스트에서 `fixedEngravingsOnServer`만 읽고 참가자에서는 신비 콤보를 복원한다. 어느 쪽도 `dungeonTempLevels`를 읽지 않는다. 특히 참가자 경로는 신비 콤보가 없으면 즉시 빈 목록을 반환한다.

스냅샷은 게임 `levelMatrix`의 +3은 읽지만, 그 +3의 원인을 기록하지 않는다. Core는 아는 석판·각인·인챈트만 계산하므로 레벨이 어긋난다.

이 차이는 두 검증 경로에 걸린다.

- `SimulationVerifier`는 같은 `ReadFixedEffects`를 사용하므로 실시간 칸 레벨 검증에 실패한다.
- `PlanBuilder.Verify`도 실패하며, `PlanBuilder.cs:206`에서 자동 배치 목표를 비운다. 자동 배치 정책은 검증 실패를 거부한다.

즉 “친타마니 +3 뒤 F8이 막힌다”는 증상은 입력 누락과 보호 동작으로 설명된다. 검증을 끄는 방식은 원인을 해결하지 못하며 잘못된 목표 레벨을 적용할 수 있다.

### 최소 재현 결과

2칸 격자에서 첫 칸에 일반 아티팩트 하나, 두 번째 빈 칸에 친타마니가 남긴 게임 레벨 +3이 있다고 가정했다. 운영 코드는 변경하지 않고 합성 스냅샷만 비교했다.

| 입력 | 검증 | 불일치 칸 | 자동 배치 목표 |
|---|---|---|---|
| 게임 레벨 +3만 기록 | `Failed` | 1 | 0개 |
| 같은 좌표에 `FixedEffects.Level=3`도 공급 | `Passed` | 0 | 아티팩트를 +3 칸으로 배치 |

빈 칸에 남은 효과만으로도 문제가 발생한다. 다른 아이템을 그 칸에 넣어야만 발생하는 것은 아니다. 이것은 Core 재현이며 실제 제보자의 게임을 조작해 재현한 결과는 아니다.

### 수정 방향과 사용자 안내

`ReadFixedEffects`에서 서버·참가자 모두 `dungeonTempLevels`를 좌표별 고정 레벨에 합산하도록 만드는 것이 가장 작은 근본 수정이다. 기존 신비 효과와 합치되 참가자 분기의 조기 반환이 새 보너스를 버리지 않게 해야 한다. 기존 `FixedEffects`는 스냅샷 저장·계획 입력·지문·실시간 검증·후보 및 합성 문제에 이미 연결돼 있어 재사용할 수 있다.

필요한 회귀 검사는 빈 칸 +3, 그 칸의 아이템 교체·이동, 신비 효과와 중첩, 인챈트·배수 중첩, 누적 보너스, 게임이 보너스를 제거한 이후, 싱글·멀티 호스트·참가자다. 특히 Core 테스트만으로 Unity/Mirror 읽기 경로가 맞다는 보장은 할 수 없어 플러그인 빌드와 인게임 확인이 필요하다.

F9는 카탈로그를 다시 만드는 기능이므로 이 런타임 입력 누락의 해결책이 아니다. 분석 단계에서 확실한 사용자 안내는 “친타마니가 남기는 칸 보너스 누락을 수정해야 한다”이다. 제보 시점의 F10 `inventory-snapshot.json`, `inventory-dump.txt`, `BepInEx/LogOutput.log`와 화면 문구·싱글/멀티 여부가 있으면 발견한 경로와 실제 증상을 대조할 수 있다.

이번 작업은 분석과 재현이다. 운영 소스·게임 설치 파일을 수정하거나 배포하지 않았다. 이전 전체 검토 문서의 이슈를 현재도 미해결이라고 재인용하지 않았으며, 이번에 추적한 동작과 검증 결과만 결론에 사용했다.

권장 구현 순서는 **친타마니 입력 누락 수정 → 종이의 동적 카테고리 계산 수정 → F2 콤보 선호 전달 및 종이 배치 탐색 보강**이다. 첫 항목은 기능 사용을 막는 오류이고, 나머지는 사용자 의도대로 배치하는 품질에 직접 영향을 준다.

## 후속 수정 결과

- `ReadFixedEffects`는 호스트·참가자 각인 읽기를 마친 뒤 동기화된 `dungeonTempLevels`를 고정 칸 효과 목록에 더한다. 참가자에게 신비 콤보가 없거나 신비 규칙을 못 읽어도 친타마니 보너스는 남는다. 같은 칸의 각인·누적 보너스는 시뮬레이터가 합산하고 그 뒤 배수를 적용한다.
- 종이의 좌우 교집합은 열쇠의 현재 행 카테고리를 사용한다. 열쇠의 고정 카테고리를 잘못 물려주지 않고 같은 카테고리를 중복해서 세지 않는다. 종이끼리의 전파나 임의의 동적 아티팩트 전반을 새로 모델링한 것은 아니다.
- 회귀 테스트 10개를 추가했다. 좌우 열쇠·행 순환·행 변경·자기 기여 중복 계산, 소비 후 빈 칸 보너스·배치 후 안정성·아이템 이동·각인 및 인챈트·배수와 중첩·보너스 제거를 검사한다.
- 전체 테스트 312개 통과, 플러그인을 포함한 Release 빌드 성공. 테스트의 멀티 스냅샷은 Core 검증이며 Unity/Mirror가 실행되는 인게임 호스트·참가자 검증을 대신하지 않는다. 게임 폴더 배포는 하지 않았다.
