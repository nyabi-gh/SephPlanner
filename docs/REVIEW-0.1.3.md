## 1. 태그 전에 고칠 것 (P0)

### 1.1 안내문이 전부 잘린다 — 0.1.3 이 고쳤다고 적은 것을 포함해서

`RenderNotice`(`NativeHud.cs:433`)가 메시지를 `_nextMove` 에 넣는다. `_nextMove` 는 `Line()`
(`:425`)으로 만든 것이고, `Line` 은 `Widgets.Label` 이라 **`NoWrap` + `Ellipsis` + 1.4배 고정
높이**다(`Widgets.cs:78-79`). 그리고 같은 함수가 `SetCompact(true)`(`:452`)로 판을
`_compactWidth = min(_width, S(18))`(`:280`)까지 좁힌다.

계산하면 쓸 수 있는 안쪽 폭은 `18 - 2×(edge+pad)` ≈ 기준단위 16.7 이고 글자는 0.95배다.
**한글 17자쯤에서 잘린다.** 실제로 그 길을 타는 문구들:

| 문구 | 길이 | 결과 |
|---|---|---|
| `데이터 생성 실패 - F9 로 다시 시도하세요(BepInEx 로그에 이유가 있습니다).` | ~40자 | 절반 못 미쳐 잘림 |
| `가방의 물건 중 아는 아티팩트가 없습니다. F9 로 데이터를 다시 만들어 보세요.` | ~38자 | 잘림 |
| `가방에 아티팩트가 없습니다. 하나 주우면 배치를 계산합니다.` | ~30자 | 잘림 |
| `계산 실패 - ` + 예외 메시지 | 가변 | 이유가 통째로 잘림 |
| `탐험 중이 아닙니다.` / `데이터 준비 중` / `계산 중` | 짧음 | 보인다 |

첫 줄이 문제의 핵심이다. **0.1.3 은 "덤프 실패가 화면에 닿지 않는다"를 P0 로 고쳤는데,
고친 결과가 화면에서 잘려 나온다.** 사용자가 보는 것은 `데이터 생성 실패 - F9 로 다시 시…`
정도이고, 정작 "로그에 이유가 있다"는 부분이 없어진다. ROADMAP 이 "화면에서만 답이 나온다"고
꼽은 넷 중 하나가 이것이다 — 게임을 켜 보면 바로 드러날 자리다.

같은 종류의 결함을 `f614246` 이 `_notice`(한 줄 → `Paragraph`)와 `_hint`(접힌 폭으로 측정)에
대해 이미 고쳤다. `RenderNotice` 경로의 `_nextMove` 만 남았다.

**고치는 법.** `RenderNotice` 가 `_nextMove` 대신 `_notice`(이미 `Paragraph`)를 쓰거나,
그 자리에서 `Widgets.FitHeight(_nextMove, ..., _compactInner)` 를 걸 수 있는 문단 위젯을 하나
더 둔다. 색이 `Text` 여야 하는 것과 `Amber` 여야 하는 것이 갈리므로 전자보다 후자가 깔끔하다.

### 1.2 참가자 회전이 인스턴스가 아니라 좌표를 누른다

`Press`(`:604-615`)가 `inventory.DoClickAction(new ItemPosition(tablet.xIdx, tablet.yIdx))` 를
부른다. `xIdx`/`yIdx` 는 `StoneTablet` 의 평범한 필드고(`RESEARCH.md:91`), 우리가 걸음마다
기다리는 것은 `inventoryMatrix` 쪽이다(`Swapped:408`, `InstanceAt:413`). **둘이 같은 순간에
도착한다는 보장이 코드 어디에도 없다.**

어긋나면 우리는 **다른 칸을 우클릭한다.** RESEARCH 는 "그 칸에 아티팩트가 있으면 아무것도 하지
않는다"까지만 확인했다(`:216-217`). 아티팩트도 석판도 아닌 것(소모품 등)에 대해 `DoClickAction`
이 무엇을 하는지는 조사에 없다 — 우클릭은 이 게임에서 "쓰기"의 손짓이기도 하다.

게다가 이 실수는 **우리 쪽에서 조용하다.** 우리 석판의 `rotation` 은 안 바뀌므로 3초 뒤
"반영되지 않아 중단"으로 빠지고, `RestoreRotations` 는 `PressesBack(0) == 0` 이라 아무것도
누르지 않는다. 엉뚱한 칸에 한 일은 되돌려지지 않고 기록도 남지 않는다.

**고치는 법.** 누르기 직전에 `InstanceAt(inventory, new GridPos(tablet.xIdx, tablet.yIdx)) ==
tablet.instanceID` 를 확인하고 아니면 중단한다(세 줄). 더 나은 쪽은 `FindTablet`(`:650`)이 이미
`stoneTablets` 를 훑고 있으므로 **거기서 좌표를 사전의 열쇠로 함께 들고 나오는 것**이다 —
그러면 애초에 필드를 믿지 않게 된다.

### 1.3 회전 되돌리기가 조용히 포기한다

`RestoreRotations`(`:581-601`)의 실패 출구 둘이 맨 `yield break` 다 — 석판이 사라진 경우
(`:588`)와 `Press` 가 실패한 경우(`:591`). 반영 대기가 시간을 넘긴 경우는 확인조차 하지 않고
다음 걸음으로 간다(`:593-598`).

부르는 쪽(`:573-576`)은 앞으로 가던 길의 실패만 `outcome.Failure` 에 담으므로, 사용자가 보는
결과는 `… 회전이 시간 안에 반영되지 않아 자동 배치를 중단합니다. 원래 배치로 되돌렸습니다.`
가 된다. **석판 하나가 엉뚱한 각도로 남아 있어도 그렇게 적힌다.**

0.1.3 이 `Rollback`(`:427-458`)에 정확히 이 처치를 했다 — 되돌아갔는지 확인하고 못 했으면
`outcome.Note` 에 그렇게 적는다. 회전 쪽만 빠졌다. 같은 모양으로 맞춘다.

### 1.4 코루틴 본문의 예외가 아무 데도 닿지 않는다

`Prepare`(`:144`)는 통째로 `try/catch` 고, `Swap`(`:391`)·`Press`(`:604`)·`Collect`(`:621`)는
예외를 메시지로 바꿔 돌려준다 — "코루틴 안에서는 잡을 수 없다"는 이유가 주석에 있다. 그런데
**감싸지 않은 것들이 남아 있고, 전부 `inventory` 를 만진다:**

- `Swapped`/`InstanceAt`(`:408`, `:413`) — 걸음마다 대기 루프 안에서 매 프레임
- `Rollback`(`:427`) — `inventory` 가 살아 있는지 확인하지 않는다
- `LevelDrift`(`:200`) — `inventory.levelMatrix` 를 정착 대기 루프에서 매 프레임
- `FindTablet`(`:650`) — `Collect` 안이라 감싸져 있다(문제 없음)

호스트에서는 이 전부가 한 프레임 안이라 일어날 수 없다. **참가자 세션에서는 그 사이가 수 초다.**
그 사이에 인벤토리가 파괴되면(죽음, 층 이동, 접속 끊김) `MissingReferenceException` 이 나고,
`finally` 가 `InProgress` 만 되돌린 채 예외는 코루틴 밖으로 나간다. `AutoPlace` 의 `try/catch`
는 `StartCoroutine` 이 돌아온 지 오래라 못 잡고, `Guarded` 도 마찬가지다. 그래서:

- 우리 로그에 아무것도 안 남는다(유니티의 `Player.log` 에만)
- `report` 가 안 불려서 **화면에도 아무것도 안 뜬다**
- 이미 옮긴 걸음이 **되돌려지지 않는다** — 솔버가 평가한 적 없는 반쯤 배치가 남는다

이것은 정확히 `LEGAL.md` 가 "선례가 된 커뮤니티 모드가 망가뜨린 곳"이라고 적은 상태이고,
우리가 붙이는 값이 "확인과 되돌리기"라고 적은 자리다.

**고치는 법.** 두 루프 본문을 `Swap` 과 같은 모양으로 감싸고, `Rollback` 과 정착 루프에
`inventory == null` 확인을 둔다. `Apply` 의 `finally` 에서 "예외로 끝났으면" 한 줄을 보고하도록
`Outcome` 에 자리를 하나 더 두는 것도 방법이다.

## 2. 참가자 경로의 사용 경험 (P1)

### 2.1 적용 중이라는 표시가 없고, 멈출 길도 없다

`Report()` 는 `Apply` 가 **끝난 뒤에만** 불린다(`AutoPlaceFinished`, `Plugin.cs:783`).
참가자 세션에서는 걸음마다 `SyncTimeout = 3f` 를 기다리고, 되돌리기도 이미 실행한 걸음마다
3초를 더 쓴다. 열두 걸음짜리 계획이 중간에 막히면 **화면이 아무 말도 하지 않는 채로 인벤토리가
수십 초 동안 저 혼자 움직인다.**

같은 동안 안내 줄은 `F8 자동 배치` 를 계속 광고한다 — `Guide()`(`Plugin.cs:696`)가 부르는
`AutoPlaceAvailability` 는 `PlanApplier.InProgress` 를 모른다. 눌러야 비로소
"자동 배치가 아직 진행 중입니다."가 뜬다. **진행 중이라는 사실을 아는 유일한 방법이 다시 눌러
보는 것이다.**

고칠 자리 셋:

1. `PlanApplier` 가 `Progress` 문자열(`"자동 배치 중 3/12"`)을 들고, `Hint()` 가
   `_autoPlaceResult` 보다 먼저 그것을 본다.
2. `AutoPlaceContext` 에 `Applying` 을 두고 `AutoPlacePolicy` 가 거절한다 — 그러면 안내 줄에서
   키가 사라지고, 정책 판정이 한 곳에 남는다.
3. 전체 마감 시한을 둔다. 지금 최악은 걸음 수 × 3초 × 2(앞 + 되돌리기)이고 상한이 없다.

### 2.2 참가자 적용 중에도 솔버가 계속 다시 돈다

`Update`(`Plugin.cs:88-91`)는 적용 중인지 모른다. `PollGameState` → `FeedNativePanel` →
`_runner.Submit` 이 `PollIntervalSeconds`(기본 0.25초)마다 그대로 돈다. 반쯤 적용된 스냅샷은
매번 지문이 다르므로 `Submit` 은 **돌고 있던 빔 서치를 취소하고 새로 시작한다**
(`PlanRunner.cs:130-138`). ROADMAP 의 실측으로 한 번이 최대 1초·1.4GB 다.

즉 참가자가 F8 을 누르면, 서버 왕복을 기다리는 그 몇 초 동안 **초당 네 번씩 취소된 빔 서치가
돈다.** 유니티 Mono 의 GC 는 마킹 동안 모든 스레드를 세우므로 이것이 그대로 프레임 압력이고,
하필 네트워크 왕복이 늦어지는 상황과 겹친다.

`PlanApplier.InProgress` 면 `Submit` 을 건너뛴다(한 줄). 적용이 끝나면 `AutoPlaceFinished` 가
이미 `_nextPoll = 0` 으로 즉시 다시 읽게 해 둔다.

### 2.3 `InProgress` 가 참으로 굳으면 되돌릴 길이 없다

`InProgress`(`:36`)는 반복자의 `finally`(`:113-116`)로만 꺼진다. 유니티는 코루틴을 소유한
게임오브젝트가 **비활성화될 때 반복자를 Dispose 하지 않는다.** 그 경우 `InProgress` 가 참으로
남고, F8 은 그 세션 내내 "자동 배치가 아직 진행 중입니다. 잠시 뒤 다시 누르세요." 만 돌려준다 —
기다리라고 말하는데 기다려도 끝나지 않는다.

BepInEx 플러그인 객체가 비활성화되는 일은 흔하지 않으니 확률은 낮다. 다만 값이 싸다:
시작 시각을 함께 들고, 상한(예: 걸음 수 × 6초 + 5초)을 넘으면 `InProgress` 를 푼다. 두 줄이다.

### 2.4 `FrameKey` 에 `MultiplayerAutoPlace` 가 없다

`Render`(`NativeHud.cs:503-508`)가 `frame.MultiplayerAutoPlace` 로 멀티 경고 문구를 고르는데,
`FrameKey`(`:113-146`)에는 그 필드가 없다. `Warning()` 이 보는 다른 입력은 전부 열쇠에 있다 —
`_queryVerified`, `_recommendations`, `_verification`, `_reason`. 이것만 빠졌다.

지금은 다음 폴링(≤0.25초)에 새 스냅샷 객체가 오면서 저절로 맞춰지므로 눈에 띄지 않는다.

## 3. 약속과 실제가 어긋나는 곳 (P2)

### 3.1 미배치 석판이 "옮길 것이 없습니다"로 나온다

`PlanBuilder.cs:199-202` 가 `hasPlacementChanges` 를 계산한 뒤 `UnplacedTablets > 0` 이거나

각인이 걸린 참가자 세션도 그 길로 간다.

남는 것은 `UnplacedTablets > 0` 하나다. 이때 화면 경고는 "석판 N개는 놓을 자리가 없어
계산에서 빠졌습니다"라고 하는데 F8 은 "옮길 것이 없습니다"라고 해서 **같은 화면이 서로
딴소리를 한다.**

(`hasPlacementChanges` 가 거짓이 되어 같은 분기로 떨어진다). 필요한 것은 정책이 목표 개수
앞에서 `plan.Best.UnplacedTablets` 를 한 번 보는 것이다.

### 3.2 ★★★ 이 README 가 약속한 만큼 세지 않다

`PlacementSolver.Value:543` 은 `charm.Weight * charm.Worth.At(effective)` 다. 배수는 **값어치에
곱해진다.** 그런데 지금 값어치의 상당수가 레어도 어림값이다 — `data/values/charms.json` 은
`{"charms": []}` 로 **비어 있고**, 능력치가 없는 142종은 전부 어림값 위에 서 있다(ROADMAP
"반쯤 닫힌 것").

그래서 어림값이 낮은 아티팩트에 ★★★ 를 걸어도, 제대로 측정된 아티팩트를 못 이길 수 있다.
README 는 이렇게 적는다:

> 10배는 다른 것을 희생해서라도 최우선이다.

앞 문단에 "세기는 값어치 차이를 어디까지 밀어낼 수 있는지로 뜻이 정해진다"는 단서가 있긴 하나,
저 문장은 단정으로 읽힌다. **"값어치가 잘 재어진 것들 사이에서"** 라는 조건을 한 마디 붙이거나,
쪽지가 이미 "레어도로 어림잡은 것"이라고 말하는 자리에서 지정 배수의 한계도 함께 말한다.

곁들여, `WastePenalty`(`:544`)는 `Weight` 가 곱해지지 않는다. 이것은 "상한 위로는 못 올린다"는
설명과 **맞는** 동작이다(상한에 닿은 뒤 배수가 하는 일은 버티는 것뿐). 다만 그 결과 상한에 닿은
★★★ 아티팩트가 어느 칸을 고를지는 가중되지 않은 `1e-4` 항이 정하게 되므로, 의도라는 것을
한 줄 주석으로 못 박아 두는 편이 좋다.

## 4. 테스트가 못 보는 곳

이번에 들어온 것 중 **가장 위험한 코드가 가장 시험되지 않았다.**

| 새 코드 | 어디 | 테스트 |
|---|---|---|
| 걸음마다의 반영 대기, 저널, 되돌리기 검증 | `PlanApplier`(Plugin) | 없음 |
| 회전 누르기 순서와 실패 시 되감기 | `PlanApplier`(Plugin) | 없음 |
| 레벨 정착 대기와 사후 대조 | `PlanApplier`(Plugin) | 없음 |
| 회전 걸음 수 산술 | `TabletRotation`(Core) | 3개 |
| 강화 우선 단계별 배수 | `PlanPreferences`/솔버(Core) | 5개 |
| 세션 종류 판정 | `AutoPlacePolicy`(Core) | 갱신됨 |

`TabletRotation` 을 Core 로 뺀 판단은 옳았다 — 드리프트가 실제로 다른 도구를 무너뜨린 자리다.
다만 **드리프트는 산술이 아니라 순서에서도 난다**: 몇 번 눌렀는지 세다가 중간에 실패했을 때
`pressed` 에 담기는 값, 되감기가 실제로 한 바퀴를 채우는지, 밀려난 쪽까지 기다리는 판정
(`Swapped`)이 절반 도착 상태를 완료로 읽지 않는지 — 이것들이 사고가 나는 자리인데 전부
플러그인 안에 있다.

**할 만한 것.** 적용기에서 게임 타입을 걷어낸다. `Step`/`Turn` 의 시퀀서를

```
interface IGridWriter
{
    int  InstanceAt(GridPos cell);
    bool Swap(GridPos from, GridPos to);
    int  RotationOf(int instanceId);
    bool Press(int instanceId);
}
```

같은 얇은 인터페이스 뒤로 밀면, 코루틴 골격은 그대로 두고 **순서·저널·되돌리기·시간 초과가
전부 Core 에서 가짜 격자로 시험된다.** ROADMAP §4 "플러그인 로직을 Core 로" 의 항목 중
지금 가치가 가장 큰 자리이고, CI 사각지대도 그만큼 좁아진다.
