# F10 비공개 진단 수집

2026-09-10 설계 및 구현 작업 문서다. 수집처는 사용자 소유의 `sephplanner.nyabi.me`, 운영 환경은 Debian 13과 Docker다. VPS Caddy에서 HTTPS를 종료하고 WireGuard로 홈서버 `10.77.0.2:8081`의 컨테이너 8080에 연결한다. 현재 배포된 0.2.7에는 전송 기능이 없다.

배포 파일과 적용·검증 절차는 [배포 인계 문서](../deploy/diagnostics/README.md)에 있다. 실제 DNS·VPS·홈서버 설정은 이 구현 작업에서 변경하지 않았다.

## 목적

제보자가 로그를 찾아 직접 첨부하지 않아도, 문제가 생긴 순간 F10으로 진단을 남기고 제보 번호를 전달할 수 있게 한다. 계산 결과를 재현하는 데 필요한 입력과 설정을 함께 보존한다. 보석 갑옷 제보처럼 이전 진단에 해당 아이템이 없어 원인을 확인하지 못하는 상황을 줄인다.

## 사용자 동작

- F10의 로컬 진단 저장 기능을 유지한다. 첫 전송 전에 수신 도메인과 전송 항목을 알리고 동의를 받는다.
- 동의한 뒤에는 F10으로 생성한 이번 진단만 백그라운드로 전송한다. 과거에 모인 진단을 일괄 전송하지 않는다.
- 성공하면 제보 번호를 게임 화면과 로컬 기록에 남긴다. 실패하면 실패 사실과 로컬 보관 위치를 알린다.
- 전송 여부는 F3에서 변경할 수 있다. 수신처나 전송 항목이 바뀌면 기존 동의를 재사용하지 않는다.
- 전송 중 다시 F10을 누르더라도 진행 중인 자료를 덮어쓰거나 무제한 작업을 만들지 않는다.
- 전송 시작 간격을 게임 실행 세션당 최소 1분으로 제한한다. 전송 실패·취소도 시도에 포함하며, 동의를 껐다 켜도 간격을 초기화하지 않는다. 제한 중 F10은 로컬에만 저장하고 남은 시간을 알리며 나중에 자동으로 보내지 않는다. 이 간격은 초기 운영 정책값이다. 게임 시간·시스템 시계 변경의 영향을 받지 않는 경과 시간을 사용한다.

## 수집 범위

| 자료 | 목적 |
|---|---|
| 버전·빌드 식별자·게임 버전·수집 시각 | 같은 버전 이름의 다른 빌드도 구분 |
| 현재 인벤토리 진단과 스냅샷 | F10 순간의 배치와 게임 관측값 확인 |
| 현재 빌드 지정·후보 추천 설정 | 끄기 허용·사용 유지·강화 선호와 추천 조건 확인 |
| 마지막 게시 계획의 `.replay` | 당시 카탈로그·입력·직전 목표·기대 결과로 계산 재현 |
| SephPlanner의 최근 로그 | 읽기·계산·자동 적용·저장 오류 확인 |

전체 게임 폴더, 세이브, 게임 DLL, 다른 모드의 설정, GitHub 또는 관리자 자격 증명은 수집하지 않는다. 로그는 SephPlanner가 기록한 내용만 제한된 크기로 보존하며 전송용 복사본에서 사용자 경로 등 식별 정보를 가린다. 원본 로컬 로그는 변경하지 않는다.

`.replay`는 현재 스냅샷과 다른 시점일 수 있다. 게시된 계획이 없거나 이번 스냅샷 저장이 실패한 경우에는 그 사실을 기록하고 이전 파일로 대체하지 않는다. 재현 입력을 임의로 바꾸어 지문 검증을 무력화하지 않는다.

`.replay`에는 게임에서 수집한 카탈로그가 들어 있으므로 이번 사용자 요청에 따라 비공개 수집처에서 진단에만 사용한다. 공개 GitHub Issues·릴리즈·소스 저장소에는 올리지 않는다. 공개 제보에는 제보 번호와 증상만 연결한다.

## 서버와 전송

- 플러그인은 HTTPS로 진단만 제출한다. 조회·목록·삭제용 관리자 자격 증명은 플러그인에 넣지 않는다.
- 서버는 업로드를 받는 경로와 관리자 조회 경로를 구분한다. 파일은 웹 루트 밖의 영속 볼륨에 보관한다.
- 클라이언트의 파일명·크기·확장자를 신뢰하지 않는다. 허용한 항목과 압축 해제 후 크기까지 검사하고, 업로드 파일을 실행하거나 임의 경로에 풀지 않는다.
- 요청 크기·동시 처리·수집 빈도·전체 저장량에 상한을 둔다. 비밀이 아닌 클라이언트 식별값만으로 정상 사용자임을 보증하지 않는다.
- 동일한 제보를 다시 보내더라도 중복 저장하지 않도록 제보 식별자와 내용 해시를 확인한다. 서버가 실제 저장을 마친 뒤 접수 성공을 반환한다.
- 통신은 취소·시간 제한을 적용한다. 게임의 메인 스레드에서 네트워크 응답을 기다리지 않는다.
- Docker 배포 설정과 관리자 조회 방법을 함께 제공한다. 보관 기간과 용량 제한을 명시하고 관리자가 변경할 수 있게 한다.

## 검증 기준

1. 미동의·전송 해제 상태에서는 HTTP 요청이 발생하지 않는다.
2. 스냅샷·재현 저장 일부 실패와 게시 계획 부재를 구분하며 과거 파일이 섞이지 않는다.
3. 개인정보 가림 처리 뒤에도 계산 입력과 재현 결과가 보존된다.
4. 성공·통신 실패·시간 초과·게임 종료·중복 요청에서 로컬 기록과 화면 상태가 일치한다.
5. 관리자 인증 없이 진단 목록·원문을 읽을 수 없다.
6. 허용하지 않은 파일·경로 이동·중복 ZIP 항목·손상 자료·용량 초과를 서버가 거부한다.
7. 로컬 HTTP 통합 검사와 전체 `scripts/check.ps1`을 통과한다. 실제 서버와 Unity에서의 검증은 따로 기록한다.

## 현재 검증 결과 (2026-09-10)

- `scripts/check.ps1`: 전체 547개 테스트, 포맷, 진단 도구와 플러그인 빌드 통과. 빌드 경고·오류 없음.
- 진단 관련 신규 33개 테스트: 미동의·주소 변경·HTTP 차단, 취소, 응답 검증, 부분 수집 실패, ZIP 제한, 실제 HTTP 저장·관리자 인증·중복·용량·만료·신뢰 프록시, 가림 후 재현 결과 보존, 연속·동시 전송 시도 제한 확인.
- `scripts/package-diagnostics.ps1`로 만든 서버를 Windows에서 직접 실행하고 `/health` 및 `--healthcheck` 성공 확인. 패키지 항목을 확인해 게임 자료와 관리자 토큰이 포함되지 않음을 확인.
- 운영자가 서버 배포 후 `https://sephplanner.nyabi.me/health`에서 HTTP 200과 `ok` 응답을 확인했다. 실제 업로드·재부팅 복구·Unity의 동의 화면과 전송은 별도 검증이 필요하다. 이 작업에서 서버 설정이나 공개 릴리즈를 변경하지 않았다.

## 첫 진단 창의 본문 겹침 수정

실기에서 본문이 창 밖으로 넘치고 버튼과 겹치는 문제가 확인됐다. `PlannerWindow.Build`는 부모를 비활성화한 채 글자를 만들고, 진단 창은 이 상태에서 `GetPreferredValues`로 본문 높이를 고정했다. 게임에 설치된 `Unity.TextMeshPro.dll`을 확인하니 `TMP_Text.m_isOrthographic`의 초기값은 false이고, `TextMeshProUGUI.Awake`에서 true로 바뀐다. 높이 계산은 이 값에 따라 글꼴 배율을 0.1 또는 1로 적용하므로 첫 측정과 표시의 기준이 달랐다.

공통 `Widgets.Label`에서 `isOrthographic = true`를 설정해 초기화 전 측정도 UI 표시와 같은 배율을 사용하게 했다. 창 높이를 임의로 늘리거나 지연을 넣지 않는다. 게임에서 창을 처음 열 때와 다시 열 때, F3에서 전송 동의를 여는 경우 모두 본문 아래에 버튼이 배치되는지 확인해야 한다. .NET 테스트는 Unity의 실제 렌더링 검증을 대체하지 않는다.

실기 로그에서 진단 3건의 접수 성공은 확인했다. 수정한 창의 실제 표시 검증은 게임 재시작 후 진행한다.
