# 인계

직전 세션이 무엇을 했고 다음에 무엇을 할지. **[현재 상태](STATUS.md)가 정본이고 이 문서는 그날의 길잡이다.**
둘이 어긋나면 STATUS 를 믿는다. 세션마다 이 파일을 통째로 덮어쓴다 - 날짜별로 쌓지 않고, 제보별 조사 경위도
여기 남기지 않는다(결론은 해당 문서에, 경위는 커밋 메시지에).

## 2026-10-04 - 제보 6건, 성능과 모델 수정

**0.4.22 를 열었다(미공개, 릴리스 미작성).** 2026-10-04 제보 6건(0.4.21, 게임 1.0.33)과 사용자가 전해 준 제보 하나를
처리했다. 커밋마다 `check.ps1` 을 돌렸고, 결과를 바꾸지 않는 수정은 보관 제보 42건의 `--reproduce
--allow-model-change` 출력이 고치기 전과 같은 것으로 증명했다.

**성능** ("꽉 찬 가방에서 10초 넘게", `698b2f07`. 인게임 41칸 판에서 배치 1.5~2.5초, 조언 3~5초)

- `DataTool --bench` - 성능 전후는 이것으로 잰다([성능과 응답성](PERFORMANCE.md) "재는 법").
- 콤보 우선 채점이 결과 객체를 짓던 것: 후보 조언 할당 2,520 → 856 MB.
- 인게임 카탈로그 짓기가 데이터베이스 준비 신호를 안 기다리던 것: 타이틀에서 527회 / 5.4초.
- 빔 확장 실체화: 빔 400 한 번 83 → 12 MB. 시간은 그대로이고 그 7할은 `Estimate` 의 탐욕 배정이다.
- `[perf]` 에 배치 cold/warm/채점만과 "가방 빔 재탐색" 의 까닭(처음·구성·석판·각도·칸·고정)을 넣었다.

**모델** (결과가 바뀐다)

- 자리 의존 콤보(열쇠·종이·침)는 배치에서 단계를 채울 때만 값을 친다 - 견고가 다 찬 판에서 열쇠가 빙하 줄로
  가던 `b4826648`. 보관 제보 여섯이 달라져 종료 코드 기준이 0 스물아홉 / 2 열셋이 됐다.
- 꺼진 열쇠·종이·침도 콤보에 든다(디컴파일로 셋 다 확인).
- 치명타 100% 상한(처형이 있으면 200%), 게임에서 바탕을 읽는다 - `27f25bbc`. 규칙은 RESEARCH "치명타는 100% 에서
  끊긴다", 한계는 PLACEMENT-OBJECTIVE.
- 목표 레벨 `콤보만` 단계 - 효과를 버리고 콤보 수만 채워 감점 칸을 먼저 채운다(단안경 제보).

**손대지 않은 요청.** F1 펼친 화면에서 선호도 바로 바꾸기(`23eeb37e`), 고사양 모드(`698b2f07`). 마법서 0레벨은 이미
있는 목표 레벨 0 으로 되고 제보자도 나중에 그렇게 썼다.

검증: `scripts/check.ps1` 902개 통과, 경고 0. 마지막 커밋까지 `origin/main` 에 푸시했다.

**같은 날 둘째 세션.** `v0.4.22` 태그(`6cbac33`)를 달고 Windows ZIP 으로 **드래프트**를 만들었다(Mac ZIP 없음, 미공개).
실기는 아직 못 했다. 그 뒤 `Estimate` 배정의 상수를 줄였다 - 결과는 42건 재현 출력이 같고, cold 배치가 3~12% 줄었다
(PERFORMANCE 4번). 사용자가 태그를 `c8ff32b` 로 옮겨 드래프트 ZIP 을 바꿨다. 이어서 배정 행렬과 카테고리 문자열의
할당을 걷어냈다(PERFORMANCE 1b, 후보 6개 warm 조언 537 → 202MB). 태그를 다시 `bfece2c` 로 옮겨 드래프트 ZIP 에 들어 있다.
이어서 셋을 더 했다. 폴링의 지문 비용은 Unity Mono 로 재 보니 이미 작아 ROADMAP 만 고쳤고,
`FrameCost`·`GameBinding` 을 테스트 프로젝트로 링크하고 `ItemIdentity` 시험을 넣었고(검토 6-1·6-3), 제거·인챈트 조언의
문턱을 점수 눈금으로 바꿨다(검토 3-3, 42건 재현 불변). 마지막 것은 0.4.22 CHANGELOG 의 Fixed 에
넣었다. 태그를 `d2775b4` 로 옮겨 드래프트 ZIP·본문을 갱신했다.

**0.4.22 에 더한 것.** 셋을 더 했다. 업데이트가 반쯤 걸리면 알린다 - 되돌리기 실패를 `UpdateRollbackException` 으로
올리고, 시작할 때 플러그인과 Core 의 판을 대조해 다르면 다시 설치하라고 띄운다(`40ce8be`, 0.4.22 CHANGELOG 에 넣고
옛 Core 와 섞여도 돌도록 대조를 옛 API 로만 했다). `CompareTo` 단계 순서와 허용 오차를 `PlacementQualityTests` 로 고정했다(검토 3-4·3-6). `check.ps1` 이 판
대조와 경고 0 을 강제하고 `make-release.ps1` 이 그것을 부르며, `--replay` 가 실패를 종료 코드로 낸다(검토 6-4).

## 다음 세션

0. **실기.** STATUS 표 맨 위 다섯 줄(0.4.22)을 게임에서 본다. 특히 치명타 바탕은 게임 값을 처음 읽는 경로다.
   확인한 줄은 지운다.
1. **0.4.22 릴리스.** 드래프트가 있다. 실기 뒤 사용자가 공개를 정한다. 태그 뒤의 커밋을 넣을지(태그를 옮기면
   ZIP 을 다시 올린다)도 그때 정한다. Mac 에서 같은 스크립트로 ZIP 을 더한 뒤 `publish-release.ps1`.
2. **cold 빈도.** 0.4.22 제보의 `[perf]` 에서 "각도" 가 "구성" 보다 크면 빔 열쇠에서 각도를 빼는 일을 사용자와
   정한다 - 추천이 바뀔 수 있는 설계 변경이고 `--churn` 확인이 필요하다.
3. **빔 시간.** `Estimate` 상수는 줄였다. 남은 것은 확장 수·묶음 수라 추천이 바뀐다 - 2번과 함께 정한다.
4. **남은 할당.** 배정 행렬과 카테고리 문자열은 끝났다. 남은 것은 `Describe`·`OccupancyFrom`·`Clone`(PERFORMANCE 1b·3번).
5. **요청 둘**(F1 선호도, 고사양 모드)은 사용자 결정을 기다린다. 고사양 모드는 2~4번 뒤에 본다.
6. 그 밖은 [백로그](ROADMAP.md) - 멈춤 제보 계측, 플러그인 파일 테스트 링크(검토 6-1·6-3), 화면(5-2~5-5),
   운영(7-4~7-6).

**문서를 새로 만들기 전에** STATUS 의 문서 지도에 들어갈 자리가 있는지 먼저 본다. 날짜가 붙은 보고서 파일은
만들지 않는다.
