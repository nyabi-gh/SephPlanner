# 인계

직전 세션이 무엇을 했고 다음에 무엇을 할지. **[현재 상태](STATUS.md)가 정본이고 이 문서는 그날의
길잡이다.** 둘이 어긋나면 STATUS 를 믿는다. 세션마다 이 파일을 덮어쓴다 - 날짜별로 쌓지 않는다.

## 2026-09-14

되돌릴 수 없는 선택의 조언에 **한 칸 앞보기**를 넣었다. 전날 [미래를 보는 자리](notes/LOOKAHEAD-2026-09-14.md)
가 일감으로만 적어 둔 권장 1번이고, 그 문서의 뒷절에 무엇을 확인하고 무엇을 접었는지가 있다.

### 무엇이 어디에

| 무엇 | 어디 |
|---|---|
| 늘어난 판을 세우고 나눠 주는 자리 | `Core/Solver/Lookahead.cs` - 계획마다 하나, 조언 셋이 공유한다 |
| 다음 칸이 열린 격자 | `Core/Tablets/GridSpec.cs` 의 `Grown`·`OpeningStep` |
| 줄 세우기 | 세 조언의 `RankedGain`(`SoonGain ?? Gain`). 버리기는 늘어난 판에서 이득이 없으면 목록에서 뺀다 |
| 화면 | `Explain.SoonTag`·`SoonLine`, `NativeHud` 의 후보·합성 줄과 빼기 쪽지 |
| 재현 자료 | `ReplayResult` 에 `…/다음 칸` 을 **지금 값과 다를 때만** 더한다 |
| 시험 | `tests/LookaheadTests.cs` 4개, `GridSpecTests` 3개, `SolverCostTests.LookingAheadCostsOneMoreLayoutSearch` |

### 정한 것과 그 이유

- **한 칸만 본다.** 게임이 여는 단위를 디컴파일로 봤고, 확정된 것은 레벨업의 `AddStorage(1)`
  하나다. 다른 출처의 양은 프리팹에 있어 코드로 안 나온다. 몇 칸이 더 열릴지는 짐작하지 않으므로
  **새로 정한 상수가 없다.**
- **먼저 재고 넣었다.** 제보 열둘을 지금 칸 수와 +1 로 풀어, 셋에서 답이 달라지는 것을 보고 시작했다.
- **버리기는 문서보다 넓게 걸렀다.** "잠긴 칸으로 뻗는 석판"만이 아니라 **칸 하나에 이득이
  사라지는 것 전부**를 뺀다. 공짜로 얻을 것을 아이템 하나를 치르고 사는 일이라 같은 판단이다.
- **합성 짐작은 늘어난 판에서만 한다.** 두 판을 다 재면 합성 조언이 두 배가 된다(재어 봤다).

### 곁에서 고친 것

`OfferAdvisor.Clone` 이 `PlacementProblem.Scale` 을 복사하지 않아 **가상 배치만 기본 눈금으로
채점되고 있었다.** 카탈로그가 잰 눈금은 콤보 2.1768(기본 2.59)·비교 눈금 0.0319(기본 0.05)다.
배치와 화면 점수는 원래 판을 쓰므로 영향이 없었고 조언의 증가분과 순위만 어긋났다. 제보
`4c1efa35`·`8a7728df` 의 재현 차이는 대부분 이 수정 몫이다.

## 2026-09-13 (셋째 세션)

게임 안 업데이트를 넣었다. 게임을 켜면 새 안정판이 있는지 보고, 있으면 창으로 묻고, 누르면 받아
DLL 둘을 바꾸고, 다시 시작하라고 안내한다. 사용자가 정한 흐름 그대로다.

### 무엇이 어디에

| 무엇 | 어디 |
|---|---|
| 최신 태그 읽기와 zip 받기 | `Core/Runtime/UpdateClient.cs` - `releases/latest` 의 302 `Location` 으로 버전을 안다. API 도 JSON 도 안 쓴다 |
| zip 검증과 교체 | `Core/Runtime/UpdatePackage.cs` - `manifest.json` 의 SHA-256 으로 DLL 둘을 대조하고, `.old` 로 밀어 두고 새 파일을 놓는다. 실패하면 되돌린다 |
| 창 | `Plugin/Ui/UpdateWindow.cs` - 묻기·받는 중·완료·실패 네 단계를 창 하나가 돈다 |
| 배선 | `Plugin.cs` 의 `StartUpdateCheck`·`StartUpdateInstall`·`CheckUpdateProgress`·`FinishPreviousUpdate` |
| 설정 | `[Updates] CheckOnStart`, F3 의 "시작할 때 업데이트 확인" |
| 테스트 | `tests/UpdateTests.cs` 18개. 실제 0.3.9 zip 으로 `Extract` 가 통하는 것도 손으로 확인했다 |

### 정한 것과 그 이유

- **로드된 DLL 은 이름을 바꿀 수 있다.** 사용자가 게임을 켠 채 `Rename-Item SephPlanner.Core.dll
  SephPlanner.Core.old` 를 돌려 통과했다. 그래서 패처 DLL 을 더 넣지 않고 플러그인 안에서 끝낸다.
- **옛 파일은 `.dll.old` 가 아니라 `.old` 다.** 확장자 석 자 패턴이 더 긴 확장자에도 맞는 윈도우
  규칙 때문에 `*.dll` 이 `.dll.old` 를 잡을 여지를 남기지 않는다.
- **확인은 동의 창 없이 한다.** GitHub 에 가는 것은 "최신 판이 무엇이냐" 하나이고 받는 것은 창에서
  따로 묻는다. README·설치안내에 적었고 F3 에서 끌 수 있다. 진단 전송의 "동의 없이는 요청 없음"
  원칙은 진단에만 남는다.
- **확인 실패는 조용하다.** 오프라인이면 로그 한 줄이고 화면에는 아무것도 안 뜬다.
- **`releases/latest` 는 프리릴리스를 빼 준다.** 그래서 시험판 사용자(0.3.9)에게 0.3.8 을 권하지
  않는다 - 지금보다 높을 때만 창이 뜬다.

## 다음 일감

**0. 앞보기를 실기에서 본다.** 기록된 제보 열둘에 상점·상자를 연 것이 하나도 없어 **후보 추천
경로가 실제 판으로 확인되지 않았다.** 상점을 열고 아래·오른쪽으로 뻗는 석판이 있는 판에서
`다음 칸 +N` 이 붙는지, 그리고 `[perf]` 로 조언 시간이 개발 PC 의 +8~27% 와 폭이 맞는지를 본다.

**1. 업데이트는 실기에서 한 바퀴 봤다.** 0.3.7 로 내려 깔고 켜니 창이 떴고 0.3.8 을 받아 바꿨으며
재시작에 0.3.8 이 올라왔다. 남은 것은 `.old` 뒷정리와 "업데이트됐습니다" 알림뿐이고, 시험 뒤
배치해 둔 개발 빌드가 다음 실행에서 그것을 한다. STATUS 의 "게임 안 업데이트".

**2. 0.3.9 실기 확인은 그대로 남아 있다.** 침의 강화 대상, 모래시계 지정, 상점 사파이어 보충 칸.
STATUS 의 "아직 배포하지 않은 것". **Publish 는 사용자 몫이다.**

**3. 0.4.0 은 Publish 됐고(2026-09-13) 지금 Latest 다.** 자동 업데이트를 가진 첫 판이라 0.3.9 이하
사용자는 이번 한 번은 손으로 올린다. **0.4.1 이 드래프트로 올라가 있다** - 컷·태그·zip 까지
2026-09-14 세션에서 했고 **Publish 는 사용자 몫이다.** 0.4.0 사용자부터는 게임 안에서 받는다.

**4. 성능 - [성능과 응답성](PERFORMANCE.md).** 다음 걸음은 고치는 것이 아니라 재는 것이다.

## 알아 둘 것

**CI 가 `v0.3.9` 태그에서 빨간 것은 정상이다.** `.editorconfig` 의 LF 수정(`f42f07b`)이 0.3.9 컷
뒤에 들어가서 그 태그의 트리는 여전히 포맷 검사에 걸린다. `main` 은 초록이다.

**옛 태그가 로컬과 원격에서 갈라져 있다.** `git fetch --tags` 의 "would clobber existing tag" 는
정상이며 **`--force` 로 맞추지 않는다** - 릴리스 자산이 원격의 그 태그에 붙어 있다.

**`AGENTS.md` 가 커밋 트레일러를 금지한다.** 커밋 전에 메시지에서 그 줄들을 지운다.

**사용자용은 둘이다.** 대문 `README.md` 는 설치하고 첫 30분까지고, 빌드 지정·배치 판정 규칙·제보
절차처럼 쓰던 사람이 찾아오는 것은 [자세한 사용법](USAGE.md)에 둔다. **기능이 늘 때 붙일 자리는
대문이 아니라 USAGE 다** - 대문이 다시 불어난 것이 이 분리의 이유였다. 개발 쪽은
[개발 문서](DEVELOPMENT.md)다.
