# 인계

직전 세션이 무엇을 했고 다음에 무엇을 할지. **[현재 상태](STATUS.md)가 정본이고 이 문서는 그날의 길잡이다.**
둘이 어긋나면 STATUS 를 믿는다. 세션마다 이 파일을 통째로 덮어쓴다 - 날짜별로 쌓지 않고, 제보별 조사 경위도
여기 남기지 않는다(결론은 해당 문서에, 경위는 커밋 메시지에).

## 2026-11-15 - 돌파의 나침반 배치 (Windows)

제보 `eebed530`(0.6.3 창작마당, 게임 1.1.3): "돌파의 나침반이 우선 지정을 따르지 않고 쿠나이 같은 곳에 박힌다". 런이 끝난
로비에서 보낸 제보라 가방이 비고 `plan.replay` 도 없어 그 판은 못 봤다. 원인은 코드에서 찾고 같은 모양의 시험 판으로 재현했다.

- **원인 둘.** 돌파에 분배처럼 "가장 값진 뿌리의 몫 × 제 레어도 어림값(전설 1.45)"을 줘서, 아래에 침이 없어도 값진 쿠나이
  밑으로 끌려갔다. 또 침이 이미 지정 대상 바로 밑에 있으면 돌파가 그 사이로 들어가는 수가 없었다(한 개 이동·지원 짝 이동은
  중간 배치가 늘 나빠진다).
- **고친 것.** 침은 돌파가 없을 때의 몫만 갖고, 돌파가 풀어 주는 덤은 돌파가 갖는다(`Compass.Lifted`, `LiftWorth`). 합은
  게임과 같다. 다듬기에 돌파를 침과 그 위 칸 사이에 끼우고 침과 그 아래 사슬을 한 칸 내리는 수(`PolishLiftInsertions`)를 더했다.
  `PolishSupportPairs` 의 시도·채점 부분은 `SupportWork` 로 떼어 둘이 같이 쓴다. 분배는 그대로 어림이다.
- **검증.** `CompassTests` 셋: 침 없는 돌파는 0, 몫 나누기의 합, 지정 전설 대상 + 더 값진 쿠나이 판에서 대상 → 돌파 → 침.
  셋 다 옛 코드에서 실패하고, 끼워 넣기 수를 빼면 마지막 시험이 실패한다. `check.ps1` 통과(1,061개, 경고 0, 1.1.x 설치본만 -
  Core 만 바뀌었다). 보관 리플레이 52건은 옛 빌드와 출력·종료 코드가 모두 같다. 다만 돌파가 가방에 든 판이 하나도 없어(a8f6f9e1
  은 북향의 침만) 이 대조는 "돌파가 없는 판은 그대로" 까지만 말한다. 속도는 재지 않았다 - 두 경로 다 돌파가 있을 때만 돈다.
