# 인계

직전 세션이 무엇을 했고 다음에 무엇을 할지. **[현재 상태](STATUS.md)가 정본이고 이 문서는 그날의 길잡이다.**
둘이 어긋나면 STATUS 를 믿는다. 세션마다 이 파일을 통째로 덮어쓴다 - 날짜별로 쌓지 않고, 제보별 조사 경위도
여기 남기지 않는다(결론은 해당 문서에, 경위는 커밋 메시지에).

## 2026-11-03 - 0.6.0 마무리와 드래프트 (Windows, 1.1.1)

0.6.0 을 열고(사용자 결정) 아래를 `main` 에 넣었다. 커밋마다 `check.ps1` 을 돌렸다(마지막 1022개, 경고 0).

- **설정 창 정리**(`9ee0ea4`): 일반 설정 소제목(화면·추천·계산·진단·업데이트·세부 조정), 고른 탭 밑줄, 값 칸 폭,
  바로 실행 버튼 옆 키. BepInEx 판 한국어는 실기로 봤다.
- **창작마당 판 진단 전송**(`9f5d85c`): TEAM HORAY 가 2026-11-02 허용(LEGAL "진단 전송 문의"). 진단 코드는 두 판이 함께
  쓰는 자리로, 업데이트만 `BepInExHost/` 에 남았다. 창작마당 판은 동의를 가져오지 않고 다시 묻는다(사용자 결정). 공존 시
  창작마당 판 보류, 창작마당 판 단독 전송을 실기로 봤다.
- **BepInEx 마지막 판은 짓지 않고 안내만 한다**(사용자 결정, ROADMAP). CHANGELOG·창작마당 설명글에 DLL 둘을 지우라고 적었다.
- **같은 번호의 석판 둘**(`266a17e`, `4949c94`): 자동 제보 `4dd465fb`·`5be39302`. 해골이 새 판을 시작하면 저주가 같은
  `instanceID` 로 둘 들어와 우리가 하나만 읽었다(STATUS "원인을 모르는 채", RESEARCH `NewItemOwnInstance`). 서브 에이전트
  검토가 첫 수정의 구멍 셋(회전 단계, 조언의 시험 번호 충돌, 석판 수)을 잡아 둘째 커밋으로 막았다.
- **릴리스**: 태그 `v0.6.0` 은 `4949c94`. 드래프트에 Windows zip(같은 커밋)과 본문이 있다. 태그는 사용자 허락으로 두 번
  강제로 옮겼다.

## 다음 세션

1. **드래프트의 macOS zip 을 다시 만든다**(지금 것은 `3389be3`). Mac 에서 태그를 다시 받고 `make-release.ps1` 후
   `gh release upload ... --clobber`. 두 zip 의 manifest 커밋이 `4949c94` 인지 본다.
2. **창작마당 등록**(사용자, 게임 안 "창작마당에 올리기")과 썸네일·설명글 검토. 등록 뒤에 공개(`publish-release.ps1`).
3. **STATUS 표 맨 위 다섯 줄의 실기.** 특히 저주 둘(해골로 새 판), BepInEx 판 회귀.
4. **CI 의 가끔 실패하는 테스트 둘**(STATUS "원인을 모르는 채"). 사용자가 이번에는 미뤘다.
5. README·INSTALL·USAGE 를 창작마당 기준으로(BepInEx 판에서 넘어오는 안내 포함).
6. 직전 인계에서 남은 것: 조건 칸이 낡은 석판(ROADMAP), HUD 불투명도 → Auto 언어 구독 → 첫 검증 안내.

**문서를 새로 만들기 전에** STATUS 의 문서 지도에 들어갈 자리가 있는지 먼저 본다. 날짜가 붙은 보고서 파일은
만들지 않는다.
