# 인계

직전 세션이 무엇을 했고 다음에 무엇을 할지. **[현재 상태](STATUS.md)가 정본이고 이 문서는 그날의 길잡이다.**
둘이 어긋나면 STATUS 를 믿는다. 세션마다 이 파일을 통째로 덮어쓴다 - 날짜별로 쌓지 않고, 제보별 조사 경위도
여기 남기지 않는다(결론은 해당 문서에, 경위는 커밋 메시지에).

## 2026-11-19 - 재현 대조와 1.0.33 (Windows)

Mac 의 전체 검증에서 넘어온 Windows 일을 했다.

- **재현 대조.** `reports/` 의 `plan.replay` 는 47개가 아니라 53개다. 돌파 수정 전(`bc45bf7`), 합치기 수정 전(`bca6c52`),
  `main` 을 `--reproduce --allow-model-change` 로 돌렸다. "계산 코드 차이" 줄을 빼면 세 빌드의 출력이 모두 같고, 다른 것은 수정 전
  빌드가 형식 27 자료 `a8f6f9e1`(0.6.1)을 거절한 것 하나다. 그 자료는 이제 재생되지만 저장 결과와 6곳이 다르다 - 돌파 수정 전
  코드에 형식 27 수정만 얹어도 같게 나와 0.6.1 이후 계산이 바뀐 몫이다. 종료 코드는 0 스물 / 2 서른셋(측정 덤프 없음).
- **돌파 수정은 보관 자료로 못 쟀다.** 강화 대상을 지정한 자료가 다섯이고 그 카탈로그에 돌파의 나침반이 없다. 제보 `eeb4f2ad`
  원본은 Windows 에 없다. 확인은 Mac 의 시험과 게임 실기뿐이다.
- **1.0.33.** `UI_GameOverLabel` 이 있고 게임 오버 경로가 1.1.4 와 같다. 플러그인이 1.0.33 어셈블리로 경고 0 으로 빌드된다.
  런 중 가방 읽기가 매번 실패한다는 추정은 틀렸다. 지원을 내릴지는 사용자가 정한다 - 0.6.6 에서는 남기고 다음 판에서 내리며 0.6.6 에
  예고하자고 제안했고 답은 아직이다.
- **고친 것: 긴 토큰이 진단을 막던 정규식.** `LobbyCodes` 의 뒷문구 갈래가 토큰 안의 시작 위치마다 끝까지 다시 훑었다. .NET 에서
  8192자 약 0.5초, 32768자 7.4초로 제곱이다. 토큰 첫 글자에서만 시작하고 되짚지 않게 했다(32768자 1ms). 이 PC 에서는 게임 문장
  상한(8192자)으로 1초 제한에 안 닿아 시험은 `RedactGame` 에 32768자를 넣는다 - 고치기 전에는 시간 초과로 실패했다. Mono 속도는 안 쟀다.
