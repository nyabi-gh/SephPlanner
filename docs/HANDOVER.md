# 인계

직전 세션이 무엇을 했고 다음에 무엇을 할지. **[현재 상태](STATUS.md)가 정본이고 이 문서는 그날의
길잡이다.** 둘이 어긋나면 STATUS 를 믿는다. 세션마다 이 파일을 덮어쓴다 - 날짜별로 쌓지 않는다.

### `40f5874c` 0.4.18 호스트 자동 제보 "고정 효과 원본과 게임 행렬에서 되뺀 값이 다릅니다" - 고침(0.4.19)

계획 재현은 일치한다(269.45 → 269.45). 게시된 계획의 가방은 6×6·34칸, F10 순간은 6×8·48칸으로 그 사이
23초에 넓어졌다. 어긋난 칸은 빈칸 `(0,6)`·`(0,7)` 둘(계산 2 / 게임 0)이고, 0열의 정의 석판 둘
(`VERTICAL +1`)이 새 칸에 줄 몫이다. 게임 `levelMatrix` 에는 새 칸의 열쇠가 아예 없었다.

디컴파일로 본 것: 행렬의 열쇠는 지우는 곳이 없으므로 열쇠가 없다는 것은 게임이 그 석판을 48칸으로 한 번도
다시 적용하지 않았다는 뜻이다. 칸 수를 바꾸는 길은 `LocalAddStorage` 하나이고 `Permission` 으로 감싸여
끝에 전체 재계산이 돈다. **그런데도 왜 재적용을 건너뛰었는지는 밝히지 못했다** - 따라가 본 중첩 경로는 전부
재적용해야 했다. 넓어진 출처(레벨 업·상태·패시브)도 자료에 없다.

수정(`9367808`): 석판·각인마다 게임 자신의 `StoneTablet.ParseQuery`(지금 격자)와 적용해 둔 `EffectRange` 를
견준다. 다르면 게임이 아직 다시 계산하지 않은 것이라 고정 효과 층은 막지 않고 기다리며(추적기에도 안 먹인다),
계획 검증은 `Unavailable` 로 "아이템을 하나 옮기면 게임이 다시 계산합니다" 를 띄운다. 자동 제보는 나가지
않는다. 우리 파서가 아니라 게임 파서라서 우리 해석 오류를 이 상태로 숨기지 않는다. 덤프 `[고정 효과]` 절에
되뺀 값과 옛 격자로 적용된 석판을 적는다 - 이번에는 그것이 없어 스크래치 프로그램으로 칸을 되짚었다.
남은 것: 적용 여부(`IsApplied`)만 낡은 경우는 다루지 않는다. `QueryVerifier` 는 칸 수 42까지만 대조한다.
