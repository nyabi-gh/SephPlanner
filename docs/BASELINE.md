# 기준 버전과 이식 범위

0.3.3은 0.3.2의 다음 판이 아니다. 2026-09-10에 사용자가 `v0.2.8`(`3c1846f`)을 기준으로 되돌리기로
결정했고, 거기에 필요한 수정만 골라 이식한 것이 지금의 `main`이다. 0.3.0~0.3.2의 DPS 기준 추천과
전투 조건 설정은 의도적으로 포함하지 않는다. 이 문서가 그 결정과 이식 범위의 기록이다.

되돌린 트리는 `93cec54`이고 `e451a1e`는 0.3.2의 커밋 계보만 잇는 병합이다. 작업 브랜치
`codex/0.2.8-patches`는 `main`에 들어갔다. 되돌리기 전 작업 공간의 0.3.2 및 미커밋 사용성 개편은
그대로 보존했다.

## 방향

0.2.8의 강화 우선·양보와 콤보 추천 기준, F2 두 탭과 점수 표시를 기준으로 한다.
이 점수는 실제 DPS가 아니며 기존 능력치 환산과 추정값이다. 알려진 효과 누락까지 해결됐다는
뜻은 아니다. 이후 기능은 필요한 문제를 재현하고 작은 패치로 하나씩 검증한 뒤 가져온다.

## 첫 패치

- 합작 창을 열거나 닫을 때 새 계획이 없어도 HUD 추천 목록을 갱신한다.
  `3c5069f`의 화면 갱신 수정과 회귀 테스트를 가져왔다. DPS 표시 변경은 가져오지 않았다.
- 0.3.x 및 실험 빌드의 전용 설정은 파일에서 보존하지만 계산에 반영하지 않는다.
  강화 우선·콤보 등 공통 설정은 계속 사용한다. 빌드 초기화는 이 버전이 지원하는 설정만 지운다.
  이후 버전으로 돌아가면 보존된 전용 설정이 다시 적용될 수 있다.
- 최소 강화, DPS 추천·상세 설정, 미계산 효과 변경 승인, 방향 설정은 포함하지 않는다.
  사용 유지·끄기 허용을 포함한 0.2.8 기존 조작도 우선 유지한다. 이름과 조작 개편은 실기 피드백 후 별도 패치한다.
- 첫 테스트 빌드는 0.2.8을 사용했고, 배포 준비에서 0.3.3으로 올렸다.

설정 보존은 기존 Json.NET의 [JsonExtensionData 공식 문서](https://www.newtonsoft.com/json/help/html/SerializationAttributes.htm)를
확인하여 구현했다. 패키지·게임 DLL 참조는 기준 버전 그대로 유지하고 빌드로 검증한다.

## 0.3.0·0.3.1 수정 선별

공개된 0.3.0·0.3.1 릴리즈를 GitHub API로 읽고 `v0.2.8` 및 기준 패치 소스와 비교했다.
처음에는 조사만 했고, 이후 사용자 요청으로 미포함 항목을 구현했다.

### 친타마니 돌

발동으로 아이템이 사라진 뒤 원래 칸에 남은 레벨 보너스는 이미 적용된다.
`GameReader.ReadFixedEffects`는 `GridInventory.dungeonTempLevels`를 읽어 좌표별 `FixedEffectCell`로
추가한다. 호스트 전용 분기 밖에 있으므로 참가자의 동기화된 값도 읽는 경로다.
`PlanBuilder`는 이를 고정 칸 효과로 전달한다. 아이템 인챈트처럼 이동시키지 않는다.

현재 설치 게임 DLL의 `Charm_Chintamani`를 다시 디컴파일했다. 치명적인 피해를 받은 뒤 회복·
무적 처리와 함께 자기 좌표에 `AddDungeonTempLevel(..., addLevel)`을 호출하고 `ForceRemoveItem`한다.
클래스 초기값은 3이며, 플러그인은 이 숫자를 하드코딩하지 않고 게임에 실제 기록된 값을 읽는다.
임의로 버리거나 파괴하는 모든 경우에 +3을 예측해서 넣는 기능은 아니다.
발동 전 아이템의 회복·생존 가치를 정밀 평가한다는 뜻도 아니다.

`ChintamaniTests` 4개를 현재 작업 사본에서 재실행해 통과했다. 빈 +3 칸 활용과 배치 안정화,
아이템 이동 후 좌표 유지, 다른 칸 효과·인챈트·배수와의 조합, 보너스 제거 후 계획 무효화를 검사한다.
싱글·멀티 입력 테스트는 실제 멀티플레이 동기화 실기 검증을 대신하지 않는다.
게임 디컴파일 기록은 `artifacts/release-audit/Charm_Chintamani.txt`에 보관했다.

표시)은 아래 후속 패치에서 닫았다. **넷째는 아직 열려 있다** — 발리송과 천칭·영원의 식은 구형
평가 기준의 별도 누락 조사로 진행한다.

새 카탈로그 속성을 읽는 수정은 형식 15의 기존 캐시를 그대로 쓰면 적용되지 않는다.
수집 변경을 이식할 때 카탈로그 형식 갱신과 재현 자료 호환을 함께 처리해야 한다.
지문 검사를 무시하거나 오래된 카탈로그에 값이 있다고 가정하지 않는다.

## 후속 패치 구현

제외·교체 제한, 마음의 짐 기본 활성 보호, F10 수치 지문, 합성 부호를 수정했다.
사용자 선택에 따라 천칭은 현재 쪽을 유지하도록 탐색·후보 추천·캐시·자동 적용에 연결했다.
그때 카탈로그 20과 재현 9를 정했다. 지금은 성장 아티팩트를 담느라 카탈로그가 21이며,
20으로 모은 자료도 계속 재생한다. 구형 재현 1·카탈로그 15도 검증 후 읽는다.
새 형식 번호는 기존 0.3.x 및 실험 형식과 충돌하지 않게 정했다. 제품 버전은 배포 준비에서 0.3.3으로 올렸다.
게임 DLL의 천칭 XIdx <= 2 규칙을 직접 확인했고 툴팁에도 조작 방법을 알린다.
카탈로그 수집·게임 화면·F8의 실기는 아직 검증하지 않았다. 검사 결과는 아래 "검사 기록"에 있다.

## 검증과 다음 순서

1. 전체 기존 테스트, 추가 회귀 테스트, 포맷, 진단 도구와 게임 DLL 참조 플러그인 빌드를 검사한다.
2. 배포된 DLL로 실기 비교한다. 강화 우선 지정 전후, F2 두 탭, 합작 창 갱신, F8을 확인한다.
3. 발리송은 별도 패치로 다룬다. 게임 DLL에서 확인한 거리 조건과 WIDE 범위 확대를 근거로
   기존 평가에서의 수집·환산 누락을 조사한다. DPS 전용 구현을 그대로 가져오지 않는다.
4. 다른 제보도 이 기준 버전에서 재현한 뒤 필요한 수정만 가져온다. 종합 평가 모드나 새 설정 묶음을 다시 추가하지 않는다.

카탈로그는 형식 21로 다시 수집되며 0.3.x F10 재현은 이 버전에서 지원하지 않는다. 기존 진단
파일을 지우거나 새 버전 입력을 구형 형식으로 가장하여 읽지 않는다. 게임 폴더에 어느 빌드가
설치돼 있는지는 [현재 상태](STATUS.md)에 적는다. 교체 전 DLL은 `artifacts/game-backups/`에 둔다.

## 검사 기록

후속 패치까지 마친 뒤 `scripts/check.ps1` 통과: 테스트 572개, 실패·건너뜀 없음. 포맷·진단 도구·
플러그인 Release 빌드도 통과했다. 실제 게임 Mono로 만든 형식 1과 9 자료를 .NET 테스트에서 재생하고
변조 차단을 확인했다. NuGet 연결 실패로 취약성 자료 조회 경고 `NU1900`이 남았다. 로그는
`artifacts/baseline-0.2.8/artifacts/baseline-check/check-backport-final.log`다. 테스트의 Json.NET은
잠금 파일 기준 13.0.3, 게임 참조 어셈블리는 13.0.0.0이다.

이 숫자는 그때의 기록이다. 현재 값과 실기 진행 상황은 [현재 상태](STATUS.md)를 본다.

## 배포

소스는 비공개 저장소에 두고 공개 저장소에는 패키지만 올린다. zip의 `manifest.json` 커밋은 그
버전의 태그와 같아야 하며, `make-release.ps1`이 HEAD에 태그가 없으면 멈춘다.

0.3.3을 2026-09-10에 Pre-release로 올렸고, F10 진단 메모를 담은 0.3.4가 2026-09-11에 Latest가
됐다. 그 뒤 성장 아티팩트 지원이 들어갔다. 어디까지 실기로 확인했는지는
[현재 상태](STATUS.md)에 적는다.
