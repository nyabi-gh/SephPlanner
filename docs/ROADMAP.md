# 남은 작업

무엇을 / 왜 / 무엇이 있어야 끝나는지만 적는다. 무엇이 언제 들어갔는지는 [변경 기록](CHANGELOG.md)과 git 로그에
있고, 게임에서 아직 못 본 것은 [현재 상태](STATUS.md)의 표에 있다. 끝난 항목은 지운다.

## 1. 남의 손을 빌려야 확정되는 것

- **저사양 PC 의 진입 지연.** 2026-09-11 의 두 제보(같은 사람)에서 카탈로그 짓기가 15~20회 / 670ms 안팎이었다
  (기준선 3회 / 98.7ms). 타이틀에서 게임 데이터가 서기 전에 지었다 버린 것이다. 0.4.15 는 `OnAllDatabasesReady` 를
  덤프에만 걸어서, 카탈로그 파일이 이미 있는 사람은 여전히 폴링마다 지었다(2026-10-04 제보 `3e262106` 527회 / 5.4초).
  0.4.22 가 인게임 카탈로그 짓기도 그 신호 뒤로 미뤘다. Windows `[perf]` 의 시도 횟수가 1~3회로 떨어지면 닫는다.
- **"감점 석판 옆에 아티팩트를 놓고 다른 석판으로 +시킨다"(2026-09-11, 0.3.7 드래프트).** 단절
  (`UP 3 / DOWN 3 / LEFT -1 / RIGHT -1`)을 넣은 합성 판을 여러 조합으로 풀어도 재현되지 않았다. 당시 혈석 귀걸이가
  값어치 27 레벨이던 회귀의 증상일 수 있다. 다시 오면 F10 을 받는다.
- **이동 뒤 화면 상태를 다시 잡지 않는다.** 게임은 `Swap` 다음에 `OnItemSelected(icon, -1)` 로 석판 테두리를 끄는데
  우리는 부르지 않는다. 고치려면 게임의 선택 상태를 우리가 운전해야 하므로 잔상 제보가 실제로 이것일 때 손댄다
  ([게임 내부 조사](RESEARCH.md)의 "회전").
- **콤보 우선을 여럿 켰을 때의 열쇠·종이**(아래 "판단이 필요한 것"). 제보자의 F10 이 있어야 닫힌다.

## 2. 백로그

순서는 대략 위험이 큰 순이다. "검토 N-N" 은 2026-09-22 전체 검토(0.4.12, `8625dcf`)의 항목 번호이고, 원문은
git 로그의 `docs/notes/REVIEW-2026-09-22.md` 에 있다.

### 매 프레임 / 폴링마다 도는 것

측정 근거가 있는 것들이다. **제보 `3fc4d9ac`(79분 세션, 후보 추천 켬)에서 폴링 평균이 3.55ms 로
올랐다.** 후보 추천을 끈 나머지 두 제보는 그림이 다르다 - 아래 지문 항목.

- **상자·상점 찾기가 메인 스레드에서 가장 큰 덩어리였다.** 상자·상점 찾기 39.4초(60%),
  합성기 7.8초, 세피라이트 4.7초로 세션 합계 52.0초, 상자·상점 찾기는 평균 2.17ms 로
  기준선(1.21ms)의 1.8배였다. **씬 탐색 자체와 `SceneCache.Alive()` 는 이미 걷어냈다**
  (`NetworkRegistry` 가 `spawned` 만 돈다. [성능과 응답성](PERFORMANCE.md)의 "끝난 것").
  위 수치는 그 전에 잰 것이므로 **지금 열려 있는 것은 `OfferReader.Fill` 이 인벤토리마다 다시
  보는 `Vector3.Distance` 와 `GetComponentInParent<ItemChest>()` 뿐이고, 그것이 얼마나 남았는지는
  걷어낸 뒤로 다시 재지 않았다.**
- **세션이 길어질수록 나빠진다.** 같은 제보의 5분 단위 로그를 구간별로 환산하면 폴링 전체
  2.68 → 4.10ms, **지문 0.30 → 0.82ms(2.7배)**, 상자 1.82 → 2.30ms 다. 가방이 차는 몫과 층에
  오브젝트가 쌓이는 몫이 섞여 있어 아직 가르지 못했다.
- **고정 효과 되빼기의 비용을 안 쟀다(2026-09-22).** 폴링마다 고정 층 없는
  `TabletSimulator.Run` 이 한 번 늘었다(`FixedEffectLayer.Get`, `GameReader`). 이 비용은 `[perf]` 의
  `가방 읽기` 구간에 묻혀 따로 보이지 않는다. 0.07~0.08ms 로 묻힐 것으로 보지만 추정이다. 재려면 구간을 하나 더한다.
- **"지문 계산과 제출" 이 폴링 평균의 절반 안팎이다. 다만 고칠 값이 작다**(2026-10-04 재측정). 0.4.21 제보 넷에서
  평균 0.29~1.24ms 다. 지문의 중복은 이미 없다 - `Submit` 이 문맥·배치·전체를 한 번씩 계산하고 플러그인은 그 값을
  받아 쓴다. Unity Mono(`mono-bdwgc`)에서 41칸·아티팩트 30·석판 11 합성 판의 지문 셋이 약 0.2ms 이고, 그 큰 몫은
  `SHA256.Create()`(2.4µs)가 아니라 Mono 의 SHA-256 계산 자체(20KB 에 98µs)다. 해시 함수는 재현 자료의 지문과
  묶여 있어 바꿀 수 없다. 폴링은 40프레임에 한 번꼴이라(`698b2f07` 폴링 12,858회 / 프레임 524,880회) 0.2ms 를 덜어도
  보이지 않는다. 같은 구간의 최악 130ms 는 카탈로그를 짓고 실행기를 처음 만드는 폴링 한 번이다(`b4826648` 은 둘 다 폴링 1번, 131ms).
  **다시 열 조건:** 폴링 간격이 짧아지거나, 지문 구간 최악값이 카탈로그를 짓는 폴링이 아닌 데서 나오는 제보가 올 때.
  그때는 입력 문자열이 직전과 같으면 해시를 건너뛰는 것부터 본다.
- **빔 탐색이 cold 배치의 절반이다**(2026-10-04). 할당과 탐욕 배정의 상수는 걷었다. 남은 것은 확장·묶음 수라
  추천이 바뀐다. [성능과 응답성](PERFORMANCE.md) 4번.
- **자동 진단 수집이 메인 스레드에서 수 MB 를 직렬화한다**(검토 4-3). `Plugin.CollectDiagnostic`·
  `DiagnosticCapture` 가 리플레이·카탈로그를 직렬화하고 해시한다. `FrameCost` 에 그 단계가 없어 비용을 잰 적이 없다.
  재고(1시간) 나서 필요하면 백그라운드로 옮긴다(반나절).
- 작은 것 셋. `EnchantOf` 를 아이템마다 두 번 부른다(`GameReader`, `InventoryView`). `PluginPreferences.ToPreferences`
  가 `Revision` 캐시 없이 매번 새로 만든다. `Guide` 가 캐시 확인 전에 `AutoPlaceAvailability` 를 계산한다.

### 솔버

- **제거 조언이 평소 재계산의 8할이 됐다** (2026-09-12). 빔을 계획 사이에 돌려 쓰게 되자
  (성능 계획 2번) 남은 자리가 `DiscardAdvisor` 로 옮겨 갔다 - 제보 `3fc4d9ac` 의 재계산 676ms 중
  648ms 다. 캐시를 받지 않고 빔을 직접 돌리는 것과, 제거 후보 마흔을 하나씩 채점하며 그때마다
  `Polish` 를 파는 것 둘이 섞여 있어 갈라 재야 한다.
  [성능과 응답성](PERFORMANCE.md) 1번.
- **석판 제거 갈래의 잣대가 아티팩트 밀어내기 쪽으로 기운다.** "갈래를 가르는 것은 배치가
  아니다"는 석판 집합이 같은 갈래에만 맞다.
- **침의 대상 고르기가 대상의 지금 레벨을 안 본다** (2026-09-14). `PositionalWorth.TargetShare` 는
  `상한 레벨`로 재는데, 이는 값이 자리마다 흔들리지 않게 하려고 0.3.9 에서 고른 모양이다. 침이
  주는 것은 대상 피해의 백분율이라 **0레벨에 박힌 대상은 실제로 거의 받지 못하는데** 모델은 그것을
  모른다. 여기에 침이 고를 수 있는 72종 중 65종이 값어치가 레어도 어림값뿐이라, 지금 줄 세우기는
  사실상 "레어도 × 최대레벨" 이다. 사용자가 `강화 대상` 으로 덮을 수 있으므로 급하지 않다.
  **다시 열 조건:** 지정을 걸지 않은 사람에게서 "침이 엉뚱한 것을 강화한다" 는 제보가 또 올 때.
  그때도 값을 새로 재는 것이 아니라 상한 레벨 대신 그 배치의 유효 레벨로 재는 가장 단순한 모양부터
  본다 - 흔들림이 실제로 생기는지가 그때 확인할 것이다.
- **휘장의 혼돈 모드 크기를 못 쟀다.** `PositionalWorth.EnhanceStep` 은 레벨 한 칸이고 잰 값이
  아니다. 혼돈 모드는 능력치가 아니라 소환물 동작을 바꾸는 것이라 정적 데이터에 수치가 없다.
  **망원경 쪽은 2026-09-16 에 재어 이 상수에서 떼어 냈다**(`EnlargeSteps`, 카탈로그 23).
- **거대화 크기를 레벨 0 으로만 잰다** (2026-09-16). 게임의 거대화는 그때의 피해량에 곱으로
  걸려 레벨이 오를수록 커지는데(레벨 0 에서 1.25~2.5칸, 상한에서 3.75~6칸), `EnlargeSteps` 는
  흔들림을 피하려고 레벨 0 값을 쓴다 - 침의 `TargetShare` 가 상한 레벨로 재는 것과 같은 걱정이다.
  언제나 아래로 잡으므로 틀려도 한쪽으로만 틀린다. **다시 열 조건:** 대상 판정과 이 크기를 고친
  뒤에도 "망원경 옆에 행성이 안 모인다" 는 제보가 또 올 때. 그때는 이웃의 유효 레벨로 재고,
  폴링마다 배치가 흔들리는지를 `--churn` 으로 먼저 본다.
  제보 `24911147` 의 직접 원인은 크기가 아니라 두 이동의 탐색 누락이었다([배치 평가](PLACEMENT-OBJECTIVE.md)의
  "탐색과 최적성").
- **망원경 둘이 같은 행성을 감싸면 두 번 센다** (2026-09-16). 게임의 거대화는 중첩되지 않는다
  (`isEnhanced` 카운터를 `bool` 로 읽는다). 우리는 망원경마다 이웃을 세므로 겹치는 행성의 몫이
  두 번 들어간다. 망원경을 둘 드는 판이 드물고, 배정 비용 행렬에서 "옆 망원경이 이미 먹었다" 를
  빼려면 비용이 싸지 않아 두었다. **다시 열 조건:** 망원경 둘이 붙어 있는 제보가 올 때.
- **거대화 크기가 피해량 표의 기울기에 그대로 눌린다** (2026-09-16). `EnlargeSteps` 는
  `0.5 × 레벨 0 피해량 ÷ 레벨 한 칸` 이라 위쪽 한계가 없다. 지금 일곱 표는 1.25~2.5칸으로
  얌전하지만 기울기가 완만해지면 값이 급등한다 - 암흑 행성이 50→90(4칸) 대신 50→60 이 되면
  한 칸이 2.5 라 **10칸**이 된다. 행성의 레벨 한 칸 값어치는 레어도 어림값(1.0~1.45)이라
  기울기와 무관하게 고정이므로 분모만 작아지는 모양이다. **다시 열 조건:** 게임 패치가 행성
  피해량 표를 건드릴 때, 또는 망원경 값이 이상하다는 제보가 올 때. 그때는 카탈로그를 다시 지을
  때 이 비율을 찍어 보고(몇 칸을 넘으면 로그) 상한을 둘지 정한다.
- **후보 조언의 콤보 진행 가치가 남은 걸음 수를 안 본다.** 배치는 0.4.22 부터 진행 가치를 쓰지 않는다. 판단과
  다시 열 조건은 [배치 평가](PLACEMENT-OBJECTIVE.md)의 "앞을 보는 자리".
- **이웃 의존 아티팩트 대부분이 아직 모델 밖이다.** 목록과 게임 규칙은 [게임 내부 조사](RESEARCH.md)의
  "아직 모델 밖인 효과". 종이 중첩과 능력치 전환은 갱신 순서까지 재현해야 해서 정적 수식으로는 안 된다.
- **직접 시험이 없는 것**(검토 3-6). `CompareTo` 단계 순서와 허용 오차의 관계는 `PlacementQualityTests` 가 붙잡았다
  (2026-10-04). 남은 것은 `CharmCriteria.ReadsNeighbors`,
  `StatExchange.CrossValidate`·`IsReliable`, `DirectedCharmSupport`·`ContextStatWorth`·`BuildStatWorth`·`PreparedTablet`.
- 솔버의 작은 것(검토 3-5). `DirectedCharmSupport.Estimate` 에 메모가 없고 `ImproveTablets` 가 패스마다 할당한다. `TabletQuery`
  캐시가 호출마다 전역 lock 을 잡고 10만 개에서 통째로 비운다. `PlacementSolver.cs` 는 2,000줄이고 XML 주석이 깨진
  자리가 있다. 추정이라고 적지 않은 상수(`PriorityMultiplier`·`PriorityWorth`·`PlanBonus`, `OfferAdvisor` 의
  `0.000001`).

### 검증·도구·빌드

- 버전은 여전히 네 곳에 손으로 적힌다(`Directory.Build.props`, `[BepInPlugin]`, `CHANGELOG`, STATUS).
  `check.ps1` 이 넷이 어긋나면 멈추지만(`make-release.ps1` 도 그것을 부른다), 한 곳에서 나오게 만든 것은 아니다.
- **CI는 Plugin을 빌드하지 못한다.** DataTool 빌드·포맷은 2026-09-05 추가했고 Plugin은 로컬 `check.ps1`로 검사한다.
  근본 해법은 Plugin 의 로직을 Core 로 더 옮겨 CI 가 검사할 표면을 넓히는 것이다. 적용기의
  걸음 순서·저널·되돌리기·시간 상한은 `ApplyPlanRoutine` 으로 옮겨 가짜 격자로 시험한다.
  Plugin 에 남은 것은 사전 검증(`PlanApplier.Prepare`)과 게임 타입을 감싸는 포트뿐이다.
- **참가자 자리의 시뮬레이션 검증이 약해졌다(2026-09-22, 0.4.12).** 되뺀 고정 층을 넣으면
  `SimulationVerifier.CompareMatrices` 는 구성상 통과한다 - 층이 차이를 정의하기 때문이다.
  참가자에게 남은 진짜 검사는 석판별 `Applied`·`EffectRange` 대조와 `FixedEffectTracker` 의
  배치 불변성인데, **불변성은 아이템이 움직여야 발동한다.** 자동 배치는 스스로 이동을 만드니
  적용 앞뒤로 되빼기를 다시 재면 검사 기회를 놓치지 않는다. 호스트는 원본 목록을 쓰므로
  기존 강도 그대로다.
- **자동 진단의 중복 제거는 `stage` 를 가르지 못한다(2026-09-22).** 숫자를 지운 모양으로 묶어
  좌표만 다른 같은 오류는 한 번으로 셈하지만(`AutomaticDiagnosticPolicy.Shape`), 한 원인이
  `시뮬레이션 불일치` 와 `자동 배치 실패` 처럼 여러 단계로 흩어지면 여전히 따로 센다.
  세션 상한 10 은 그대로다.
- **`QueryVerifier` 가 카탈로그 정의만 돈다.** 합성 석판의 여러 줄 질의는 게임 원본과 대조된 적이
  없다. RESEARCH.md 의 "석판 합성" 절 참고.
- **플러그인 파일 넷이 여전히 컴파일 검사 밖이다**(검토 6-1). `FrameCost`·`GameBinding` 은 2026-10-04 에 테스트
  프로젝트로 링크했다. `SimulationVerifier`·`QueryVerifier`·`EffectStateDiagnostics`·`GrowthProgressWatch` 는 게임
  타입(`GridInventory`·`StoneTablet`·`UnitAvatar`)을 직접 읽어 링크되지 않는다. `GrowthProgressWatch` 의 판정은 이미
  Core(`GrowthProgressReading`)에 있고, 나머지 셋의 비교는 게임 행렬을 읽는 몇 줄이라 떼어 내는 값이 작다.
  **다시 열 조건:** 이 셋에서 판정이 틀린 제보가 오면 그 비교를 Core 로 옮기며 시험을 붙인다.
- 도구·CI 의 작은 것(검토 6-4). CI 에 cache·concurrency·timeout 이 없고 push+PR 로 두 번 돈다.
  `CharmValueSource` 가 스키마 오류를 삼킨다. 픽스처 생성 프로그램이 `artifacts/` 에만 있다.

### 성장(변화) 아티팩트

1.0.31 이 들여온 종류다. `Charm_GrowthStatusInstance`(→ `Charm_StatusInstance` 상속)를 쓰며
조건을 채우면 자기 칸에서 `ForceRemoveItem` 뒤 `reward` 아이템으로 바뀐다. 지금 다섯 쌍이 있다 -
방패 문장, 코등이, 견장, 공명석, 크랭크.

능력치는 이미 측정되므로 배치와 활성은 바르게 돈다.

**진행도 수집은 넣었다**(카탈로그 형식 21). 목표 횟수와 바뀔 대상을 카탈로그에 담고, 스냅샷의
`GrowthProgress` 에 인스턴스별 진행도를 적는다.

**싱글·호스트·참가자가 한 경로를 쓴다.** 게임은 `questCounter` 를 서버에만 두지만 소유자에게는
`SetEffectHUDValue` 로 표시값을 보내고, 이름이 `Charm_{인스턴스}` 라 인스턴스로 바로 이어진다.
호스트에서도 `isOwned` 라 같은 이벤트가 로컬로 발생하므로 자리를 가리지 않는다. 값은 진행도가
오를 때뿐 아니라 효과가 켜질 때(`OnEnabledEffect`)도 다시 오므로, 아이템을 옮겨 효과가 갱신되면
그 자리에서 최신값이 들어온다. 아직 한 번도 오지 않았으면 호스트에 한해 원본 필드를 읽고,
그것도 아니면 `null` 로 둔다 - 0 은 아직 아무것도 못 채웠다는 뜻이라 지어내지 않는다.
값이 매 전투마다 올라가므로 계획 지문에는 넣지 않았다.

**값어치에도 반영했다.** 진행한 만큼 바뀔 아티팩트의 값어치 쪽으로 끌어올린다(`GrowthWorth`).
빛바랜 방패 문장은 레벨 0에서 1.54 이고 철벽의 문장은 4.62 라, 다 키운 것을 안 키운 것과 같게
보면 거의 완성된 것을 빼라고 말하게 된다. 낮아지지는 않으며, 근거는 둘 중 약한 쪽을 따른다.

**진행도는 다섯 칸으로 끊는다.** 그대로 쓰면 가드 한 번마다 계획이 낡는다. 계획 지문도 같은
칸을 보고, **성장하는 아이템이 있는 가방에서만** 지문에 더한다 - 무조건 더하면 이 항목이 없던
시절의 F10 자료가 전부 지문 불일치로 거부된다. 실제 게임 Mono 자료로 만든 회귀 검사가 그것을
잡아냈다.

남은 것.

- **전투 가치로는 재지 않았다.** 바뀔 대상의 값어치도 능력치 환산이라 "강화형이 실제로 얼마나
  센가"를 잰 것은 아니다. 결투가의 견장 쌍은 양쪽 다 레어도 어림값이라 특히 그렇다.
- **성장이 끝나는 순간.** 친타마니와 같은 `ForceRemoveItem` 경로라 계획 무효화가 이미 잡을
  것으로 보이지만 실기에서 확인하지 않았다.

### 기능 (이번 작업 밖)

- **아티팩트 자리 고정(2026-09-11 요청).** "모피증 신비 빌드에서 둘이 붙어 있어야 하는데 자꾸
  옮긴다"는 제보다. 지금 F2 의 `조건 무시 칸` 은 제한 해제 칸 고정이라 다른 것이고, 자리 고정은 STATUS
  표의 "좌표/회전 고정" 으로만 남아 있었다. 모양은 **"지금 자리 고정"** 토글이 맞다고 본다 -
  칸을 고르는 UI 를 만들지 않고(HUD 는 입력을 받지 않는다) 손으로 붙여 놓은 뒤 둘 다 고정하면
  된다. 배정에서 다른 칸을 금지하고(기존 `HoldPenalty` 자리), 석판이 그 칸을 차지하지 못하게
  막고, 고정 때문에 배치가 불가능하면 계획을 포기하지 않고 그 고정만 무시하며 경고한다. 지문·재현
  자료·설정에 함께 실어야 해서 재현 형식이 올라가고, 기존 `조건 무시 칸` 과 화면 이름을 갈라야 한다.
  **구현 전에 우리 쪽에서 재현한다(2026-09-11).** 제보자에게 F10 을 되묻는 길은 닫았으므로,
  모피증 조합을 직접 만들어 솔버가 정말 둘을 떼어 놓는지 본다. 모피증이 조화의 수정이면 그 이웃
  효과는 이미 점수에 있으므로, 떼어 놓는다면 점수가 틀린 것일 수 있고 그러면 고정은 증상만 덮는다.
  실드 메이트도 "지정이 안 듣는다" 로 보였지만 점수 버그였다.
  **범위가 줄었다(2026-09-13).** 침·모래시계가 누구를 강화할지는 `강화 대상` 지정이 답했고, 그쪽은
  칸을 얼리지 않아 솔버가 짝을 더 좋은 자리로 함께 옮긴다. 자리 고정이 남는 것은 "둘이 붙어 있어야
  한다" 처럼 강화 연결이 아닌 인접 요구다. 모피증 재현은 여전히 하지 않았다.
- **패드 2단계 - 버튼 지정 UI·글리프·커서 대체(2026-09-16).** 1단계만 넣었다(지도가 닫혀 있고 다른 게임 창이 떠 있는
  동안의 `View` 로 우리 창 열기, 창의 `바로 실행` 탭). 남은 것은 셋이다. **버튼 지정 UI**:
  `ShortcutCapture<T>` 가 이미 제네릭이라 잡는 쪽만 `InputSystem.onAnyButtonPress` 로 바꿔 끼우고
  저장은 컨트롤 경로 문자열이면 된다 - 다만 **지정할 수 있는 버튼이 사실상 `View` 하나뿐이라
  지금은 고를 것이 없다.** **안내 줄 글리프**: `ControllerManager.Instance.GetController(...)` 로
  게임이 들고 있는 아이콘 셋을 쓴다. **커서가 필요한 자리 셋**(이동 모드, 빌드 창 우클릭,
  HUD 툴팁)의 패드 대체. **다시 여는 조건:** 패드 사용자에게서 "창은 열리는데 이것을 못 한다"는
  제보가 오거나, 게임이 패드 바인딩을 바꿔 빈 버튼이 생길 때. 그전에는 Steam Input 으로
  `F1`~`F10` 을 잡는 길을 안내한다(USAGE.md 의 "게임패드로 쓰기").
- **아티팩트별 최소 레벨 요구(≥N).** 다른 플래너에 있는 기능이고 이번 범위에서 뺐다.
- **로컬 런 기록.** 런 종료 시 최종 격자·점수·콤보를 로컬 JSON 으로. 백엔드 없음 원칙 유지.
- **다국어.** `Naming.CurrentLanguage = "current"` 단일 언어 구조. 15개 언어 데이터는 이미 추출
  가능하므로 배관만 남았다.

## 3. 반쯤 닫힌 것 — 아티팩트 가치 데이터

**이 프로젝트의 가장 큰 구멍이다.** 아티팩트 311종(1.0.31) 중 능력치로 값어치를 잰 것이 173종이고 137종은
레어도 어림값뿐이다. 레어도는 세기의 대리값으로 나쁘다 - 레벨 0 값어치 중앙값이 일반 1.50, 고급 1.67, 희귀 2.00,
전설 1.47 로 순서가 서지 않고, 레어도·원가·최대레벨·카테고리 등 메타데이터 14개로 값어치를 아는 106종을 10겹
교차검증해도 평균만 찍는 것(0.386)과 다를 게 없었다(0.364).

- **환산율.** 방법은 [게임 내부 조사](RESEARCH.md)의 "콤보 가중치"·"아티팩트 가치". 보정을 자유롭게 두는 반복법은
  발산하고, 씨앗을 "상한까지의 오름폭 ÷ 레벨 수" 로 재면 붙박이 보너스를 주는 아티팩트가 터진다 - 둘 다 해 봤고
  되돌렸다. 눈금(`ComboThreshold`·`ComboProgress`·`DamageBonus`·점수 비교 눈금)은 `WorthScale` 이 카탈로그를 지을 때
  잰다. 남은 손값은 `StatExchange.ShrinkageWeight` 하나인데 교차검증으로 고른 통계적 선택이라 패치로 낡지 않는다.
- **레벨이 올라도 값어치가 내려가는 것은 두 종이다**(도마뱀 판금 갑옷, 아이스 스타. `--values` 가 적는다). 도마뱀은
  레벨 0→4 에서 피해감소 +7.56%p 를 사면서 이동·공속 -8%p, 쿨감 -8 을 내는 진짜 맞교환이라 환산율로는 못 고치고,
  칸 설명이 이유를 밝힌다.
- **회피와 방어력은 선형이 아니다.** 게임은 `UnitAvatar.ApplyDamage` 에서 `dodge% = 80·ln(E/6200+1)` 로 재고 `E` 를
  10000 에서 자르며 결과를 0 에서 자른다 - 총합이 음수여도 손해가 0 이다. `GetDamageReduction` 은 방어력이 양수면
  `44.5·ln(D/40+1)`, 음수면 선형이다. 이동 속도만 선형이다. 우리는 셋 다 선형·대칭으로 본다(아래 "더 큰 갈림길").
- **발리송.** 0.3.x 에서 고르지 않고 남긴 넷째다. 게임 DLL 의 거리 조건과 `WIDE` 범위 확대를 근거로 수집·환산
  누락을 조사한다. DPS 전용 구현을 그대로 가져오지 않는다.

**손값 없이 137종을 메우는 길(2026-09-11 결정, 진행 중).** 손으로 채우는 표(`data/values/charms.json`)는 패치마다
사람이 다시 손봐야 하므로 목표가 아니다. 게임 코드에는 레벨별 숫자가 있다 - `Charm_*` 클래스 205개 중 143개가
`*ByLevel` 배열을 들고 있다.

| 묶음 | 종 | 게임이 주는 것 |
|---|---|---|
| 능력치를 게임 API 로 직접 더함 | 42 | `AddCustomStat`·`AddMaxHp` + `*ByLevel` |
| 피해를 줌 | 34 | `IAttackableCharm.GetDamage`, 대개 이미 값매긴 능력치의 몇 % |
| 소환·동료 | 15 | `damageByLevel`, `hpByLevel` |
| 마법서 | 26 | `mpCostsByLevel`·`cooldownTime`·`ammo` (피해는 prefab 안) |
| 유틸(랜턴, 잎 획득량 등) | 26 | 전투 세기가 아니다 |

**진짜 벽은 상수 하나다** - "초당 피해 1 = 레벨 몇". 2~4 묶음은 레벨별 숫자가 나오지만 발동 빈도를 모르며, 그것이
0.3.0~0.3.2 DPS 노선이 막힌 자리다.

첫 걸음(능력치 채널 넓히기)은 들어갔다. IL 을 읽어 어느 배열이 어느 능력치로 가는지 찾는다(`CharmStatScan`,
카탈로그 22, `--charm-stats`). 지켜야 할 규칙이 넷이다.

- **애매하면 버린다.** 인자를 잘못 짝지으면 틀린 능력치로 값매김하게 되고 그건 값을 안 매기는 것보다 나쁘다.
- **효과가 켜질 때 주는 것만 센다**(`OnEnabledEffect`). 조건부로 주는 것을 늘 받는 것으로 세면 크게 부풀린다 -
  인공정령 이피엘은 가드 중에만 MP 재생 50 을 주는데 그대로 세면 격자에서 가장 값진 아티팩트가 된다.
- **코드에서 읽은 표는 환산율 표본에서 뺀다**(`CharmStatTable.FromCode`). 그 표는 값어치에서도 아래 한계로만 쓴다.
- **이름이 정확히 이어질 때만 쓴다.** 코드는 `AttackSpeed`, 능력치 표는 `ATTACK_SPEED` 라 글자만 남겨 맞춘다.
  비슷해 보인다고 이어 붙이지 않는다.

남는 구멍은 대가가 배열이 아니라 상수일 때다(갈망의 보주의 `mpReserve`). 다음 걸음은 `*ByLevel` 곡선의 **모양**을
뽑는 것이다 - 137종은 전부 같은 직선(레어도값 × 레벨)이라, 절대값을 몰라도 "레벨로 3배가 되는지 1.2배가 되는지"만
맞으면 칸 배정이 나아진다. 그 뒤가 위의 상수 하나다.

**더 큰 갈림길 - 점수의 단위를 바꾸는 것(2026-09-11 논의, 미결).** 사용자가 "다른 걸 기준으로 구현해도 괜찮다"고
열어 둔 자리다.

- **지금 막히는 곳.** 능력치 표만으로는 "이 아티팩트가 센 것" 과 "이 능력치가 비싼 것" 을 가를 수 없다.
- **손 말고 다른 바깥 정보가 있다 - 게임 자신의 효과 공식이다.** 점수를 "레벨" 이 아니라 게임이 화면에 띄우는
  수치로 매기고, 한계효용으로 계산한다: `Δ효과 = f(현재총합 + Δ능력치) − f(현재총합)`. 플러그인은 현재 총합을 안다.
- **폐기한 DPS 노선과 다르다.** 그쪽은 전투 결과(시전 빈도·적 모델·시간)를 예측하려다 막혔다. 이쪽은 능력치를 게임이
  직접 보여 주는 숫자로만 옮기고 전투는 시뮬레이션하지 않는다.
- **남는 손값은 능력치 계열 20개쯤이다.** "회피 1%p 와 피해감소 1%p 와 물리 피해 1 을 어떻게 견주나" 는 사람이
  정해야 하지만 플레이어가 판단할 수 있는 종류의 값이다.
- **이것만으로 고쳐지는 것.** 회피의 0 하한, 방어력·회피의 체감, 같은 능력치를 쌓을 때의 과대평가.
- **비용.** 카탈로그 형식이 오르고 `ComboWorthMeasure`·`PositionalWorth` 가 같은 자를 쓰므로 함께 움직인다.

370ms 안팎으로 같았다.

코드는 JIT 보다 느렸다**(442ms 대 300ms). 어디를 고칠지와 무엇을 안 할지는
[성능과 응답성](PERFORMANCE.md).

## 5. 알려진 한계 (고치지 않기로 한 것)

- `CharmCriteria` 의 5/6/7 하드코딩, MUL 덧셈 누적과 0 건너뛰기, 미지 조건 토큰의 PLACED 통과,
  질의의 연속 공백 처리 — 전부 게임 자체 구현과 동일함을 디컴파일로 확인했다. "고치면" 게임과
  어긋난다. 근거는 각 코드의 주석과 RESEARCH.md, 고정 테스트는 `CharmCriteriaTests`·
  `TabletSimulatorTests`.
- **플레이 중(창 없이)의 패드 단축키는 두지 않는다**(2026-09-16). 게임이 패드 버튼을 하나도
  남기지 않고 써서, 어느 버튼을 잡아도 우리 동작과 게임 동작이 한 누름에 함께 난다
  (RESEARCH.md 의 "패드 단축키"). 막으려면 입력을 가로채야 하는데 그것은 HUD 무입력 보장을
  깨뜨린다 - 게임을 방해하지 않는다는 말의 근거가 그것이다. **다시 여는 조건:** 게임이 패드
  바인딩에서 버튼을 비울 때.
- **탐색을 더 오래 하는 모드는 두지 않는다.** 재어 보니 빔 폭을 넓혀도 얻는 것이 없다. 병목은
  폭이 아니라 잣대와 다양성이었고 그쪽을 고쳤다(`PlacementSolver` 클래스 주석).
- **솔버를 C/C++/Rust 로 다시 쓰지 않는다** (2026-09-11). 빠르기는 하다 - `Solve` 한 번이
  Mono 1,685ms 에서 추정 120~200ms 다. 그런데 그중 5.6 배는 언어가 아니라 런타임의 몫이라
  솔버를 한 줄도 안 고치고 얻을 수 있고(위 "측정 기준선"), 남은 몫은 두 구현의 동치를 지키는
  유지비 - 657개 테스트, `1e-9` 허용오차에 걸린 점수의 동치, 게임 패치마다 두 곳에 넣는 일,
  지금도 Plugin 을 못 세우는 CI - 와 맞바꿔야 한다. 옮길 크기는 근거가 아니다. 성능에 필요한
  커널은 700~900줄이지 6,867줄이 아니다(2026-09-12 정정. 자세한 것은 계획 8번).
  판단 기준은 정확도가 아니라 유지비다. 대신 할 것과 순서는 [성능과 응답성](PERFORMANCE.md).
  **다시 여는 조건:** 그 계획을 전부 하고도 `[perf]` 가 초 단위이고, 그 시간이 낭비가 아니라
  정말 필요한 계산일 때. 그때도 전체가 아니라 빔 탐색 + `Estimate` + 시뮬레이터의 커널 하나만
  떼고, 같은 입력에 같은 배치 목록이 나오는지 C# 판과 대조한다.

### 값어치 모델에서 안 하기로 한 것 (2026-09-11)

이 프로젝트는 무급이고, **판단 기준은 정확도가 아니라 "이 변경이 앞으로 나에게 일을 시키는가"**
