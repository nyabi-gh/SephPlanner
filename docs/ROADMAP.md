# 남은 작업

현재 구현과 다음 검증 순서는 [현재 상태](STATUS.md)를 따른다. 여기에는 아직 닫히지 않은 것과
다시 재기 비싼 측정값만 둔다. 완료된 릴리스의 확인 과정은
[0.2.x 시절의 확인 목록](notes/ROADMAP-0.2.x.md)으로 옮겼다.

무엇을 / 왜 / 무엇이 있어야 끝나는지만 적는다. 무엇이 언제 들어갔는지는 `CHANGELOG.md` 와 git
로그에 있으므로 여기서 되풀이하지 않는다.

## 1. 남의 손을 빌려야 확정되는 것

- **저사양 PC 의 진입 지연.** 우리 잣대는 아래 "측정 기준선" 의 카탈로그 짓기 3회 / 98.7ms 다.
  제보의 `[perf]` 에서 시도 횟수가 수십 번이거나 합계가 초 단위면 우리 것이고, 3회 안팎인데도
  느리면 게임 자체 로딩이다.
  - 짚이는 곳 하나를 닫았고 **재어서 확인했다.** `GameReader.FindLocalPlayer` 의 폴백이
    타이틀·로비에서 폴링마다 두 번 씬을 통째로 훑고 있었다. 세션이 서 있지 않으면 그 폴백은
    반드시 빈손이라는 것을 게임 어셈블리에서 확인하고 잘랐고, 실측에서 **아바타 없는 폴링
    292 회가 쓴 시간이 합계 5.5ms(한 번에 0.019ms)** 로 나왔다(아래 "측정 기준선"). 잘라내기
    전 값은 없으므로 절감분 자체는 추정이다.
  - 그래서 남은 것은 **카탈로그 짓기가 느린 기계에서 어떻게 나오느냐**뿐이다. 이쪽 기계에서는
    3 회 / 83.4ms 로 고사양 기준선(3 회 / 98.7ms)과 같다.
  - **2026-09-11 제보의 `[perf]` 는 15 회 / 666.2ms 였다**(시도 15 회). 기준선의 다섯 배이고,
    시작 5 분 뒤 로그에 이미 13 회로 찍혀 있어 세션 중 F9 로는 설명되지 않는다. 같은 제보에서
    지문 계산 최악도 92.4ms(기준선 52.6ms)다. 둘 다 한 제보의 한 기계이므로 재현을 먼저 본다.
    **제보자에게 조건을 되묻지 않기로 했다(2026-09-11).** 같은 숫자가 다른 제보에서 또 나오면
    그때 본다.
- **자동 배치 뒤 석판이 화면에 남는다는 제보(2026-09-11).** 모양이 하나 밝혀졌다. 0.3.5 에서
  넣은 회전 알림이 가방이 닫혀 있어도 **석판 툴팁**(`UI_StoneTabletTooltip`)을 화면 오른쪽
  툴팁 자리에 띄우고, 가방을 열었다 닫을 때까지 남았다. 커서가 올라간 석판에만 알리도록 고쳤고,
  가방을 닫은 채 `F8` 을 눌러도 뜨지 않는 것을 `09c06ac` 로 실기 확인했다(RESEARCH.md 의 "회전").
  커서를 올려 둔 채 돌렸을 때 옛 테두리가 남지 않는지는 아직 보지 않았다.
  - **원래 제보가 이것이라고 단정할 수는 없다.** 그 알림은 0.3.5 에 들어갔고 제보 당시의 공개
    버전에는 없었으므로, 제보자가 호스트·싱글이었다면 다른 것이다.
  - **참가자였다면 설명이 된다.** 참가자 회전은 게임의 `Rotate` 를 그대로 타고 거기서 게임이
    직접 같은 알림을 보내므로, 0.3.4 이하에서도 가방을 닫은 채 돌리면 같은 툴팁이 떴을 것이다.
    그쪽은 게임이 보내는 것이라 우리가 막을 수 없다. **제보자가 방을 연 쪽인지 참가한 쪽인지가
    갈림길이다.**
  - 여전히 남는 것: 제보자는 **월드(캐릭터 주변)** 라고 했다. 툴팁 자리는 화면 오른쪽 중앙이라
    캐릭터 근처로 읽힐 수는 있지만, 우리 쓰기 표면에는 월드 오브젝트를 만들거나 표시하는 것이
    없고 `StoneTablet` 에는 표시를 켜고 끄는 코드가 아예 없다.
  - **이 항목은 닫는다(2026-09-11).** 제보자에게 스크린샷·F10 이나 호스트/참가자 여부를 되묻지
    않기로 했다. 설명된 모양(석판 툴팁)은 고쳤고, 남은 것은 같은 증상이 다시 올 때 본다.
- **이동 뒤 화면 상태를 다시 잡지 않는다.** 게임은 `Swap` 다음에 `OnItemSelected(icon, -1)` 로
  석판 테두리를 전부 끄는데 우리는 부르지 않는다. 고치려면 게임의 선택 상태를 우리가 운전해야
  하므로, 위 제보가 실제로 이것인지 확인된 뒤에 손댄다.
- **다음 게임 패치 뒤 멀티 경로 재확인.** 개발사가 "동기화 구현이 최적화 중이라 바뀔 수 있다"고
  했다(LEGAL.md "받은 답변"). 패치 뒤에는 참가자 경로가 아직 그대로인지 다시 본다.
  - 1.0.31 에서 디컴파일로 확인했다. `GridInventory.Swap` → `LocalSwap`/`CmdSwap`,
    `DoClickAction` → `LocalDoClickAction`/`CmdDoClickAction`, `StoneTablet.Networkrotation`
    셋 다 그대로다. 우리가 쓰는 것은 이 셋뿐이고 내장 자동 정리는 부르지 않는다.
    구조가 그대로라는 것이지 참가자 세션 실기를 다시 본 것은 아니다.

## 2. 백로그

0.1.2·0.1.3 두 번의 전체 검토에서 살아남은 것들과, 그 뒤에 새로 나온 것들이다. 순서는 대략
위험이 큰 순이다. 검토 보고서 원본은 git 로그에 있다(`docs/REVIEW.md`, `docs/REVIEW-0.1.3.md`,
`docs/P1_REMEDIATION.md`, `19ab3f3` 까지).

### 매 프레임 / 폴링마다 도는 것

측정 근거가 있는 것들이다. 지금 폴링 평균은 1.92ms 라 급하지는 않다.

- **`PlanRunner.Submit` 이 지문 셋을 겹쳐 계산한다** — 폴링당 `Placement` 3회, `PlanningContext` 4회.
  실측에서 **이것이 가장 큰 끊김의 원인이다**: 최악 52.63ms 가 폴링 전체의 최악값과 같고, 합계
  145.6ms 는 상자·상점 찾기(215.9ms) 다음이다. 2026-09-05 Submit 내부는 문맥→배치→전체 순으로 재사용하도록 수정했다. 플러그인과 Submit 사이의 중복은 남아 있고 변경 후 인게임 비용은 아직 측정하지 않았다.
- 빔 확장이 확장마다 대여섯 개를 할당하고 가지치기 전에 전부 실체화한다. 먼저 실기에서 GC 끊김이
  남았는지 재고 나서 손댄다.

### 솔버

- **석판 제거 갈래의 잣대가 아티팩트 밀어내기 쪽으로 기운다.** "갈래를 가르는 것은 배치가
  아니다"는 석판 집합이 같은 갈래에만 맞다.
- **이웃·수량 효과의 지원은 종류별로 다르다.** 별조각·모래시계·벨트·비늘·열쇠와 침 사슬은
  후속 구현이 들어갔다. 효과 구조 지원과 전투 가치 추정을 구분한 [현재 상태](STATUS.md)를 참고한다.
- **망원경·휘장의 강화 크기를 못 쟀다.** `PositionalWorth.EnhanceStep` 은 레벨 한 칸이고 잰 값이
  아니다. 강화도 혼돈 모드도 능력치가 아니라 소환물 동작을 바꾸는 것이라 정적 데이터에 수치가 없다.
- **콤보 진행 가치의 모양.** `Worth.ComboProgress` 는 임계값까지 한 걸음이 남았든 넷이 남았든 같은
  값을 준다. 남은 걸음 수를 보는 편이 맞아 보이지만, 못 채운 콤보의 값어치는 결국 채우게 되느냐에
  달려 있어 정적 데이터로는 잴 수 없다.

### 검증·도구·빌드

- `LayoutCache.Of` 가 취소된 탐색 결과도 캐시한다(빌드마다 새 캐시라 지금은 안전).
- 버전은 여전히 세 곳에 손으로 적힌다(`Directory.Build.props`, `[BepInPlugin]`, `CHANGELOG`).
  `make-release.ps1` 이 셋이 어긋나면 멈추지만, 한 곳에서 나오게 만든 것은 아니다.
- **CI는 Plugin을 빌드하지 못한다.** DataTool 빌드·포맷은 2026-09-05 추가했고 Plugin은 로컬 `check.ps1`로 검사한다.
  근본 해법은 Plugin 의 로직을 Core 로 더 옮겨 CI 가 검사할 표면을 넓히는 것이다. 적용기의
  걸음 순서·저널·되돌리기·시간 상한은 `ApplyPlanRoutine` 으로 옮겨 가짜 격자로 시험한다.
  Plugin 에 남은 것은 사전 검증(`PlanApplier.Prepare`)과 게임 타입을 감싸는 포트뿐이다.
- **`QueryVerifier` 가 카탈로그 정의만 돈다.** 합성 석판의 여러 줄 질의는 게임 원본과 대조된 적이
  없다. RESEARCH.md 의 "석판 합성" 절 참고.
- DataTool의 `--help`, 단일 명령·인자 검사, `--reproduce`의 실패·차이 종료 코드를 추가했다.
- 완료(2026-09-05): 테스트 어셈블리에만 내부 접근을 허용해 이동 순열을 직접 검증한다.

### 화면

- 완료(2026-09-05): 자동 배치는 게시된 계획의 배치 지문과 검증 결과를 확인한다. 추천만 계산 중이면 동일 배치의 적용을 허용한다.

  이 항목은 그대로 남는다 - 이쪽은 후보 추천이고 저장 형식이 3상태로 바뀐다.

### 성장(변화) 아티팩트

1.0.31 이 들여온 종류다. `Charm_GrowthStatusInstance`(→ `Charm_StatusInstance` 상속)를 쓰며
조건을 채우면 자기 칸에서 `ForceRemoveItem` 뒤 `reward` 아이템으로 바뀐다. 지금 다섯 쌍이 있다 -
방패 문장, 코등이, 견장, 공명석, 크랭크.

능력치는 이미 측정되므로 배치와 활성은 바르게 돈다.

**진행도 수집은 넣었다**(카탈로그 형식 21). 목표 횟수와 바뀔 대상을 카탈로그에 담고, 스냅샷의
`GrowthProgress` 에 인스턴스별 진행도를 적는다.

**싱글·호스트·참가자가 한 경로를 쓴다.** 게임은 `questCounter` 를 서버에만 두지만 소유자에게는
`SetEffectHUDValue` 로 표시값을 보내고, 이름이 `Charm_{인스턴스}` 라 인스턴스로 바로 이어진다.
호스트에서도 `isOwned` 라 같은 이벤트가 로컬로 발생하므로 자리를 가리지 않는다. 값은 진행도가
오를 때뿐 아니라 효과가 켜질 때(`OnEnabledEffect`)도 다시 오므로, 아이템을 옮겨 효과가 갱신되면
그 자리에서 최신값이 들어온다. 아직 한 번도 오지 않았으면 호스트에 한해 원본 필드를 읽고,
그것도 아니면 `null` 로 둔다 - 0 은 아직 아무것도 못 채웠다는 뜻이라 지어내지 않는다.
값이 매 전투마다 올라가므로 계획 지문에는 넣지 않았다.

**값어치에도 반영했다.** 진행한 만큼 바뀔 아티팩트의 값어치 쪽으로 끌어올린다(`GrowthWorth`).
빛바랜 방패 문장은 레벨 0에서 1.54 이고 철벽의 문장은 4.62 라, 다 키운 것을 안 키운 것과 같게
보면 거의 완성된 것을 빼라고 말하게 된다. 낮아지지는 않으며, 근거는 둘 중 약한 쪽을 따른다.

**진행도는 다섯 칸으로 끊는다.** 그대로 쓰면 가드 한 번마다 계획이 낡는다. 계획 지문도 같은
칸을 보고, **성장하는 아이템이 있는 가방에서만** 지문에 더한다 - 무조건 더하면 이 항목이 없던
시절의 F10 자료가 전부 지문 불일치로 거부된다. 실제 게임 Mono 자료로 만든 회귀 검사가 그것을
잡아냈다.

남은 것.

- **전투 가치로는 재지 않았다.** 바뀔 대상의 값어치도 능력치 환산이라 "강화형이 실제로 얼마나
  센가"를 잰 것은 아니다. 결투가의 견장 쌍은 양쪽 다 레어도 어림값이라 특히 그렇다.
- **성장이 끝나는 순간.** 친타마니와 같은 `ForceRemoveItem` 경로라 계획 무효화가 이미 잡을
  것으로 보이지만 실기에서 확인하지 않았다.

바뀌는 순간은 친타마니와 같은 `ForceRemoveItem` 경로이므로 계획 무효화가 이미 잡는지 실기에서
확인한다.

## 3. 반쯤 닫힌 것 — 아티팩트 가치 데이터

**이 프로젝트의 가장 큰 구멍이다.** 게임 1.0.31 기준 아티팩트 311종 중 능력치 표로 값어치를 잰
것이 167종이고, 나머지 **144종은 레어도 어림값뿐**이다. 레어도는 세기의 대리값으로 좋지 않다는
것도 재서 확인했다(레벨 0 값어치 중앙값이 일반 1.50, 고급 1.67, 희귀 2.00, 전설 1.47 로 순서가
서지 않았다).

- 잰 것: 게임의 `Charm_StatusInstance.stats` 를 능력치별 환산율로 레벨 단위로 옮긴다.
  방법은 RESEARCH.md 의 "콤보 가중치" 절, 도구는 `DataTool --measure` 와 `--values`.
- 안 된 것: 게임이 매겨 둔 원가·사파이어 가격을 대리값으로 써 봤으나 상관이 약했다.
- 남은 길: `data/values/charms.json` 을 손으로 채운다. 지금은 빈 배열이다. `--values` 가 지금
  덤프 기준의 분위와 초안을 뽑아 준다.
- 아직 안 한 것: 빌드별 가중치. 같은 아티팩트라도 무엇을 노리는 빌드냐에 따라 값어치가 다르다.
- **환산율 자체도 재야 한다.** 값어치를 잰 167종조차 능력치별 환산율에 기대고 있다. 레벨이
  올라도 값어치가 내려가면 낮은 칸이 정답이 되고, 모델 안에서는 맞는 선택이지만 사용자에게는
  버그로 보인다(2026-09-11 제보). `--values` 가 그런 아티팩트와 원인 능력치를 적어 주므로
  목록은 이제 손에 있다. 1.0.31 기준 **네 종 전부**다.

  | 아티팩트 | 구간 | 원인 |
  |---|---|---|
  | 도마뱀 판금 갑옷 | 레벨 0→1→2→3→4 전부 | `MOVE_SPEED` 가 레벨마다 −2 씩 더 깎인다 |
  | 토끼마을 경비병 투구 | 레벨 1→2 | `EVASION` −400 → −800 |
  | 아이스 스타 | 레벨 4→5 | `FROST_RELIC_DAMAGE` 0 → −10 |
  | 보석 갑옷 | 레벨 0→1→2 | `PHYSICAL_DAMAGE` −3 → −5 → −7 |

  **도마뱀 판금 갑옷이 가장 급하다** - 모든 구간이 내려가므로 솔버는 언제나 가장 낮은 칸으로
  보낸다. 보석 갑옷은 [배치 평가](PLACEMENT-OBJECTIVE.md)의 출발점이었던 그 아이템이다. 그때
  고친 것은 "빈 정상 칸이 있어도 끄는" 쪽이고 레벨 곡선의 비단조는 그대로 남아 있었다.
  비단조 자체를 금지하지는 않는다 - 고칠 곳은 솔버가 아니라 `MOVE_SPEED`·`EVASION` 같은
  환산율이거나 `charms.json` 이다.

- **환산율을 다시 쟀다(2026-09-11). 다시 재기 비싼 측정이므로 결과만 남긴다.**
  스크립트와 출력은 로컬 `artifacts/exchange-remeasure-20260911/` 에 있다.

  - **환산율이 낮게 나오는 이유는 묶음 이중 계산이다.** `StatExchange.From` 은 능력치마다 따로
    "레벨 하나가 이걸 얼마 올려 주나"를 재는데, 표본 아티팩트는 그 레벨로 능력치를 여럿 동시에
    산다. 걸음을 능력치마다 중복해서 세므로 묶여 나오는 능력치일수록 환산율이 작게 나오고
    단위값이 부풀려진다. 증거는 `--values` 가 찍는 분포다 - **잰 값 107종의 레벨당 값어치
    중앙값이 1.50 인데 정의상 1.00 이어야 하는 수다.** MOVE_SPEED 를 주는 11종 중 그것만 주는
    것이 1종, EVASION 13종 중 1종뿐이다.
  - 레벨 예산을 기여분대로 나눠 되먹이면 **MOVE_SPEED 2 → 3.8, EVASION 200 → 496** 이다
    (시작값·감쇠를 바꿔도 같은 자리로 온다). 능력치 표가 내려가는 아티팩트는 6종 11구간에서
    2종 6구간으로, `--values` 목록은 **네 종에서 한 종**으로 준다. 대가가 둘 있다 - 레벨당
    분포가 납작해지고(0.73~2.67 → 0.65~1.16), `CharmWorth.Tiers` 를 다시 뽑아야 한다.
  - **도마뱀 판금 갑옷은 환산율로 고칠 수 없다.** 레벨 0→4 에서 피해감소 +7.56%p 를 사면서
    이동 -8%p, 공속 -8%p, 쿨감 -8 을 낸다. 0→1 이 단조가 되려면 DEFENSE 환산율이 1.50 이하여야
    하는데 표본 10종은 3~4.8 을 가리킨다. 빌드가 갈리는 진짜 맞교환이므로 답은 `charms.json`
    손값이거나 화면 설명이다. 설명은 0.3.6 에 넣었다.
  - **회피와 방어력은 선형이 아니다.** 게임은 `UnitAvatar.ApplyDamage` 에서
    `dodge% = 80·ln(E/6200+1)` 로 재고 `E` 를 10000 에서 자르며 **결과를 0 에서 자른다** - 총합이
    음수여도 손해가 0 이라는 뜻이다. `GetDamageReduction` 은 방어력이 양수면 `44.5·ln(D/40+1)`,
    음수면 선형이다. 이동 속도만 선형이다(`StatusInstance_MoveSpeed` 가
    `moveSpeedMultiplier += Value*0.01`). 우리는 셋 다 선형·대칭으로 값매김한다.

## 5. 알려진 한계 (고치지 않기로 한 것)

- `CharmCriteria` 의 5/6/7 하드코딩, MUL 덧셈 누적과 0 건너뛰기, 미지 조건 토큰의 PLACED 통과,
  질의의 연속 공백 처리 — 전부 게임 자체 구현과 동일함을 디컴파일로 확인했다. "고치면" 게임과
  어긋난다. 근거는 각 코드의 주석과 RESEARCH.md, 고정 테스트는 `CharmCriteriaTests`·
  `TabletSimulatorTests`.
- **탐색을 더 오래 하는 모드는 두지 않는다.** 재어 보니 빔 폭을 넓혀도 얻는 것이 없다. 병목은
  폭이 아니라 잣대와 다양성이었고 그쪽을 고쳤다(`PlacementSolver` 클래스 주석).
