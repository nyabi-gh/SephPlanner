### 0.2.0 확인 목록

## 2. 남의 손을 빌려야 확정되는 것

- **저사양 PC 의 진입 지연.** 우리 잣대는 아래 "측정 기준선" 의 카탈로그 짓기 3회 / 98.7ms 다.
  제보의 `[perf]` 에서 시도 횟수가 수십 번이거나 합계가 초 단위면 우리 것이고, 3회 안팎인데도
  느리면 게임 자체 로딩이다.
  - 짚이는 곳 하나를 닫았다. `GameReader.FindLocalPlayer` 의 폴백이 타이틀·로비에서 폴링마다
    두 번 씬을 통째로 훑고 있었다(`FindObjectsByType` 은 이 게임에서 한 번에 4ms 대다).
    세션이 서 있지 않으면 그 폴백은 반드시 빈손이라는 것을 게임 어셈블리에서 확인하고 잘랐다.
    **다만 우리 손으로는 재지 못했다** - 기준선 측정이 런 안에서만 이뤄져 이 구간의 전후 값이
    없다. 제보로 확인할 몫이다.
- **다음 게임 패치 뒤 멀티 경로 재확인.** 개발사가 "동기화 구현이 최적화 중이라 바뀔 수 있다"고
  했다(LEGAL.md "받은 답변"). 패치 뒤에는 참가자 경로가 아직 그대로인지 다시 본다.

## 3. 백로그

0.1.2·0.1.3 두 번의 전체 검토에서 살아남은 것들과, 그 뒤에 새로 나온 것들이다. 순서는 대략
위험이 큰 순이다. 검토 보고서 원본은 git 로그에 있다(`docs/REVIEW.md`, `docs/REVIEW-0.1.3.md`,
`docs/P1_REMEDIATION.md`, `19ab3f3` 까지).

### 매 프레임 / 폴링마다 도는 것

측정 근거가 있는 것들이다. 지금 폴링 평균은 1.92ms 라 급하지는 않다.

- `PlanRunner.Submit` 이 지문 셋을 겹쳐 계산한다 — 폴링당 `Placement` 3회, `PlanningContext` 4회.
- 빔 확장이 확장마다 대여섯 개를 할당하고 가지치기 전에 전부 실체화한다. 먼저 실기에서 GC 끊김이
  남았는지 재고 나서 손댄다.

### 솔버

- **석판 제거 갈래의 잣대가 아티팩트 밀어내기 쪽으로 기운다.** "갈래를 가르는 것은 배치가
  아니다"는 석판 집합이 같은 갈래에만 맞다.
- **이웃 의존 아티팩트 여섯이 남았다.** 12종 중 여섯을 넣었다(하얀 종이, 조화의 수정, 북향의 침,
  거대한 망원경, 헌신의 휘장, 그리고 목록 밖의 캘세더니 열쇠). 남은 것은 `Charm_AutoMagic`,
  `Charm_ReduceMPCost`, `Charm_RightSpellCooldownHelper`, `Charm_NearMagicBullet`,
  `Charm_WoodenBox`, `Charm_MagicCoolDownBonusByTag`, `Charm_BoltMagicMultiShot`. RESEARCH.md 참고.
- **망원경·휘장의 강화 크기를 못 쟀다.** `PositionalWorth.EnhanceStep` 은 레벨 한 칸이고 잰 값이
  아니다. 강화도 혼돈 모드도 능력치가 아니라 소환물 동작을 바꾸는 것이라 정적 데이터에 수치가 없다.
- **콤보 진행 가치의 모양.** `Worth.ComboProgress` 는 임계값까지 한 걸음이 남았든 넷이 남았든 같은
  값을 준다. 남은 걸음 수를 보는 편이 맞아 보이지만, 못 채운 콤보의 값어치는 결국 채우게 되느냐에
  달려 있어 정적 데이터로는 잴 수 없다.
- **계획 갈아타기 문턱(사용자 결정 대기).** 지금은 이득이 조금이라도 있으면 최선 배치로 갈아탄다.
  실측에서 아티팩트 하나 주웠을 때 +1.2점을 위해 19수 개편이 나왔다. 문턱을 둘지는 취향 문제다.
- **아티팩트 자리 고정이 없다.** 강화 우선은 가중치일 뿐 "이 칸에 놔라"가 아니다. 요청이 하나
  들어와 있는데(제한 해제 석판 관련) 무엇이 불만이었는지 아직 못 물어봤다. 지금도 솔버는 제약
  무시 석판을 알아서 쓴다는 것은 확인했다.

### 검증·도구·빌드

- `LayoutCache.Of` 가 취소된 탐색 결과도 캐시한다(빌드마다 새 캐시라 지금은 안전).
- 버전은 여전히 세 곳에 손으로 적힌다(`Directory.Build.props`, `[BepInPlugin]`, `CHANGELOG`).
  `make-release.ps1` 이 셋이 어긋나면 멈추지만, 한 곳에서 나오게 만든 것은 아니다.
- **CI 가 Plugin 도 DataTool 도 짓지 않는다.** `check.ps1` 로 완화했지만 구멍은 남아 있다.
  근본 해법은 Plugin 의 로직을 Core 로 더 옮겨 CI 가 검사할 표면을 넓히는 것이다(1.2 가 그 첫 걸음).
- **`QueryVerifier` 가 카탈로그 정의만 돈다.** 합성 석판의 여러 줄 질의는 게임 원본과 대조된 적이
  없다. RESEARCH.md 의 "석판 합성" 절 참고.
- **DataTool 에 `--help` 가 없고** `--solve` 는 어디에도 문서가 없다.
- `InternalsVisibleTo` 가 없어 Core 내부를 시험하려면 public 으로 열어야 한다.

### 화면

- **`F8` 이 상관없는 변화에 막힌다.** `AutoPlace` 가 새 스냅샷을 읽어 다시 제출한 뒤 상태를 보는데,
  선택지만 달라져도(상자를 여닫는 순간이 그렇다) 새 계산이 시작돼 "계산 중"으로 거절된다. 정작
  적용에 필요한 것은 `PlacementFingerprint` 가 같은지뿐이고 그것은 따로 확인하고 있다. 문구에
  "잠시 뒤 다시 누르세요"를 넣어 급한 불은 껐지만, 근본은 적용 관문이 계획 전체의 최신성을
  요구하는 것이다. **자동 배치 관문이라 0.2.0 실기 확인 뒤에 손댄다.**
- **후보 추천을 끄면 상자를 열어도 저절로 펼쳐지지 않는다.** `AutoExpand` 가 `Offers.Count` 만
  보기 때문이다. 펼침의 쓸모는 후보 목록만이 아니라 격자와 이동 목록에도 있으므로 상자가 열린
  것 자체로 펼치는 편이 맞아 보이는데, 지금 동작도 README 에 의도로 적혀 있어 취향의 문제다.

### 판단이 필요한 것

- **F10 덤프가 씬의 모든 세피라이트를 `type`·거리와 함께 나열한다.** 보상 번호와 칸 수는 0.1.3 이
  막았지만 "저쪽에 NORMAL 세피라이트가 하나 있다"는 사실 자체는 거리 제한 없이 적힌다. 진단
  가치와 원칙이 부딪히는 자리다. `inRange` 밖의 것은 개수만 남기는 선택지가 있다.
- **프리셋의 "피하는 콤보" 반영.** 지금은 양수 카테고리만 빌드 우선으로 켠다. 음수를 점수에
  쓰려면 콤보 가치를 깎는 방향이 맞는지 실제 빌드로 확인해야 한다.

### 기능 (이번 작업 밖)

- **아티팩트별 최소 레벨 요구(≥N).** 다른 플래너에 있는 기능이고 이번 범위에서 뺐다.
- **로컬 런 기록.** 런 종료 시 최종 격자·점수·콤보를 로컬 JSON 으로. 백엔드 없음 원칙 유지.
- **다국어.** `Naming.CurrentLanguage = "current"` 단일 언어 구조. 15개 언어 데이터는 이미 추출
  가능하므로 배관만 남았다.

## 4. 반쯤 닫힌 것 — 아티팩트 가치 데이터

**이 프로젝트의 가장 큰 구멍이다.** 아티팩트 299종 중 능력치 표로 값어치를 잰 것이 157종이고,
나머지 **142종은 레어도 어림값뿐**이다. 레어도는 세기의 대리값으로 좋지 않다는 것도 재서 확인했다
(레벨 0 값어치 중앙값이 일반 1.50, 고급 1.67, 희귀 2.00, 전설 1.47 로 순서가 서지 않았다).

- 잰 것: 게임의 `Charm_StatusInstance.stats` 를 능력치별 환산율로 레벨 단위로 옮긴다.
  방법은 RESEARCH.md 의 "콤보 가중치" 절, 도구는 `DataTool --measure` 와 `--values`.
- 안 된 것: 게임이 매겨 둔 원가·사파이어 가격을 대리값으로 써 봤으나 상관이 약했다.
- 남은 길: `data/values/charms.json` 을 손으로 채운다. 지금은 빈 배열이다. `--values` 가 지금
  덤프 기준의 분위와 초안을 뽑아 준다.
- 아직 안 한 것: 빌드별 가중치. 같은 아티팩트라도 무엇을 노리는 빌드냐에 따라 값어치가 다르다.

## 6. 알려진 한계 (고치지 않기로 한 것)

- `CharmCriteria` 의 5/6/7 하드코딩, MUL 덧셈 누적과 0 건너뛰기, 미지 조건 토큰의 PLACED 통과,
  질의의 연속 공백 처리 — 전부 게임 자체 구현과 동일함을 디컴파일로 확인했다. "고치면" 게임과
  어긋난다. 근거는 각 코드의 주석과 RESEARCH.md, 고정 테스트는 `CharmCriteriaTests`·
  `TabletSimulatorTests`.
- **탐색을 더 오래 하는 모드는 두지 않는다.** 재어 보니 빔 폭을 넓혀도 얻는 것이 없다. 병목은
  폭이 아니라 잣대와 다양성이었고 그쪽을 고쳤다(`PlacementSolver` 클래스 주석).
