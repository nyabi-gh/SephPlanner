### 고사양 기준선 (2026-09-03, 0.1.2 릴리스 바이너리 그대로)

개발 PC, 세피리아 1.0.30, 릴리스 zip 의 DLL 을 그대로 넣고(manifest 와 해시 일치) 탐험 하나에
들어가 세피라이트를 열고 F8 을 한 번 누른 뒤 F10. 세션은 약 100초(프레임 14423회, 폴링 402회)라
ROADMAP 이 적은 2~3분보다 짧지만, 핵심 숫자인 카탈로그 짓기는 부팅 때 한 번 도는 값이라 길이와
무관하다.

| 구간 | 횟수 | 평균 | 최악 | 합계 |
|---|---|---|---|---|
| **카탈로그 짓기(시작 시)** | **3회** | 32.90ms | 50.55ms | **98.7ms** |
| 폴링 전체 | 402 | 2.30ms | 70.47ms | 924.2ms |
| 　상자·상점 찾기 | 382 | 1.15ms | 5.22ms | 439.5ms |
| 　합성기 찾기 | 382 | 0.24ms | 5.23ms | 91.4ms |
| 　세피라이트 찾기 | 382 | 0.11ms | 8.45ms | 42.2ms |
| 　지문 계산과 제출 | 402 | 0.62ms | 67.64ms | 248.0ms |
| 화면 갱신(매 프레임) | 14422 | 0.03ms | 12.61ms | 452.7ms |
| 다시 그린 프레임 | 378 / 14423 (2.6%) | | | |

읽는 법.

- **진입 지연의 잣대는 시도 3회 / 98.7ms 다.** 제보자의 `[perf]` 에서 시도 횟수가 수십 번이거나
  합계가 초 단위면 우리 것이고, 3회 안팎인데도 느리면 게임 자체 로딩이다. 고치기 전 코드는 준비될
  때까지 초당 스무 번 시도했으므로 시도 횟수만 봐도 옛 빌드인지 갈린다.
- 폴링 평균 2.30ms 는 실기 측정(1.92ms)과 같은 자리다. 최악 70.47ms 는 한 번뿐이고 `지문 계산과
  제출` 의 최악 67.64ms 와 겹친다 - 런 첫 폴링에서 카탈로그를 짓고 `PlanRunner` 를 만드는 순간
  이다(아래 "성능에 남은 것" 2번, 예전 114ms 가 이번엔 50ms 대).
- 화면 갱신 최악 12.61ms 도 한 번이다. 어느 프레임인지는 남지 않으므로 반복되면 그때 잰다.

### 2. 남의 손을 빌려야 확정되는 것

- **진입 지연이 정말 우리 것인가.** 부팅 직후 리소스 훑기가 초당 스무 번 돌던 것은 고쳤지만
  (아래 "폴링이 메인 스레드에서 쓰던 시간"), 제보자가 겪은 지연이 전부 그것인지 게임 자체
  로딩이 섞인 것인지는 **그 PC 의 `[perf]` 절이 있어야** 안다. 볼 것은 `카탈로그 짓기` 의
  **시도 횟수와 합계 시간**이다. 위 고사양 기준선(3회 / 98.7ms)과 나란히 놓으면 갈린다.
  0.1.2 릴리스 노트에 끊김·지연이 남으면 F10 의 `[perf]` 절을 함께 올려 달라고 적어 두었다.

### 3. 성능에 남은 것 (측정 근거 있음)

순서는 남은 크기 순이다.

1. **빔 탐색 내부의 할당.** 최악 시나리오(가방 꽉 참 + 후보 8 + 합성기)가 아직 1.8GB 를
   할당한다. 유니티 Mono 의 GC 는 마킹 동안 모든 스레드를 세우므로 이것이 남은 프레임 압력의
   전부다. 손댈 자리는 빔 확장의 증분 시뮬레이션(부모 결과 재사용, O(석판수²) → O(석판수))이다.
   **먼저 재라** - 실기에서 GC 때문에 끊기는 것이 실제로 남아 있는지부터다.
2. **카탈로그 최초 생성 114ms.** 런 시작 후 첫 폴링에서 한 번. 덤프(`CatalogDump`)가 같은 일을
   이미 하므로 결과를 나눠 쓰면 없앨 수 있다("인게임 화면에 남은 것" 절).
3. **캐시 갱신이 한 폴링에 몰릴 때 16ms.** `SceneCache` 셋의 만료가 겹치면 그 폴링에서 셋을 다
   훑는다. 드물지만(세션에 몇 번) 고치려면 만료를 어긋나게 두면 된다.
4. **상자·상점 찾기 1.17ms.** 1초 캐시라 폴링 넷 중 하나가 훑는다. 간격을 늘리면 더 줄지만
   새로 떨어진 꾸러미가 늦게 보인다. 지금 값은 프레임 예산 안이라 급하지 않다.

### 4. 구조와 품질

- **CI 가 플러그인을 빌드하지 못한다.** `scripts/check.ps1` 로 완화했지만(밀기 전 로컬에서
  같은 검사 + 플러그인 빌드), 구멍 자체는 남아 있다. 근본 해법은 플러그인에 있는 로직을
  `SephPlanner.Core` 로 더 옮겨 CI 가 검사할 수 있는 표면을 넓히는 것이다.
- **감사가 아직 덮지 않은 곳.** `SettingsWindow`·`BuildWindow` 의 렌더링, `CatalogDump` 의 쓰기
  경로, `QueryVerifier`, 진단 파일들, `DataTool`. 위험 패턴 검색만 돌렸고 정독하지 않았다.
- **사소한 것 셋.** `Plugin.OnDestroy` 가 `_settings` 는 null 검사를 하면서 `_window`/`_build` 는
  하지 않는다(Awake 가 실패한 경우에만 문제). 릴리스 `manifest.json` 의
  `gameAssembly.fileVersion` 이 `0.0.0.0` 이라 그 칸이 쓸모가 없다(SHA-256 은 정상).
  `PollIntervalSeconds` 의 하한 0.05초는 성능을 고려한 값이 아니다(초당 20회 폴링이 된다).

### 5. 기능 쪽 (이번 작업 밖)

아래 절들에 그대로 있다. 성능과 무관하게 이 프로젝트의 가장 큰 구멍은 여전히 **아티팩트 가치
데이터 142종**이고("반쯤 닫힌 것"), 그다음이 **빌드별 가중치**다.

## 끝난 것

- **효과 텍스트 툴팁.** 격자 칸과 후보 목록에 마우스를 올리면 아티팩트가 실제로 무슨 일을
  하는지 보여준다. 문장은 게임의 `Charm_Basic.BuildEffectString`을 프리팹 컴포넌트에 그대로
  불러서 얻는다 — 로컬라이제이션 원문에는 `{VALUE}` 같은 자리표시자가 남아 있어 그대로 쓸 수
  없고, 그 자리를 채우는 것이 이 함수다. `showAllLevel`을 켜서 레벨별 값이 범위로 나오게 했다.
  덤프는 종류마다 한 번뿐이라 특정 레벨의 값을 담으면 다른 레벨에서 거짓말이 된다.
  TextMeshPro 서식은 `RichText.Strip`으로 걷어낸다.
- **콤보 가중치 실측.** `Worth.ComboThreshold`를 2.0(설계값)에서 3.4(실측)로, 조화의 수정
  환산값 `Worth.DamageBonus`를 0.05(짐작)에서 0.4(실측)로 옮겼다. 재는 길
  (`--measure`)과 결과는 RESEARCH.md 의 "콤보 가중치" 절에 있다.
- **프리셋 코드 가져오기.** `F2` 빌드 창에 붙여넣기 자리를 두었다. 디코더는
  `SephPlanner.Core`의 `PresetCode`이고, 즐겨찾기 아티팩트는 후보 목록 가중치로, 과일 꼬치의
  양수 카테고리는 빌드 우선 칩을 대신 눌러 주는 것으로 이었다. 칩을 대신 눌러 주는 방식이라
  가져온 뒤에도 손으로 켠 것과 똑같이 끄고 켤 수 있다. 원문 코드는 `UserSettings`에 남는다.
- **석판 합성 추천.** 가진 석판 중 어느 둘을 합치면 좋은지 알려준다. 후보 추천과 같은 방식으로
  합친 상태의 배치를 다시 풀어 증가분을 본다. 합성이 재료의 회전을 결과 질의에 구워 넣으므로
  답에는 "어느 각도로 넣을지"까지 들어간다. 그 굽는 일을 하는 `TabletQuery.Rotated`는 읽을 때
  돌리는 것과 같은 결과를 내야 하며, 회전 16조합으로 고정해 두었다. RESEARCH.md 의 "석판 합성" 절.
- **후보 미리보기(what-if).** 후보를 누르면 그걸 집었을 때의 격자를 그대로 보여주고, 달라지는
  칸을 금색 테두리로 짚는다. 다시 누르면 돌아온다. 솔버가 후보마다 이미 배치를 풀어 두므로
  계산은 늘지 않는다 - 버리던 결과를 들고 있게 한 것뿐이다.
- **아티팩트 가치 실측.** 아티팩트 사이의 우열이 레어도라는 대리값에 기대고 있던 것을 게임의
  레벨별 능력치 표에서 재는 것으로 바꿨다. 299종 중 110종이 온전히, 47종이 아래 한계로 잡힌다.
  아래 "반쯤 닫힌 것" 절에 무엇이 남았는지 있다.
- **인게임 네이티브 화면.** 플러그인이 게임 HUD 캔버스 안에 같은 내용을 직접 그린다
  (`NativeHud`/`NativeSkin`/`Widgets`). 글꼴과 아이콘은 게임이 지금 쓰는 것을 그대로 가리키고,
  크기는 게임 HUD 글자 크기에 대한 비율로 잡는다. 입력을 하나도 가져가지 않으므로 누를 것이
  없고 조작은 F5~F8 단축키다(불투명도·이동·접기·자동 배치). 게임에서 동작을 확인했다.
  배경과 한계는 RESEARCH.md 의 "인게임 UI" 절.
- **참고용 표시.** 후보 목록 머리에 순위가 참고용임을 늘 띄우고, 지금 보이는 후보 중 몇 개가
  레어도 어림값인지 세어 HUD에 적는다.
- **설정 창.** 켜고 끄기·모서리·크기·폭·불투명도·후보 추천·단축키를 `F3` 으로 여는 우리 창에서
  고른다(`SettingsWindow`). 값은 BepInEx 설정과 같은 자리를 읽고 쓴다. 게임의 `UIBase`를 상속해
  컨트롤 스택에 올라가므로 여는 동안 캐릭터 조작이 멈추고 ESC 로도 닫힌다.
  **게임 설정 창에 탭으로 붙이는 길은 만들어 보고 접었다** - 그 창이 탭 다섯에 딱 맞게 짜여 있어
  우리 탭이 들어갈 자리가 없고 선택 표시가 탭 그림마다 박혀 있다. 잰 값은 RESEARCH.md 의
  "게임 설정 창에 탭으로 붙이는 길은 접었다" 절에 남겼다.
- **단축키 충돌 해소.** 게임이 수정키를 보지 않아 Ctrl+Alt+P 가 재능 창을 함께 열고 있었다.
  게임 바인딩을 뽑아 F 키가 비어 있음을 확인하고 옮겼다. RESEARCH.md 의 "게임 단축키" 절.
- **WPF 화면에 남아 있던 다섯을 인게임으로.** 프리셋 코드·빌드 우선 콤보·강화 우선 지정은
  `F2` 빌드 창(`BuildWindow`)으로, 후보 미리보기는 `F1` 순환으로, 툴팁은 커서 좌표를 읽는
  쪽지(`Tooltip`)로 옮겼다. 아래 "옮기고 나서" 절에 정한 것과 남은 것이 있다.
- **P1 계획 안전성과 카탈로그 일관성.** `5233acd`에서 계획 generation·상태 지문·fail-closed
  검증을 도입하고, 가득 찬 가방의 실제 교체 상태와 세대별 원자적 카탈로그 게시를 구현했다.
  Windows에서 Plugin을 포함한 전체 Release 빌드와 테스트 176개를 통과했다. 게임 안의 F9/F8
  수동 인수 시나리오는 아래 확인 목록과 `P1_REMEDIATION.md`에 남아 있다.

## 옮기고 나서

다섯을 다 옮기고 실게임에서 확인한 뒤 2026-09-01에 WPF 프로젝트와 프로세스 간 파이프를
제거했다. 화면과 설정은 이제 플러그인 안에만 있다.

| 옮긴 것 | 어떻게 |
|---|---|
| 프리셋 코드 | 빌드 창의 "빌드 코드 붙여넣기" 가 `GUIUtility.systemCopyBuffer` 를 읽는다. 게임도 프리셋을 클립보드로 주고받으므로 입력 칸 자체가 없다 |
| 빌드 우선 콤보 | 빌드 창의 "콤보" 쪽. 다음 발동까지 몇 개 남았는지를 게임 콤보 패널과 같은 분수형으로 적는다 |
| 강화 우선 지정 | 빌드 창의 "아티팩트" 쪽. HUD 격자를 누르게 만들면 무입력 보장이 깨지므로 목록으로 갔다 |
| 후보 미리보기 | `F1` 로 순환한다. 자리를 번호가 아니라 후보의 열쇠(`OfferAdvice.Key`)로 기억해, 계획이 다시 풀려 순서가 바뀌어도 보던 것을 계속 본다 |
| 툴팁 | 커서 좌표를 읽어 우리가 그린 사각형과 겹치는지 직접 센다. `raycastTarget` 을 켜지 않으므로 HUD 의 무입력 보장이 그대로다 |

**정한 것들.**

- **선택은 플러그인이 제 파일에 담는다** — `%LOCALAPPDATA%\SephPlanner\plugin-settings.json`
  (`PluginPreferences`). 목록과 프리셋 원문을 BepInEx의 한 줄 설정에 억지로 넣지 않는다.
- **인게임도 `charms.json` 을 읽는다.** 측정값 파일을 DLL에 품고 `CharmValueSource`가 읽는다.
  겸사겸사
  "레어도로 어림잡은 것이 몇 개"를 세는 자리도 손으로 채운 값을 함께 보게 고쳤다 - 빠뜨리면
  채워 넣은 아티팩트까지 어림값으로 세어 화면이 실제보다 못 미더운 말을 하게 된다.
- **설명 문장은 `SephPlanner.Core` 의 `Explain` 하나로 모았다.** 화면 코드와 점수 코드에서
  설명 규칙을 중복하지 않는다.
- **창 뼈대는 `PlannerWindow` 로 묶었다.** 설정 창과 빌드 창이 같은 방식(게임 `UIBase` 상속,
  컨트롤 스택, ESC 로 닫기, 여는 동안 시간 정지)이라 한 자리에 두었다.
- **목록은 쪽 넘김이다.** 아티팩트가 서른 개 가까이 될 수 있어 다 펼치면 창이 화면을 넘어간다.
  누른다고 다시 정렬하지 않는다 - 그러면 방금 누른 줄이 다른 것으로 바뀌어 연달아 누르다
  엉뚱한 것을 지정하게 된다.
- **접힌 화면에서는 쪽지가 뜨지 않는다.** 접는 이유가 게임 화면을 가리지 않는 것인데 곁눈질용
  한 줄 옆에 쪽지가 뜨면 그 이유가 무너진다.

### 실물 확인 - 한 번 돌려 봤고, 두 가지가 걸렸다

사용자가 게임에서 돌려 봤다. **BepInEx 로그로 확인된 것**: 빌드 창과 설정 창이 뜨고, 이동
모드와 자동 배치가 돌고, 시뮬레이터 검증이 통과했다(`석판 2개와 칸별 레벨까지 일치`).

**걸린 것 둘은 고쳤으나 고친 뒤로는 아직 안 켜 봤다.**

1. **"계산 중"에서 멈춘 것처럼 보였다.** `PlanBuilder.Build`가 서로 다른 두 경우(격자가 비었다 /
   아는 아티팩트가 없다)에 똑같이 `null`을 돌려주는데 화면이 둘 다 "계산 중"으로 적고 있었다.
   새 탐험을 시작하면 아티팩트를 하나 줍기 전까지 늘 그 상태다. `PlanBlocker`로 이유를 함께
   돌려주고 양쪽 화면이 그대로 말하게 고쳤다.
2. **세피라이트 보상 창·레벨업 창에서 화면이 안 보였다.** 무엇을 집을지 고르는 바로 그 순간이라
   후보 추천이 무의미해진다. 원인은 위 "창이 열리면 감춰지는 것이 아니라 덮인다"(RESEARCH.md)에
   있다 - 정렬 순서 문제였고 중첩 캔버스로 올려 고쳤다.

같이 나온 것 둘도 고쳤다. 부팅 직후 게임의 `LocalizationManager` 가 준비되기 전에 카탈로그를
지으려다 터지던 것(`CatalogSource` 가 캐시하지 않고 물러섰다가 다시 짓는다), 그리고 솔버가
바쁠 때 빌드 지정 변경이 반영된 것으로 처리돼 버려지던 것(`PlanRunner.Submit` 이 받아들였는지
알려준다).

인게임에서 정상 동작하는 것을 확인했다.** 아래 항목 하나하나를 짚어 본 기록은 아니므로 목록은
그대로 둔다. `P1_REMEDIATION.md`의 수동 확인표(F8·F9 시나리오)도 아직 항목별 기록이 없다.

## 반쯤 닫힌 것 - 아티팩트 가치 데이터

**가장 큰 구멍이었다.** 어디에 놓을지는 잘 답하는데 무엇을 집을지를 못 답했다. 점수가 레벨
모델이라 전투 효과가 센 아티팩트와 밋밋한 아티팩트가 똑같이 `+2`로 뜨고, "얼마나 센가"에 대한
신호는 `Worth.OfRarity`의 레어도 배수(1.0~1.7)가 전부였다.

### 한 것: 게임에서 잰다

계획에 없던 길이 있었다. 콤보 가중치를 재는 데 쓴 다리 - 아티팩트와 콤보가 같은 능력치 체계를
쓴다는 것 - 가 아티팩트끼리 견주는 데도 그대로 놓인다. `Charm_StatusInstance.stats[]`의
레벨별 능력치 표를 능력치별 환산율로 나누면 아티팩트가 레벨마다 주는 것이 레벨 단위로 나온다.
`CharmStatWorth`가 그 계산이고, 플러그인이 덤프 시점에 재어 정의에 실어 준다.

- **299종 중 110종은 값어치가 전부 측정됐다**(능력치만 주는 아티팩트). 47종은 잰 값을 아래
  한계로 쓴다(고유 효과가 더 있다).
- **레어도가 대리값으로 나빴음이 확인됐다.** 전설의 레벨 0 값어치 중앙값이 일반보다 낮고,
  같은 레어도 안의 폭이 레어도 사이의 차이보다 훨씬 크다. RESEARCH.md 의 "아티팩트 가치" 절.
- **결함 하나가 잡혔다.** 레벨을 올릴수록 나빠지는 아티팩트(도마뱀 판금 갑옷)를 예전 모델은
  좋은 칸에 앉혔다.

### 남은 것: 142종은 여전히 레어도뿐

능력치를 주지 않는 아티팩트는 게임 데이터로 답이 나오지 않는다. 그건 **손으로 채우는 수밖에
없고**, 그 자리가 `data/values/charms.json`이다(채우는 법은 `data/values/README.md`).

**다만 그 판단을 댈 사람이 아직 없다.** 저장소가 비공개라 커뮤니티에서 받는 길이 막혀 있고,
게임 데이터에서 더 짜낼 것이 있는지도 아래처럼 재 보고 접었다. 그러니 이 절은 "누가 채우면
된다"가 아니라 **"채울 자리와 도구는 다 되어 있고 판단이 없다"**로 읽어야 한다. 판단이 생기는
길은 세 갈래다 - 저장소 공개(TEAM HORAY 답변에 달렸다), 로컬 런 기록이 쌓이는 것(백로그),
그리고 그때그때 아는 것만 한두 개씩 넣는 것(항목마다 따로 물러서므로 부분만 채워도 된다).

```powershell
dotnet run --project src/SephPlanner.DataTool -- --values
```

지금 무엇이 비어 있는지 찍고, 비어 있는 것만 식별자와 게임 효과 설명까지 붙여 초안으로 뽑는다.
등급 다섯 칸의 값은 측정된 분포의 분위에서 왔으므로 등급을 매기는 일만 사람 몫이다.

**배제한 것의 범위는 그대로다.** 배제할 근거가 있었던 것은 *공략 사이트를 긁어서 그 글을
재배포하는 것*이지 *공략 지식을 쓰는 것*이 아니다. 사실과 평가에는 저작권이 없으므로 공략을
읽고 우리 표현으로 등급을 매기는 데는 라이선스 문제가 없다. 출처는 `sources`에 참고 문헌으로만
적고 본문을 옮기지 않는다.

저장소가 비공개라 커뮤니티 PR 로 채우는 길은 막혀 있다. 가치 데이터만 따로 공개 저장소로
떼면 열리지만, 아직 그럴 만큼 데이터가 쌓이지 않았다.

### 재 봤으나 안 됐다: 게임이 매겨 둔 가격

142종을 사람이 채우려면 게임을 깊이 아는 사람이 있어야 한다. 그래서 그 전에 **게임 안에 이미
있는 다른 사람의 판단**을 찾아 재 봤다. `ItemEntity.cost`(원가)와 `sapphirePrice`(주머니 차원
해금가)가 후보였다. 옆에 있는 `customCost` 플래그가 선언만 되고 어셈블리 어디에서도 읽히지
않으므로, 가격이 레어도에서 자동으로 나오는 값이 아니라 아이템마다 손으로 넣은 값이라고 볼
근거가 있었다.

**답을 아는 110종으로 재 보니 쓸 수 없었다.**

```
    원가          0.34
    사파이어가     0.34
    레어도        0.34  <- 지금 쓰는 대리값
```

순위 상관이 레어도와 소수점까지 같다. 이유는 그다음 줄에 그대로 나온다 — 레어도마다 가격이
**한 값뿐**이다(일반 400, 고급 600, 희귀 800, 전설 1100. 사파이어가도 2/3/4/5). 개발사가
아이템마다 넣을 수 있게 해 두었을 뿐 실제로는 레어도별로 일괄해 두었다는 뜻이라, 가격은
레어도와 같은 말이고 새로 아는 것이 없다.

**그래도 덤프에서 빼지 않았다.** `--values`가 매번 다시 재므로, 패치로 개발사가 가격을
아이템별로 손보면 그때 저절로 드러난다. 같은 조사를 다시 하지 않기 위한 기록이기도 하다.

`PriceProxy`가 그 계산이다. 쓸 만하다고 미리 정해 두고 잰 것이 아니라, 숫자를 보고 접었다.

### 남은 142종의 모양

왜 일괄 해결이 없는지가 여기 있다. 능력치 표가 없는 142종은 컴포넌트 클래스가 **75종 남짓으로
잘게 흩어져 있다.** 가장 큰 무리가 `Charm_Magic` 26종(스킬을 하나 얻는 아티팩트)이고, 그다음이
`Charm_LeadNPC` 9종, `Charm_SummonGreenBat` 7종이며 나머지는 대부분 한두 종씩이다.

능력치 이름을 그대로 단 클래스(`Charm_IncreaseHP`, `Charm_IncreaseMoveSpeed` 등)는 같은 다리로
옮길 수 있어 보이지만 다 합쳐 일고여덟 종이다. 하얀 종이·조화의 수정처럼 하나씩 모델에 넣는
길은 열려 있으나, 한 종을 넣을 때마다 그 클래스를 따로 읽어야 하고 얻는 것은 한두 종이다.

**즉 142종은 게임 데이터만으로 한꺼번에 풀리지 않는다.** 지금은 레어도 어림값 위에 서 있고,
그것이 예전과 같은 상태이지 나빠진 것은 아니다.

### 아직 안 한 것: 빌드별 가중치

`tags`는 파일 형식과 로더에 있지만 점수에 쓰지 않는다. 데이터가 하나도 없는 지금 프로필
가중치 기계를 먼저 만들면 아무것도 흐르지 않는 배관이 된다. 항목이 쌓이면 그때 잇는다.
그때의 모양은 이미 있는 "빌드 우선" 칩(`PlanPreferences.PriorityCategories`)과 같아야 한다.

## 백로그 (순서 미정)

- **계획 갈아타기 문턱(사용자 결정 대기).** 지금은 이득이 조금이라도 있으면 최선 배치로 갈아탄다.
  실측에서 아티팩트 하나 주웠을 때 +1.2점을 위해 19수 개편이 나왔다 - 이걸 그대로 둘지, "이득이
  문턱을 넘을 때만 계획을 바꾼다"로 완화할지(점수 일부 포기)는 취향 문제라 사용자에게 물어보고
  정한다. 화면에는 +이득이 이미 떠 있어 무시하는 선택지도 있다.

- **이웃 의존 아티팩트 가치 모델 확장.** 12종 중 하얀 종이와 조화의 수정을 넣었다. 남은 열은
  `Charm_UpCharmDamage`, `Charm_AutoMagic`, `Charm_ReduceMPCost`,
  `Charm_RightSpellCooldownHelper`, `Charm_NearMagicBullet`, `Charm_PlanetModule`,
  `Charm_WoodenBox`, `Charm_MagicCoolDownBonusByTag`, `Charm_BoltMagicMultiShot`,
  `Charm_CompanionChaos`. 각자 로직이 달라 하나씩 봐야 한다. RESEARCH.md 참고.
- **콤보 진행 가치의 모양.** `Worth.ComboProgress`는 임계값까지 한 걸음이 남았든 넷이 남았든
  같은 값을 준다. 남은 걸음 수에 따라 달라지는 편이 맞아 보이지만, 못 채운 콤보의 값어치는
  결국 채우게 되느냐에 달려 있어 정적 데이터로는 잴 수 없다. 모양을 바꾸려면 그 판단 근거를
  따로 마련해야 한다.
- **프리셋의 "피하는 콤보" 반영.** 가져오기는 과일 꼬치의 양수 카테고리만 빌드 우선으로 켠다.
  음수(그 카테고리를 피하겠다는 뜻)는 화면에 개수만 보여 주고 점수에는 쓰지 않는다. 콤보 가치를
  깎는 방향이 맞는지 실제 빌드로 확인한 뒤에 붙인다.
- **인스턴스 질의 대조.** `QueryVerifier`가 카탈로그 정의만 돌아서 합성 석판의 여러 줄 질의는
  게임 원본과 대조된 적이 없다. RESEARCH.md의 "석판 합성" 절 참고.
- **후보 미리보기의 "달라지는 칸"이 잣대가 다르다.** `PlanBuilder.FillPreviews`가 후보 격자
  (`OfferAdvisor.Faster`, 빔 150)를 최선 배치(기본 빔 400)와 견준다. 두 탐색이 동점 배치를
  다르게 고르면 후보 때문이 아닌 칸이 금색으로 표시된다. 증가분 쪽은 기준을 일부러 같은 강도로
  다시 풀어 이 함정을 피해 두었는데(`OfferAdvisor.Rank`), 그 배치를 점수만 남기고 버려서
  미리보기가 쓰지 못한다. 들고 있게 하면 고쳐진다.
- **로컬 런 기록.** 런 종료 시 최종 격자·점수·콤보를 로컬 JSON으로. 백엔드 없음 원칙 유지.
- **다국어.** `Naming.CurrentLanguage = "current"` 단일 언어 구조. 15개 언어 데이터는 이미
  추출 가능하므로 배관만 남음.

## 성능 여지

체감 문제가 실제로 생겨(적용 후 반영까지 ~3초) 실측 녹화로 재고 손댔다. 스냅샷당 평균
1713ms → 348ms (RESEARCH.md "제안이 흔들리지 않게 하는 것" 절 끝).

- ~~`TabletQuery.Parse` 메모이제이션~~ 했다. 다만 병목의 주범은 아니었다(13%).
- ~~Estimate 최심부의 할당 제거~~ 했다 - 낙관적 점유를 좌표 계산으로, 정렬을 분포 세기로.
  이것이 주범이었다.
- 빔 확장의 증분 시뮬레이션 — 여전히 남은 여지. 현재 O(석판수²), 부모 결과 재사용으로
  O(석판수) 가능.

### 조언 한 번이 탐색 한 번이던 것 (2026-09-03)

위 측정은 **스냅샷 하나를 푸는 값**이었고, 조언이 그것을 몇 번 부르는지는 세지 않았다. 거기가
진짜 구멍이었다 - 후보 추천은 "이것을 집으면"을 판을 통째로 다시 풀어 답했고, 가방이 차면
밀려날 후보마다 그 짓을 반복했다. 42칸이 꽉 찬 채 후보 8개면 탐색이 288번이다.

측정한 `PlanBuilder.Build` 한 번 (42칸, 석판 6, 아티팩트 36, .NET 10 / 개발 PC):

| 상황 | 전 | 후 |
|---|---|---|
| 평상시 (후보·합성기 없음) | 203ms / 337MB | 146ms / 228MB |
| 합성기가 있는 층 | 4.3초 / 6.1GB | 0.54초 / 0.79GB |
| 상자를 열었다 (후보 8) | 26.5초 / 40GB | 0.94초 / 1.4GB |
| 후보 8 + 합성기 | 30.5초 / 46GB | 1.29초 / 1.8GB |

- ~~후보 추천의 갈래마다 도는 배치 탐색~~ 했다. **아티팩트 후보는 석판을 건드리지 않는다** -
  같은 석판 구성이면 탐색을 돌려 쓰고(`LayoutCache`), 갈래는 배정만 다시 푼다. 비용의 97%가
  탐색이고 배정은 3%다(`PlacementSolver`를 `SearchLayouts`/`EvaluateLayouts`로 가른 근거).
- ~~합성 추천의 쌍마다 도는 탐색~~ 했다. 짐작으로 줄을 세우고 보여줄 것만 제대로 푼다.
- ~~소지금이 재계산을 부르던 것~~ 했다. 지문에 값 대신 "살 수 있는가"를 넣는다.
- ~~낡아진 풀이가 끝까지 도는 것~~ 했다. `PlanRunner`가 취소를 건다.
- **남은 여지는 탐색 자체의 할당이다.** 빔 확장이 (빔 x 칸 x 회전)마다 리스트와 시뮬레이션
  결과를 새로 만든다. 위 표의 "후" 열에 남은 MB 는 대부분 여기다. 손대려면 빔 확장의 증분
  시뮬레이션(위 항목)과 같은 자리다.

### 폴링이 메인 스레드에서 쓰던 시간 (2026-09-03, 실기 측정)

위까지는 백그라운드 쪽 이야기였다. **폴링은 여전히 게임 루프 안에서 돌았고, 거기가 다음
병목이었다.** 이번에는 짐작하지 않고 플러그인이 스스로 재게 했다(`FrameCost`, F10 덤프의
`[perf]` 절). 재길 잘했다 - 감사에서 "0.5~2ms쯤 되지 않겠나"라고 적었던 값이 실제로는 **15ms** 였다.

실측(Sephiria, 세션 약 5.7분, 144fps → 프레임 예산 6.9ms):

| 구간 | 전 | 후 |
|---|---|---|
| **폴링 전체 평균** | **15.22ms** | **1.92ms** |
| 　세피라이트 찾기(씬 탐색) | 7.19ms | 0.15ms |
| 　합성기 찾기(씬 탐색) | 4.37ms | 0.24ms |
| 　상자·상점 찾기(씬 탐색) | 3.96ms | 1.17ms |
| 　가방 읽기 | 0.04ms | 0.03ms |
| 　시뮬레이터 대조 | 0.12ms | 0.08ms |
| 메인 스레드 총점유 | 6.1% | 0.77% |

**`FindObjectsByType` 한 번이 이 게임에서 4ms대다**(비활성 포함은 7ms). 안쪽을 깎을 수 있는
것이 아니므로 덜 부르는 것만이 답이었고, 셋이 각각 다른 답을 가졌다.

- ~~세피라이트를 폴링마다 비활성까지 훑던 것~~ **보상 창이 열려 있을 때만 훑는다.** 후보가 될 수
  있는 것은 그 창이 보여주는 하나뿐이라, 닫혀 있으면 아무리 찾아도 후보가 나올 수 없었다.
  비활성 포함이 필요한 이유(여는 동안 본체가 꺼진다)가 곧 창이 열린 순간이라 서로 맞물린다.
- ~~합성기·상자를 폴링마다 훑던 것~~ **결과를 잠시 들고 쓴다**(`SceneCache`, 합성기 5초 / 상자 1초).
  비싼 것은 찾는 일이지 보는 일이 아니다 - 뚜껑이 열리는 것은 이미 씬에 있던 것의 상태 변화라
  목록을 들고 있어도 지연이 없고, 층이 바뀌어 오브젝트가 파괴되면 간격과 무관하게 곧바로 다시 찾는다.
- **두 측정은 다른 세션이지만 줄어든 배수가 설계한 배수와 맞는다** - 합성기 20배 기대에 18배,
  상자 4배 기대에 3.4배, 세피라이트는 거의 돌지 않아 48배. 세션 잡음이라면 셋이 각자 예측대로
  떨어질 이유가 없다. `세피라이트 찾기`가 평균 0.15ms 인데 최악 8.39ms 인 것도 같은 근거다 -
  평소엔 안 돌고 창을 연 그 순간에만 돈다.
- **화면 갱신은 프레임당 0.03ms 로 남았다.** 49171 프레임 중 다시 그린 것은 1316 회(2.7%)로
  폴링 횟수와 거의 같다. 더티 렌더가 설계대로 듣고 있다.
- **감사에서 용의자로 올렸던 둘은 무죄였다.** 가방 읽기(`SyncDictionary` 선형 훑기) 0.04ms,
  시뮬레이터 대조 0.12ms. 측정이 아니었으면 엉뚱한 곳을 고쳤을 것이다.
- **남은 메인 스레드 스파이크는 하나다.** 런 시작 후 첫 폴링의 114ms - 위 "인게임 화면에 남은
  것"의 카탈로그 최초 생성이다. 런당 한 번이라 급하지 않다.
