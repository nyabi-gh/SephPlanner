## 1. 종합 판단

**구조를 바꿀 이유는 없다. 이 프로젝트의 약한 곳은 코드도 법무도 아니라 다음 셋이다.**

1. **CI 가 못 보는 사각지대가 플러그인 주변에 몰려 있다.** 유니티 의존이 없는 플러그인 파일 5개가
   테스트 프로젝트에 링크되지 않아 컴파일조차 검사받지 않고, 배치 스크립트는 아무것도 복사하지
   않아도 성공하며, 경고를 오류로 올리는 관문이 없다. 셋 다 같은 구멍의 다른 얼굴이다.
2. **"지금이 어디인가"를 말하는 문서 셋(STATUS·ROADMAP·HANDOVER)이 서로 다른 시점에 멈춰
   있다.** HANDOVER 가 "어긋나면 STATUS 를 믿어라"고 하는데 STATUS 쪽이 틀렸다.
3. **한 사람이 멈췄을 때의 계획이 없다.** 업데이터 저장소와 진단 서버 주소가 개인 자산으로
   하드코딩돼 있고, 서버 배포 설정의 유일본이 운영자 디스크에 있으며, HANDOVER.md 는 세션 로그다.

코드 자체에서 가장 값이 큰 수정은 넷이고 전부 한 시간 안이다. 후보 조언의 콤보 가치가 배치
점수와 다른 눈금으로 계산되는 것(1-1), 후보마다 기준 배치를 다시 푸는 캐시 충돌(1-2), 진단
전송 동의 저장이 실패해도 메모리 상태는 동의로 남는 것(2-1), `LookupMatrix` 의 선형 훑기(2-2)다.

## 2. 강점

지켜야 할 것을 먼저 적는다.

- **비교 기준이 한 자리에 있고 문서와 일치한다.** `PlacementQuality.CompareTo` 의 9단계가
  `PLACEMENT-OBJECTIVE.md` 목록과 한 칸도 어긋나지 않는다. 헝가리안 비용은 순서군이라 다단계
  우선순위를 넣어도 최적성이 유지되고, 우선순위 항은 double 안에서 정확히 표현된다.
- **조용히 틀릴 수 있는 최적화에 자기 대조가 붙어 있다.** `VerifyIncrementalPolish` 가 증분
  채점을 무작위 판에서 전체 재계산과 맞춘다.
- **적용기의 실패 모형이 코드베이스에서 가장 잘 만들어진 부분이다.** 걸음마다 반영을 확인하고,
  "확인된 실패"와 "미확정 쓰기"를 갈라 후자에서는 되돌리기조차 멈춘다.
- **계측이 주장의 근거가 된다.** `FrameCost` 가 구간별 최악값과 그 폴링의 GC 횟수까지 남겨
  "최악값이 GC 냐 JIT 이냐"를 실제로 갈랐다. `SolverCostTests` 는 시간이 아니라 탐색 횟수로
  회귀를 고정하고, 갈래가 줄어 통과하는 가짜 초록을 하한으로 막는다.
- **HUD 가 게임 입력을 건드리지 않는다는 주장에 코드 근거가 있다.** `raycastTarget` 을 전부
  끄고 커서 좌표만 읽으며, 창만 게임 컨트롤 스택에 올라가 ESC·시간 정지가 따라온다.
- **제3자 라이선스와 게임 저작물 미배포가 실제로 지켜진다.** NOTICE 가 Doorstop 과 BepInEx
  v5-lts 를 구분하고, 릴리스 스크립트가 zip 필수 항목을 검사한다. 디컴파일 산출물은 작업 트리에
  있지만 `git log --all` 로 한 번도 커밋된 적이 없음을 확인했다.
- **릴리스 스크립트가 진짜로 검증한다.** 깨끗한 트리, HEAD 태그, 버전 3중 대조, BepInEx zip
  SHA-256, 파일별 해시 manifest.
- **"단추" 금지, 고정 씨앗, 건너뛴 테스트 0, 임시 폴더 위생(재분석 지점 검사)** 전부 지켜진다.

## 3. 솔버·계획 (`src/SephPlanner.Core/{Solver,Planning,Tablets}`)

### 3-1. 후보 조언의 콤보 가치가 배치 점수와 다른 눈금이다 (높음, 1시간)

- 위치: `Solver/OfferAdvisor.cs:306` → `Solver/Worth.cs:63-64`
- 문제: `ComboValue` 가 `Worth.OfComboStep` 을 부르는데 그것은 `WorthScale.Default`(하드코딩
  2.59/0.32)로 계산한다. 배치 점수는 `problem.Scale`(카탈로그가 잰 눈금)로 계산되고 `Rank` 는
  둘을 더해서 줄을 세운다(`:227`).
- 근거: 같은 파일 `:517-519` 의 주석이 "카탈로그가 잰 눈금은 기본값과 다르다(콤보 2.1768 대
  2.59)"라고 스스로 적는다. Core 에서 `Worth.OfComboStep` 을 채점에 쓰는 곳은 여기뿐이다.
- 영향: 콤보 가치가 약 19% 부풀려져 후보 순위가 뒤집힐 수 있다. 화면의 `ComboBonus` 도 다른 단위다.
- 제안: `EvaluateCombo`/`ComboValue` 에 `problem.Scale` 을 넘긴다. `Worth` 의 정적 위임에
  "표시용이며 채점에 쓰지 않는다"를 적는다. 회귀 시험 하나.

### 3-2. 기준 배치 캐시가 앞보기와 번갈아 서로를 밀어낸다 (높음, 1시간 임시 / 반나절 제대로)

- 위치: `Solver/LayoutCache.cs:101-106`, `Solver/OfferAdvisor.cs:179`·`:358`, `Solver/Lookahead.cs:41`,
  `Planning/PlanBuilder.cs:200`
- 문제: `Baseline` 캐시가 한 칸이고 적중 조건이 `ReferenceEquals(_baselineProblem, problem)` 이다.
  `Rank` 의 후보 루프가 `BestTrial`(원 문제)과 `lookahead.GainOf`(늘어난 문제)를 번갈아 부르므로
  매번 상대를 밀어내고, 미스마다 `EvaluateLayouts` 전체가 다시 돈다.
- 영향: 후보 8개면 기준 배치가 2번이 아니라 약 16번 풀린다. `PERFORMANCE.md` 가 "조언이 가장
  큰 덩어리"라고 적은 비용의 상당 부분이 여기다. `LayoutCache.Searches` 는 빔 탐색만 세므로
  `SolverCostTests` 가 이 낭비를 못 본다.
- 제안: 임시로는 `Rank` 가 이미 가진 기준 배치를 `BestTrial` 에 인자로 넘긴다. 제대로 하려면
  캐시를 2~4칸으로 넓히고 `BaselineSolves` 계측을 붙여 `SolverCostTests` 로 고정한다.
  효과는 `[perf]` 로 전후를 잰다.

### 3-3. 제거·인챈트 조언의 문턱 `0.001` 이 점수 눈금 안의 잡음이다 (중간, 30분)

- 위치: `Solver/DiscardAdvisor.cs:108`·`:130`, `Solver/EnchantAdvisor.cs:175`
- 문제: 나머지 비교는 `problem.Scale.ScoreStep`(제보에서 0.0319~0.05)으로 끊는데 여기만 절대
  상수 0.001 이다. `PLACEMENT-OBJECTIVE.md` 는 그보다 작은 차이를 환산 잡음이라고 못 박는다.
- 영향: 잡음만으로 "버리세요"·"인챈트하세요"가 뜰 수 있다. 되돌릴 수 없는 조언이라 손해가 비대칭이다.
- 제안: `ScoreStep` 으로 바꾸거나 바로 옆의 `PriorityPlacement.Compare` 하나로 판정한다.

### 3-4. `Compare` 의 1e-9 허용오차가 문서가 금지한 비추이 비교다 (중간, 2~3시간)

- 위치: `Solver/PlacementQuality.cs:72-73`, `Solver/PlacementSolver.cs:13`(`PlanBonus = 2e-8`)
- 문제: `Value` 는 눈금으로 양자화돼 안전하지만 `Familiarity`·`ComboProgress` 는 아니다.
  지금 안전한 것은 `PlanBonus` 가 1e-9 의 20배라는 문서화되지 않은 결합 때문이고, 이 비교자가
  `List.Sort`(`PlacementSolver.cs:891`)에 들어간다. `ScoreStep` 은 public setter 라 0 이 될 수 있다.
- 제안: `PlanBonus` 선언부에 관계를 적고 고정 시험을 둔다. `Familiarity` 도 눈금으로 끊어
  엡실론을 뺀다.
