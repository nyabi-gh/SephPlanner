## 1. 종합 판단

- **1인 비영리 모드로서는 엔지니어링 수준이 이례적으로 높다.** Core 가 Unity 와 분리돼 게임 없이
  테스트 856개로 검증되고, 재현 파일·상태 지문·시뮬레이션 대조·증분 채점 자기검증·탐색 횟수 고정
  시험처럼 "조용히 틀리는 것"을 막는 장치가 촘촘하다.
- **가장 큰 위험은 코드가 아니라 릴리스 과정이다.** 게임 안 확인보다 공개가 훨씬 빠르고, 업데이터가
  모든 사용자에게 매 판을 권한다. 실제로 같은 날 공개된 0.4.18 의 신비 변경에서 탐색 회귀가
  재현됐다(3-2).
- **새로 확인한 결함은 대부분 안전장치와 보조 경로의 가장자리에 있다.** 후보 추천의 번호 충돌,
  참가자 세션의 모순 잠금이 한 번의 폴링 뒤 풀리는 것, 첫 실행 실패 안내가 가려지는 것, 이동 중
  단축키가 무시되는 것이다.
- **UI/UX 는 설계 철학이 좋다.** HUD 가 입력을 뺏지 않고 쪽지로 근거를 보여 준다. 다만 첫 5분
  경험, 행동 뒤 피드백, 표기 일관성에서 신뢰를 깎는 작은 결함이 많다.
- **코드 품질은 모듈 경계와 규약 문서화가 강점이다.** 약점은 거대 클래스(`Plugin.cs` 1,622줄,
  `PlacementSolver.cs` 2,019줄), 그냥 `int` 로 다루는 식별자, 같은 값을 매기는 경로가 여럿인
  구조다. 이번 결함 가운데 두 건이 번호 공간 혼동에서 나왔다.

## 3. 가장 먼저 볼 문제

영향이 큰 순서다. 모두 이번에 새로 확인한 것이다.

### 3-1. 게임 안 확인보다 공개가 빠르다 (높음)

- 근거:
  - 0.4.0(9/13)부터 0.4.18(9/24)까지 12일 동안 정식판이 19개 나왔다. 9/16 과 9/17 에는 하루
    4개씩이다(UTC 기준).
  - 0.4.0 이후 Pre-release 는 0개다.
  - STATUS 의 "지난 릴리스 기록"과 인계가 거의 모든 판에 "게임에서 확인하지 않았다"고 적는다.
    STATUS 가 정한 공개 조건("이 확인이 드래프트를 Publish 로 넘기는 조건이다")이 작동하지 않는다.
  - 태그도 공개 전에 여러 번 옮겨졌다. 태그 푸시로 돈 CI 기록상 `v0.4.8` 은 약 14분 사이 커밋
    넷을, `v0.4.13`·`v0.4.14` 는 셋을 가리켰다.
- 실제 피해: 0.4.14 에서 기본 켜짐으로 나간 "새 판에서 지난 판 지정 정리"가 ★/▽ 를 매판 지워
  불만이 나왔고, 0.4.18 에서 되돌렸다.
- 업데이트 창은 `releases/latest` 만 보고 매 실행마다 새 판을 권한다. "이 버전 건너뛰기"와 변경
  요약이 없다.
- 제안:
  - 실기 확인 전 판은 Pre-release 로 낸다. 업데이터가 이미 무시하므로 그대로 베타 채널이 된다.
  - 실기 체크리스트를 통과하거나 자동 진단이 N일 조용하면 정식으로 승격한다.
  - `publish-release.ps1` 이 두 manifest 의 `commit` 을 태그와 대조하게 한다.

### 3-2. 0.4.18 신비 변경(`808088e`) 뒤 탐색이 "종이 끼우기"를 못 찾는다 (높음)

- 위치: `Solver/PositionalWorth.cs:123`(신비 규칙이 있으면 콤보 가치 0). 배정 비용은 직전 반복의
  행렬로 계산하고, `Polish` 는 교환을 하나씩 본다.
- 근거(합성 6×1 판 재현): 신비 둘, 종이 하나, 인챈트된 아티팩트 하나를 놓았다. 종이를 끼워 문턱을
  넘기고 강한 아티팩트를 새 ×2 칸으로 옮기면 8점인데, `Solve` 는 현재 배치 그대로 6점을 낸다.
  규칙이 없는 옛 경로는 8.59점 배치를 찾는다.
- 영향: 이중 계산을 없앤 것은 맞다. 하지만 그 값이 종이·침·열쇠를 신비 쪽으로 끌던 유일한 탐색
  신호였다. 0.4.18 은 실기 없이 공개됐다.
- 제안: 점수가 아니라 탐색에만 쓰는 유인을 둔다. 문턱을 넘기는 배치에 "새 ×2 칸의 최선 증가분"
  어림을 배정 비용으로 주거나, 단계가 바뀐 교환은 기각하기 전에 재배정한다. 재현 판은 회귀 시험으로
  둔다.

### 3-3. 후보 추천의 임시 번호가 번호 없는 아이템과 충돌한다 (중간)

- 위치: 후보 번호는 -1, -2, …에서 나온다(`Solver/OfferAdvisor.cs:182`·`:189`). 번호 없는 아이템은
  `-(칸 번호+1)` 이다(`Runtime/ItemIdentity.cs:20-21`).
- 근거(3×1 판 재현): 동행 증표가 첫 칸(번호 -1)에 있으면 후보 평가가 증표 자리를 덮어쓴다. 증표가
  사라지고 석판을 밀어내 증가분이 -2 가 된다. 증표 번호가 -100 이면 정상(증가분 0)이다.
- 영향: 옮길 수 없는 증표가 앞쪽 8칸에 있으면 후보의 증가분, 밀어낼 대상, 미리보기가 모두 틀린다.
  `ItemIdentity` 주석의 "부딪히지 않는다"는 전제가 깨진다.
- 제안: 후보 번호를 판의 최소 번호보다 작은 구간(예: -1000 이하)에서 준다. 시험 하나.

### 3-4. 참가자 세션의 "모순" 잠금이 다음 폴링에 풀린다 (중간)

- 위치: `Tablets/FixedEffectTracker.cs:92-107` 의 같은 층·같은 배치 분기가 `Contradicted` 와
  상관없이 `Trustworthy = true; Reason = ""` 를 쓴다. 소비처인 `Plugin/FixedEffectLayer.cs:133` 과
  `Plugin/SimulationVerifier.cs:35` 는 막힘 문자열의 길이만 본다.
- 근거(재현): 관측 a→b→c 로 모순이 판정된 뒤 같은 c 를 한 번 더 넣으면, 모순 표시는 참인데 이유가
  빈 문자열이 된다.
- 영향: 모순으로 막힌 자동 배치가 한 번의 폴링 뒤 조용히 열린다. `a1f24e8` 의 의도("모순은 돌아와도
  풀리지 않는다")와 반대다.
- 제안: 이 분기에서 모순 상태면 `Trustworthy` 와 `Reason` 을 건드리지 않는다. 모순 직후 같은 관측을
  넣는 시험을 붙인다.

### 3-5. 다른 키를 누르고 있으면 단축키가 먹지 않는다 (중간)

- 위치: 모든 단축키가 `KeyboardShortcut.IsDown()` 을 쓴다(`Plugin/Plugin.cs:228-244`). BepInEx
  5.4.23 의 `ModifierKeyTest` 는 마우스를 뺀 모든 키가 떼어져 있어야 참이다(소스 확인).
- 영향: WASD 로 이동하거나 Shift 를 쥔 채 F4·F7·F8 을 누르면 반응이 없다. 사용자에게는 "가끔 안
  먹는다"로 보인다. USAGE 가 권하는 "Steam Input 에 F키 얹기"도 이동 중에는 막힌다. README 문제
  해결 표에 이 원인이 없다.
- 제안: 판정을 직접 한다. 주 키가 눌렸고 지정한 수정키가 모두 눌렸으면 참으로 보고, 지정하지 않은
  Ctrl·Alt·Shift·Cmd 만 거부한다.

### 3-6. 첫 실행에서 "데이터 생성 실패 - F9" 안내가 가려진다 (중간)

- 위치: `_panelAwaitingRefresh` 가 첫 프레임에 켜지고(`Plugin.cs:148`) 실행기가 생긴 뒤에만
  꺼진다(`:940`). 그런데 이 검사가 `Waiting()` 보다 먼저 돈다(`:1043`).
- 영향: 카탈로그를 짓는 동안에도, 짓다가 실패해도 화면은 "최신 게임 상태를 읽는 중입니다."뿐이다.
  일부러 넣은 복구 안내(`Waiting()` 주석: "화면은 영영 '준비 중'이었다. 되살릴 키를 여기서 말한다")가
  무력화된다. INSTALL.txt 의 "데이터 준비 중"도 첫 실행에는 뜨지 않는다.
- 제안: 실행기가 없으면 `Waiting(null)` 을 먼저 본다.

### 3-7. CI 가 간헐적으로 실패하고 재실행으로 넘어간다 (중간)

- 근거(로그 확인):
  - 문서만 바꾼 `1cef51a`(실행 34804800593)에서 `PlanRunnerTests.ASupersededRunIsToldToStop` 이,
    `31fc519`(실행 35800893160)에서 `StatsCountDiscardedSolvesAndTheBacklog` 가 5초 대기 시한을
    넘겨 실패했다.
  - 재실행으로 초록을 만든 실행이 2건 있다(`1fc5e68`, `655dddb`). 어느 문서에도 기록이 없다.
- 원인(추정): 실행기는 `ThreadPool.QueueUserWorkItem` 으로 돈다(`Runtime/PlanRunner.cs:517`).
  시험은 풀 스레드를 최대 5초 붙잡는 대리자와 벽시계 대기에 기댄다. 병렬로 도는 무거운 시험과
  겹치면 스레드 풀이 모자랄 수 있다.
- 영향: 유일한 자동 관문이 "빨강이면 다시 돌린다"로 길든다. PlanRunner 의 진짜 경합 회귀를 가려낼
  수 없다.
- 제안: 작업 투입기를 주입하고 시험에서는 수동으로 돌려 결정적으로 만든다. 당장은 비병렬
  `[Collection]` 으로 묶고 `--blame-hang-timeout` 을 켠다.

### 3-8. 같은 판의 Windows·macOS Core 가 서로 다른 바이너리다 (중간)

- 근거: 같은 커밋(`60cc57b`)의 Core 인데 MVID 가 다르다(Windows `25ae4c88…`, macOS `0cd8bc03…`).
  SHA-256 도 다르다(`3b9704…` / `f8ccbb…`). DLL 에 빌드 PC 의 PDB 경로가 박혀 있다
  (`C:\Users\Nyabi\Documents\Code\…`, `/Users/nyabi/…`).
- 영향:
  - 재현 자료의 `CoreBuild` 가 "정보 버전 + MVID"라서(`Runtime/PlanReplay.cs:16-18`), Mac 제보를
    Windows 에서 엄격하게 재현하면 "계산 코드가 저장 당시와 다릅니다"로 실패한다(종료 코드 1).
  - `--allow-model-change` 로 돌리면 개발 PC 의 측정값으로 값어치 표를 덮어쓴다
    (`DataTool/PlanReproduce.cs:23`·`:49-54`). 제보자 입력 그대로 재생할 수 없다.
- 제안: 결정적 빌드를 켠다(`ContinuousIntegrationBuild` 나 `PathMap`, SDK 정확 고정). 그다음 공개
  단계에서 두 ZIP 의 Core 해시가 같은지 검사한다.

### 3-9. 업데이트 manifest 가 시험되지 않은 영구 계약이다 (중간)

- 위치: `Runtime/UpdatePackage.cs:27-38` 은 정규식으로 **첫** `"version"` 을 집고, `"path"` 바로
  뒤의 `"sha256"` 만 읽는다. 실제 manifest 에는 `bundled.bepinex.version`(5.4.23.5)도 있어, 지금은
  `make-release.ps1` 의 키 순서 덕분에 맞게 읽는다. 시험은 손으로 쓴 manifest 만 쓴다.
- 영향: 새 ZIP 을 읽는 쪽은 이미 깔린 옛 업데이터다. 키 순서를 바꾸거나 필드 하나를 끼우면 모든
  사용자의 자동 업데이트가 멈추고, 업데이트로는 고칠 수 없다. CI 는 초록이다.
- 제안: `make-release.ps1` 이 실제로 만든 manifest 를 골든 픽스처로 커밋한다. 스크립트 끝에서 같은
  `Extract` 로 자기 ZIP 을 검증한다.

### 3-10. HUD 에 녹색 "+0"과 "제외 후 재배치 +0"이 뜬다 (중간)

- 위치: 판정 문턱은 0.001 인데 표시 형식은 `0.#` 이다(`Plugin/Ui/NativeHud.cs:432`·`:844`·`:855`,
  배지 `:439-466`).
- 근거(직접 실행): 0.02 는 "+0"(녹색), -0.03 은 "-0", 배지는 "(0)"으로 나온다.
- 영향: 이득이 사실상 없는데 아이템을 빼라고 권하는 모양이 된다. 9/22 검토 3-3(`0.001` 절대
  문턱)이 화면에 드러나는 증상이다.
- 제안: 문턱을 `ScoreStep` 으로 바꾸고, 표시도 같은 눈금 미만이면 "변경 없음"으로 한다.

### 3-11. macOS 사용자 안내에 빈 곳이 있다 (중간)

- F키: 맥 키보드의 F1~F12 는 기본이 밝기, Mission Control(F3), Spotlight·Launchpad(F4),
  음소거(F10) 같은 시스템 기능이라 fn 없이 누르면 게임에 가지 않는다. README 와 INSTALL-macos
  어디에도 안내가 없다. 단축키 표시는 Cmd 키를 `KeyCode` 원문(예: `LeftCommand`)으로 보여 준다
  (`PluginSettings.cs:517-529`).
- 데이터 폴더: `Runtime/PlannerData.cs:67-68` 이 `LocalApplicationData` 한 줄로 경로를 정한다.
  Unity Mono 에서는 `~/.local/share`(숨김 폴더), .NET 8 이상인 DataTool 에서는
  `~/Library/Application Support` 로 풀려 둘이 다를 가능성이 크다(Mac 실측 필요). 문서는
  `%LOCALAPPDATA%` 만 안내해, Mac 사용자는 설정을 초기화하거나 제보 사본을 지울 수 없다.
- 제안: INSTALL-macos 에 fn 키, 데이터 폴더, 초기화 방법을 적는다. 경로는 OS 별로 명시한다.

### 3-12. 진단 서버의 가용성 — 알려진 전역 한도의 새 변형 (중간)

- 업로드 횟수 한도(알려진 것)만이 아니라 POST 동시 처리 한도도 전역이다. 느리게 흘리는 연결 둘이
  60초씩 붙잡으면 모든 전송이 429 가 된다(`Diagnostics/DiagnosticServer.cs:48-50`·`:105`).
- 보존 정리 루프에 예외 처리가 없다(`Diagnostics/DiagnosticRetention.cs:8`). 파일 하나를 못 지우면
  .NET 의 기본 동작(`StopHost`)으로 서버가 멈춘다.
- 연쇄: 전송이 실패하면 HUD 에 "진단 전송 실패 … 로컬 보관: `C:\Users\<계정>\…`"가 가리지 않은
  전체 경로로 12초 동안 뜬다(`Plugin.cs:657`). 방송 중이면 그대로 드러난다.
- 제안: IP 별 한도와 IP 별 용량을 둔다. 정리 루프는 파일 단위로 예외를 잡는다. HUD 에는 제보
  번호만 보여 준다.

## 5. UI/UX

### 좋은 점

- HUD 가 입력을 전혀 가져가지 않고 게임 글꼴·아이콘·배율을 빌려 쓴다.
- 접힘과 펼침이 나뉘어 있고, 선택 창이 열리면 저절로 펼쳐진다.
- 쪽지가 "왜 이 배치인가"를 설명한다. 추천 도구의 신뢰에 가장 중요한 부분이다.
- 자동 배치 잠금 사유가 사람 말로 나온다.
- 창이 게임 컨트롤 스택에 올라가 ESC 와 시간 정지가 게임과 똑같이 동작한다.

### 첫 5분 (가장 중요)

- 첫 진입 흐름: 업데이트 창과 긴 자동 진단 동의 창이 먼저 뜰 수 있다. 런에 들어가도 3-6 때문에
  "읽는 중"만 보인다. 접힌 한 줄에 나와야 할 조작 안내는 이미 소모돼 있다(9/22 검토 5-2 미해결).
- 첫 성공에 필요한 세 가지가 화면에 없다. F7 로 펼치기, F8 로 적용, 칸에 마우스를 올리면 이유가
  보인다는 것이다.
- 제안: 첫 런에 한 번만 이 세 가지를 담은 안내 카드를 띄운다. 데이터 준비 중에는 진행률을 보여
  준다.

### 신뢰를 깎는 표기

- 3-10 의 "+0".
- **좌표 단위가 화면마다 다르다.**
  - 이동 목록은 0부터 센다: `(2,3) → (0,1)`, `회전 1 → 3`(`MoveOrder.cs:41-57`).
  - 쪽지는 1부터 센다: "3열 4행"(`NativeHud.cs:857`). 격자는 "90°"다(`:1178`).
  - "3열 4행 → 1열 2행", "우클릭 2번"처럼 하나로 통일하기를 권한다.
- **조사가 고정돼 있다.** "F8 를 다시 누르세요"(`Plugin.cs:1437`), "F6 로 고정"(`:1568`), 업데이트
  창의 "새 버전 X 이 있습니다" 같은 식이다. 키와 버전은 바뀌므로 이미 있는 `Explain.With` 를 쓰거나
  조사 없이 쓴다.
- **예외 원문이 화면을 덮는다.** "계산 실패 - " 뒤에 영어 예외 원문이 붙어 HUD 전체를 덮는다
  (`Plugin.cs:1053`).
- **새 조어가 설명 없이 나온다.** "배치 미확보", "막힘N", "다음 칸 +N"이 그렇고, 배지의 "활성 보존
  우선"은 설정의 "사용 유지"와 헷갈린다.

### 행동 뒤 피드백

- F9 는 시작·완료·검증 결과가 화면에 나오지 않는다. 검증 경고는 다시 "F9 를 실행하세요"라고 해서
  안내가 순환한다(`NativeHud.cs:581`).
- F10 의 제보 번호는 12초 알림으로만 보인다. 클립보드 복사를 하거나 F3 에 "최근 제보 번호"를 두기를
  권한다.
- 결과 줄이 HUD 에서 가장 작고 흐린 글이라 성공과 실패가 같아 보인다.
- **자동 배치를 사람이 되돌리는 기능이 없다.** 적용기가 이미 걸음 기록을 갖고 있으니, 상태가
  그대로일 때 "직전 자동 배치 되돌리기"를 여는 것은 자연스러운 확장이다.

### 정보 배치와 접근성

- 후보 줄의 증가분(+N)이 맨 끝에 있어 가장 먼저 "…"로 잘린다(`NativeHud.cs:220`·`:844`).
- 선택 창이 열렸을 때 가장 필요한 후보 목록이 격자와 이동 6줄 아래에 있다.
- **색만으로 전달하는 정보.**
  - 후보 이름의 빌드 표시(민트)와 보통 글의 휘도 대비가 1.04:1 이다(`:803`).
  - 골드 부족은 빨간 가격 하나뿐이다(`:833-835`).
  - 칸 바탕 위의 흐린 글과 붉은 글은 대비가 3.4~3.6:1 로 권장치 4.5:1 에 못 미친다.
  - ● 기호나 "(골드 부족)" 같은 글자 표지를 붙이기를 권한다.

### 입력과 기기

- 3-5(이동 중 단축키)와 3-11(맥 fn 키).
- 업데이트 창의 기본 초점이 "업데이트"라 패드 A 연타가 곧 수락이다(`UpdateWindow.cs:41-42`).
- 패드 "바로 실행" 탭에 F9·F10 이 없어서, 경고가 시키는 F9 에 패드로 닿지 못한다
  (`Plugin.cs:1269-1276`).
- 멀티에서는 시간이 멈추지 않는데, 업데이트·동의 창이 "우리 창이 없을 때"만 보고 뜬다
  (`Plugin.cs:484`·`:789`). 전투 중에 조작을 가져갈 수 있으니 런 밖에서만 띄우는 편이 안전하다.

### 구조적 제안 (설계 필요)

- **빌드 지정의 인지 부하.** 지정할 것이 많다(★/▽ 각 3단계, 사용 유지, 끄기 허용, 목표 레벨, 조건
  무시 칸, 침·모래시계·별조각 우선, 콤보 우선). "기본"(★, 사용 유지)과 "고급"으로 나누고, 각
  지정이 이번 배치에서 무엇을 바꿨는지 쪽지에 한 줄로 보여 준다.
- **단축키 정리.** 드물게 쓰는 F5(불투명도)와 F6(이동)은 설정 창으로 옮기고, 화면 안내는 3개로
  줄인다.
- **설정 창 설명.** 항목별 설명이 없다. cfg 에 이미 있는 설명을 초점이 간 행 아래 한 줄로 보여
  주고, "가방 확인 간격" 같은 기술 설정은 고급으로 옮긴다.
- **현지화 준비.** UI 는 한국어인데 아이템 이름은 게임 언어를 따라가, 영어·일본어 클라이언트에서는
  두 언어가 섞인다. 당장 번역하지 않더라도 사용자 문장을 한 곳에 모아 두면, 흩어진 오류 문장 문제
  (9/22 검토 4-6)도 함께 풀린다.

## 6. 코드 품질·구조

### 강점

- 계층이 분명하다. Core(Unity 무의존), Plugin(게임 포트), DataTool, 진단 서버가 나뉘어 있고, 적용
  루틴까지 Core 로 옮겨 가짜 격자로 시험한다.
- 규약을 코드로 고정한다. `VerifyIncrementalPolish` 와 `SolverCostTests`(탐색 횟수 고정 + 하한)가
  있다.
- 취소를 예외로 통일했고, 받아들인 시도에서만 작업 공간을 새로 지어 부분 결과가 캐시에 들어가지
  않는다.
- 문화권에 독립적이다(`CultureInfo` 를 41곳에서 씀).
- 서버의 입력 방어가 충실하다.

### 약점

- **거대 클래스.** `Plugin.cs`(필드 약 60개에 입력·카탈로그·진단·업데이트·패널·자동 배치가 한데
  있음), `PlacementSolver.cs`(정적 2,019줄), `NativeHud.cs`(1,230줄).
- **원시 타입 집착.** 아티팩트 번호와 칸 번호가 둘 다 `int` 라 이번에 결함 두 건(3-3, `Estimate`)이
  나왔다. `CharmId` 나 `CellIndex` 같은 얇은 구조체를 두면 컴파일러가 막아 준다.
- **중복 경로.** 같은 값을 매기는 경로가 셋(`RankValue`, `Value`, `Describe`), 콤보를 세는 법도
  셋이다. 한쪽만 바뀌면 탐색 신호가 조용히 바뀐다(3-2 가 그 예).
- **흩어진 안전 상태.** 여러 곳에서 켜고 끄는 `RequiresResync` 깃발과 static `_routine` 에 걸려
  있다. 적용이 겹치는 문제의 뿌리다.
- **주석.** 약 8,500줄로 소스의 30% 정도다. 대부분 "왜"를 적어 가치가 크지만, 날짜·버전·제보
  번호로 경위를 적은 곳이 51곳이다. AGENTS.md 의 "Minimal Comments"와 부딪히니, 경위는 커밋과
  notes 로 옮기고 코드에는 불변식만 남기는 편이 낫다.
- **탐색 구조.** "교환 하나 + 직전 행렬 헝가리안"이라 둘이 동시에 움직여야 좋아지는 수(침 쌍, 신비
  종이, 망원경 행성)에 구조적으로 약하고, 사례별 보정이 쌓이고 있다. 중기적으로는 비용 한도 안의
  2-교환이나 짧은 대규모 이웃 탐색을 검토할 만하다.

## 7. 문서·프로세스

- 릴리스 속도와 검증 문제는 3-1 과 같다.
- **문서 구조.** 마크다운이 약 7,800줄이고 링크는 전부 살아 있다. 다만 같은 사실(제보 경위, 릴리스
  내역)이 CHANGELOG, STATUS, HANDOVER, notes, 긴 커밋 메시지에 3~4벌 적힌다. 문서가 계속 어긋나는
  구조적 원인이니, 사실 종류마다 정본을 한 곳에 두고 나머지는 링크로 잇기를 권한다.
- **용어집 없음.** 조어(갈래=Trial, 빔 열쇠, 앞보기, 되빼기)를 풀어 주는 용어집이 없다.
- **값어치 모델.** `charms.json` 이 빈 배열이라 311종 중 137종(약 44%, STATUS 의 2026-09-11 실측)이
  레어도 어림값에 기댄다. 추천 품질의 상한이 여기서 정해진다.
- **피드백 경로.** GitHub Issues 가 0건이라 피드백은 자동 진단과 이메일에 의존한다. 이슈 템플릿,
  프라이버시 고지, 1인 유지 위험은 9/22 검토 7-5~7-7 그대로다.

## 10. 확인하지 못한 것

- 게임 실행과 플러그인 빌드는 할 수 없었다. 그래서 다음은 코드 근거의 판단이다: 화면 잘림·겹침,
  씬 전환 때 HUD 가 파괴되는 빈도, 단축키 체감 빈도, 맥의 실제 폴더 경로.
- 게임 규칙의 정확성(디컴파일 대조)은 확인하지 않았다.
- 재현은 합성 판으로 했다. 실제 제보 자료(`reports/`)는 저장소에 없다.
- 성능 수치는 .NET 측정과 코드 구조에서 나온 것이고, Mono 게임 안 측정이 아니다.
