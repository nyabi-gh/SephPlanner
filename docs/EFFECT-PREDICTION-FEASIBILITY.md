# 효과 예측 가능성 검증

## 결론

기준을 **싱글플레이 자동 배치의 마지막 교환 직후**로 정하고, 초기 내부 상태와 실제 실행할
이동·효과 갱신 순서를 입력으로 제공하면 종이와 일반 가산형 능력치 전환을 재현하는 방향은
가능하다. 최종 좌표와 레벨만 받는 현재 솔버에 수식만 추가해서는 완전한 예측이 되지 않는다.
배치 이후 임의 시점의 전투·버프·다른 모드 동작까지 항상 정확하게 예측할 수 있다는 뜻은 아니다.

이번에는 별도 진단 도구에 상태 재현 모델과 반례 검사를 구현했다. 자동 배치에는 연결하지
않았다. 실기 결과와의 일치가 아직 검증되지 않았으므로 제품의 예측 완료로 취급하지 않는다.

## 근거와 실험

기준 게임 DLL의 SHA-256은
`c3939a7d431f1362daca655938480569e11f501f7d0820a989873765555a7c39`다.
로컬 디컴파일의 다음 구현을 확인했다.

- `GridInventory.LocalSwap`: 아티팩트 객체를 유지하고 좌표와 딕셔너리 항목을 바꾼다.
  종이의 이전 카테고리가 객체 재생성으로 초기화되는 구조가 아니다.
- `ReleasePermission`: `Order`만으로 정렬한 목록에서 카테고리를 갱신하고 콤보를 센다.
  이어서 석판·활성 상태·효과 갱신을 처리한다. 비활성화도 종이 카테고리를 다시 갱신할 수 있다.
- `Charm_WhitePaper`: 자기 카테고리를 먼저 비우고 양옆의 현재 카테고리를 읽는다.
  이웃 카테고리를 재귀적으로 완성한 후 읽지 않는다.
- `Charm_AddStatByAnotherStat`, `Charm_AddStatByDefense`: 인벤토리 갱신에서는 기존 전환분을
  제거한 뒤 원본 능력치를 읽는다. 타이머에서는 원본을 먼저 읽고 마지막 값과 다를 때만
  제거·재적용한다. 두 이벤트를 같은 계산으로 합칠 수 없다.
- `UnitAvatar.GetCustomStatUnsafe`: 기본 기여·계산 보너스·증폭·원소 전환을 거친다.
  원소 전환은 가장 큰 비율의 대상을 선택하며 동률이면 원소 배열의 앞쪽이 우선한다.
  다른 원소에서 들어온 전환분을 다시 연쇄 전환하지 않는다.

`CategoryReplay`는 초기 카테고리를 복사해 가지고, 명시된 교환 및 갱신 이벤트만 실행한다.
종이·침·열쇠의 카테고리 규칙을 다루며 활성 판정이나 콤보 효과 전체를 구현한 것은 아니다.
`StatReplay`는 전환을 제외한 기본 기여, 증폭, 전환별 기존 적용값과 마지막 원본값을 구분한다.
가산형 대상의 제거·재적용과 원본 능력치 조회를 재현한다. 비가산형 `StatusInstance`나
현재 프리팹을 이 모델로 자동 변환하는 어댑터는 아직 없다.

| 합성 입력 실험 | 결과 |
|---|---|
| `EMBER` 아티팩트–종이 A–종이 B–`EMBER` 아티팩트. 초기 A는 `EMBER`, B는 비어 있음 | A→B 갱신은 두 종이가 비고, B→A 갱신은 둘 다 `EMBER`를 가짐 |
| 같은 종이 초기 상태와 같은 갱신 이벤트열 | 동일한 결과로 재현됨 |
| 원본 A 기본값 10, A→B와 B→A의 단위 1 가산형 전환 | A→B 순서 갱신 후 A=20, 역순 후 A=10 |
| 원본 A 기본값 10과 자신의 이전 전환분 10, 마지막 원본값 10 | 인벤토리 갱신 후 A=20, 타이머 이벤트 후 A=30 |
| 양방향 가산형 전환을 반복 갱신 | 합성 사례에서는 값이 계속 증가하여 유한한 고정점으로 수렴하지 않음 |

이 숫자와 상호 전환 구성은 경계·반례 검사를 위한 합성 입력이다. 실제 아이템에 이 순환이
존재하거나 플레이 중 같은 증상이 발생했다는 실측 결과가 아니다. 가능한 모든 전환을
무조건 고정점에 수렴시켜 계산하는 접근이 안전하지 않음을 보여준다.

## 재현 명령

```powershell
dotnet run --project src/SephPlanner.DataTool -c Release -- --prediction-probe
dotnet test tests/SephPlanner.Tests/SephPlanner.Tests.csproj -c Release --filter FullyQualifiedName~EffectPredictionTests
```

실험 명령은 기대한 반례 결과가 아니면 종료 코드 1을 반환한다. 테스트는 추가로 음수의
내림, 증폭 후 계산, 원본을 주는 아이템 제거, 중복 적용 방지, 비활성 전환 제거, 원소 전환의
동률 선택·비연쇄성, 침의 순환, 열쇠→침→종이 전달, 교환 후 이전 상태 보존을 검사한다.
0 이하 전환 단위와 정수 변환 범위 밖 입력은 검증되지 않은 동작으로 명시적으로 거부한다.

## 실제 적용에 필요한 단계

1. **갱신 전후의 실제 기록 확보.** F10에 직접 기여·계산 보너스, 정렬 전 열거 순서,
   전환의 마지막 원본값과 타이머 경과·주기·발화 횟수를 추가했다. 단일 F10 자료는
   이벤트 기록 자체가 아니다. 게임이 제공하는 `GridInventoryStartPermission` /
   `GridInventoryEndPermission`과 실제 효과 콜백을 관찰해 초기 상태·호출열·결과를 대조해야 한다.
2. **출처별 능력치 어댑터 구현.** 일반 능력치, 콤보, 석판, 전환, 다른 동적 효과의 기여를
   분리하고 게임 `StatusInstance`가 실제로 바꾸는 키와 연산으로 변환해야 한다. 현재 총량에서
   알려진 전환분만 빼고 나머지를 영구적인 기본값으로 놓으면 아이템 제거 시 다시 틀린다.
3. **좌표 후보를 이동 이벤트열로 평가.** `ApplyPlanRoutine`은 싱글플레이에서 즉시 반영되는
   교환 사이에 반영 대기 프레임을 요구하지 않는다. 다만 교환마다 `Permission` 갱신은 발생한다.
   후보 최종 좌표만 평가하지 말고 실제 적용과 같은 교환·회전 순서 및 중간 콤보·활성을 재현해야 한다.
4. **같은 조건의 실기와 비교한 범위만 제품에 연결.** 기존 카테고리 관측값 기반 추정은 유지한다.
   확인하지 않은 콜백·비가산형 전환·외부 변경은 정확 예측으로 표시하지 않는다. 참가자 멀티의
   서버 처리 시간과 적용 뒤 전투 시간 경과는 별도 범위다.

현재 모델은 작은 규칙 단위의 구현 가능성을 보여준다. 전체 게임 상태를 정확히 재현하는
엔진이나 실제 이동 후 결과를 보증하는 기능은 아직 아니다.

## 검사 결과

`--prediction-probe`는 종료 코드 0으로 기대한 순서 의존 반례를 재현했다.
`scripts/check.ps1`에서 새 재현 검사 15개를 포함한 전체 450개 테스트, 포맷,
DataTool·Plugin 빌드가 통과했다. 실패·건너뜀과 빌드 경고·오류는 0개다.
게임 안에서 수집한 실제 이벤트열과의 비교는 아직 수행하지 않았다.
