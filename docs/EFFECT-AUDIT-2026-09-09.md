# 효과 누락과 상호작용 점검

앞부분의 판정 표는 최초 점검 당시 상태다. 이후 구현은 이 문서의 후속 작업 절과
[현재 상태](STATUS.md)를 함께 읽는다.

전체 효과를 확인한 뒤 평가 모델을 바꾸는 순서가 맞다. 현재 평가는 정적 능력치 환산과 일부
자리 효과를 지원하지만, 특수 동작을 모두 시뮬레이션하지 않는다. 희귀도 추정은 그 누락을
보충하는 값이지 효과 구현의 증거가 아니다.

## 범위와 근거

- [전체 대응 목록](EFFECT-AUDIT-INVENTORY-2026-09-09.md): 저장 카탈로그의 아티팩트 299종,
  동작 클래스 136종, 석판 68종, 콤보 20종을 점검 당시 어셈블리와 전수 대조했다.
- `Assembly-CSharp.dll` 전체를 `ilspycmd`로 디컴파일하고, 배치·카테고리·연결·능력치 전환
  경로와 활성 조건 10종을 상세 대조했다. 클래스 목록에는 상속 관계와 직접 호출 흔적도 남겼다.
- 카탈로그는 게임 1.0.30에서 저장된 형식 9다. 점검 당시 코드 형식 11의 프리팹 전수 재수집은
  수행하지 않았다. 따라서 299종을 현재 게임의 모든 활성 아이템 수라고 단정하지 않는다.
- 전체 타입 대조는 완료했으나 모든 전투 이벤트·상태값 조합을 실기로 검증한 것은 아니다.
  특히 마법 프리팹, 소환물, 상태 효과의 실제 전투 효율은 별도 검증 대상이다.
- 원본 게임 코드·DLL·카탈로그는 로컬에서만 사용한다. 전체 목록에는 식별자·요약만 기록했다.

소스 근거는 `ItemCatalog.LoadCharms/LoadStatMeasurement/LoadCombos`,
`CharmWorth.Resolve`, `PlacementSolver.ScoreOf`, `PositionalWorth`, `ComboCounting`,
`PriorityComboPlacement`, `Worth.OfComboStep`, `CharmCriteria`, `TabletSimulator`다.
게임 어셈블리와 입력 파일의 SHA-256은 전체 목록에 있다.

## 판정 기준

| 판정 | 뜻 |
|---|---|
| 규칙 반영 | 해당 위치·활성·수량 규칙을 모델링함. 전투 효율 정확도와 별개 |
| 부분 반영 | 기본 능력치 또는 관계 일부만 있음. 추가 효과·조건·대상 가치가 빠짐 |
| 효과 미반영 | 별도 동작 계산이 없고 희귀도나 정적 표로 대신함 |
| 추가 검증 | 게임 코드에서 가능성을 확인했지만 실제 프리팹·상태가 없어 결론 유보 |

저장 표 기준 105종은 정적 표, 52종은 정적 표와 추정, 142종은 추정 경로다.
이는 기존 환산 검사와 같은 분류이며 현재 모래시계 연결 모델 등은 별도로 봐야 한다.
정적 표가 있는 아이템도 다른 능력치와의 전환·전투 이벤트까지 완전히 지원된 것은 아니다.

이 그룹은 상수 가중치를 더 붙이는 것으로 해결되지 않는다. 배치별 최종 효과를 모으는 구조가
먼저 필요하며, 정적 배치 효과와 전투 시나리오를 구분해야 한다. 전투 효과 136개가 모두
검증됐다는 의미가 아니라, 136개 동작을 빠짐없이 목록에 올리고 현재 처리 경로와 연결한 것이다.

## 콤보

1. `Worth.OfComboStep`은 모든 콤보에 발동 3.4, 진행 0.43을 공통 적용한다. 측정된 콤보별
   능력치를 배치마다 합산하지 않는다. 측정 도구의 존재와 런타임 반영을 구분해야 한다.
2. `ItemCatalog.LoadCombos`는 `addStatByCombo`와 `setStatus`만 발동 단계에 넣는다.
   `ComboEffect_FlameSword`, `ComboEffect_Debuff`, `ComboEffect_Mystic`,
   `ComboEffect_Alchemy`, `ComboEffect_Guardian`, `ComboEffect_DarkCloud`가
   `OnRequestComboData`에서 직접 추가하는 단계는 합치지 않는다. 저장 카탈로그의
   `FLAMESWORD`는 4/6/8/10만 있다. 실제 프리팹의 특수 단계 값은 재수집으로 확정해야 하며,
   클래스 생성자의 기본값을 프리팹의 실제 수치로 단정하면 안 된다.
3. 해결은 특수 클래스마다 숫자를 복사하는 것이 아니라, 게임의 공통 콤보 데이터 경로에서
   발동 단계를 수집하는 것이다. 효과 설명 번역 성공 여부와 단계 수집을 결합하지 않아야 한다.
   `RequestComboData`가 런타임 상태를 요구하는 경우는 오류를 알리고 불완전한 카탈로그로 표시한다.
4. 신비 각인은 별도 규칙과 동기화된 좌표를 읽는 모델이 있다. 이 부분을 콤보 전투 효과 전체가
   지원됐다는 뜻으로 확대하면 안 된다.
5. 동적 카테고리는 기본 정의에 더하는 것인지 대체하는 것인지도 구별해야 한다. 침과 종이는
   `GetItemCategory`를 대체한다. 저장 프리팹의 정적 카테고리가 비어 있는 사례만으로 일반화를
   보장할 수 없다. 유니크 페어가 더한 개수와 제거 후보의 개수 변화도 후속 대조 대상이다.
6. F2 우선 콤보 탐색은 열쇠·종이를 대상으로 한다. 이번 종이 채점 수정이 침을 함께 옮기는
   전용 탐색까지 추가한 것은 아니다. 판정·평가·탐색의 지원 범위를 따로 표시해야 한다.

## 석판과 활성 조건

- 석판 68종 중 67종은 정적 쿼리, 1종은 사용자 쿼리다. 사용자 쿼리는 `GameReader`가
  인스턴스에서 읽는다. 각 석판의 쿼리·조건을 전체 목록에 기록했다.
- 게임 `StoneTablet`의 레벨·비활성·조건 무시·배수 효과는 `TabletSimulator`가 처리한다.
  현재 저장 카탈로그에는 과거 비교 35,616건, 불일치 0건이 기록돼 있다. 이는 이번에 게임을
  실행해 다시 측정한 결과가 아니다. 현재 입력에서도 동등한지 재수집 시 재검증해야 한다.
- 배수 누적과 인챈트 적용 순서는 기존 포팅 경로를 유지한다. 석판 수에 반응하는 아티팩트와
  신비 같은 외부 각인은 쿼리 파서만 검증해서는 확인되지 않는다.
- 배치 조건 9종은 현재 게임 `GetCriteria`와 코드 대조에서 차이를 찾지 못했다. `FullHP`는
  전투 상태 조건이므로 현재 항상 만족으로 취급한다. 사용 유지가 체력 만점을 보장하는 것은 아니다.
- 미지의 조건 이름은 현재 `None`으로 처리된다. 향후 게임 조건 추가를 자동으로 정상 지원으로
  오인하지 않도록 카탈로그의 미지원 조건 진단이 필요하다.

## 이번 수정과 검증

종이와 침의 카테고리 연결을 회귀 테스트로 먼저 재현했다. 직접 침과 침 사슬 두 사례 모두
수정 전에는 예상 `EMBER` 대신 빈 목록으로 실패했다. `PositionalWorth.CategoriesOf`가
실제 이웃 배치를 받을 때 침의 최종 대상 카테고리를 반환하도록 바꿨고, 종이의 양옆 판정이
그 경로를 사용하도록 연결했다. 대상이 사라지면 종이의 카테고리도 사라지는 경우를 함께 검사한다.

`scripts/check.ps1`에서 테스트 382개(실패·건너뜀 0개), 포맷, DataTool·Plugin 빌드가
통과했다. 빌드는 경고·오류 0개다. 실제 게임 화면과
멀티플레이에서 이번 변경의 동작은 아직 확인하지 않았다. 이번 점검은 0.2.5 배포물을 변경하지 않는다.

## 후속 작업: 수량·행별 능력치와 관측 카테고리

카탈로그 형식 14에 `ContextStatBonus`와 종이의 `match`를 추가했다. 제품 버전은 0.2.6을
유지한다. 벨트는 첫 여섯 인벤토리 인덱스의 아티팩트 수를 세며 자신과 비활성 아티팩트도
포함한다. 소비 아이템은 제외한다. 검은 비늘은 각인이 아닌 `stoneTablets.Count`를 센다.
열쇠는 프리팹의 행 카테고리와 게임 `SearchCategory`의 네 가지 능력치 대응을 사용한다.
빈 행 카테고리도 배열에서 제거하지 않아 뒤 행의 주기가 바뀌지 않도록 했다.

레벨별 원래 수치는 프리팹에서 읽고, 독립적인 일반 능력치 표의 `StatExchange`로 환산한다.
`StatusInstance_Critical`, `FireDamage`, `IceDamage`, `LightningDamage`가 원래 값을 해당
`ECustomStat`에 그대로 더하는 것을 확인했다. 추가 능력치를 환산 기준의 표본으로 넣지는 않는다.
계산 가능한 효과는 정적 능력치와 수량별 능력치의 합으로 평가하며 레어도 추정값을 중복해서
더하지 않는다. 환산 누락은 추정 하한을 유지하고 표시하며, 가중치는 이득에만 적용한다.
직접 지정한 가치 설정은 우선한다. 원소 증폭·전환 후의 실제 DPS를 계산한 것은 아니다.

종이·침·열쇠는 `GetItemCategory`를 덮어쓰므로 전체 개수 계산에서도 정적 카테고리를
더하지 않는다. 종이의 일치 개수는 프리팹에서 읽는다. 종이 이웃의 카테고리는 정적 정의가
아닌 스냅샷의 최근 관측값을 읽고, 현재 자신의 콤보 몫을 뺄 때도 관측값을 쓴다.
관측값 변화는 계획 지문에 포함한다. 이것은 종이 중첩의 완전한 이동 후 시뮬레이션이 아니다.

`GridInventory.ReleasePermission`은 `charms.Values`를 `Order`만으로 정렬해 한 번씩
`OnPreSetEffectRefreshed`를 호출한다. 같은 순서인 종이끼리는 안정 정렬을 보장하지 않는다.
종이는 자기 값을 지운 다음 이웃의 현재 값을 읽으므로 이전 상태와 호출 순서에 따라 달라진다.
그 뒤 활성 갱신에서 `OnDisabledEffect`가 다시 호출될 수도 있다. 빈 집합에서 재귀적으로
고정점을 구하는 방식은 이를 재현하지 못한다. 현재는 관측값을 이용한 추정임을 툴팁에 표시한다.

능력치 전환도 수식을 확인했다. 방패 가방은 `floor((float)방어력 / 10)`을 레벨별 배수와
곱한다. 다른 능력치 전환은 프리팹의 `perBaseStatByLevel`로 원본 능력치를 나눈 뒤 내림하고
각 대상 능력치의 `addByLevel`을 곱한다. 하지만 원본은 `GetCustomStatUnsafe` 결과로,
